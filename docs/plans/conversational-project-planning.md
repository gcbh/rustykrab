# Plan: Conversational Project Planning

**Status:** Proposed
**Date:** 2026-09-01

## 1. Product idea

The primary interface for autonomous software delivery is an ongoing
conversation with a project orchestration agent. The user should not have to
arrive with a complete specification, learn a schema, or author YAML.

The orchestration agent helps the user discover and shape the project over
time. It inspects the repository, develops options, records decisions, exposes
assumptions, identifies the next useful uncertainty, and keeps a coherent
project model behind the conversation.

Only the next sufficiently understood slice is compiled into a frozen execution
contract. That internal contract is generated by the system and is not the
planning experience.

```text
ongoing conversation
  <-> evolving project model
       -> human-readable projections
       -> readiness assessment
       -> proposed execution slice
       -> authorization
       -> frozen internal delivery manifest
       -> autonomous delivery
       -> observed result
       -> project-model reconciliation
```

This preserves both halves of the product promise:

- planning is collaborative, exploratory, and easy to revise; and
- once a slice is authorized, implementation, verification, PR creation,
  merge, deployment, and assurance can proceed without user supervision.

## 2. The planning conversation

The orchestration agent is the user's stable counterpart for the life of a
project. Internal research, architecture, implementation, and verification work
may use fresh specialized contexts, but they report through the orchestration
agent. The user does not have to coordinate a collection of agents.

A useful planning turn may do several things:

1. interpret the user's new information in the context of the whole project;
2. inspect relevant repository or environment facts;
3. update the project model through a proposed revision;
4. explain any materially changed interpretation;
5. develop alternatives and recommend one when a decision is emerging;
6. ask the single highest-leverage question, when an answer is actually needed;
7. continue non-blocking research or decomposition while waiting; and
8. identify whether a bounded execution slice has become ready.

The agent must not turn planning into a form-filling interview. It should infer
safe details from evidence, use recorded defaults for reversible choices, and
focus the conversation on decisions that materially change behavior, cost,
risk, or authority.

### 2.1 Example interaction

```text
User:
  I want RustyKrab to take a long-running software plan and deliver it.

Orchestrator:
  I see two distinct systems: a persistent project planner and a delivery
  controller. The delivery controller can be autonomous, but the planner should
  keep the long-term direction editable. I inspected the existing task queue and
  E2E harness; they are useful foundations, while durable project decisions and
  execution-slice state do not exist yet.

  The next choice that changes the architecture is whether planning belongs to
  one durable project conversation or can be fragmented across task threads. I
  recommend one canonical project conversation with linked specialist runs.

User:
  Yes, I want one agent I keep talking to.

Orchestrator:
  Recorded. I have updated the project model and split the first milestone into
  (1) project memory and decisions, (2) planning conversation behavior, and
  (3) just-in-time execution-slice compilation. The first slice can now be built
  without deciding deployment details.
```

The conversation remains ordinary prose. Structured state appears as concise,
inspectable projections—not as required user input.

## 3. The canonical project model

The canonical plan is a versioned graph of typed claims, not one mutable prose
document and not a single model context window.

Important node types are:

- **intent** — why the project exists and what outcome matters;
- **outcome** — an observable product or operational result;
- **requirement** — behavior that must be true;
- **constraint** — a limit on implementation, policy, compatibility, or scope;
- **non-goal** — an attractive adjacent problem explicitly kept out of scope;
- **decision** — a selected option with rationale and consequences;
- **option** — an alternative still being evaluated or intentionally rejected;
- **assumption** — a provisional belief with impact and validation method;
- **question** — an unresolved issue, its importance, and who may decide it;
- **risk** — a failure mode, likelihood, impact, mitigation, and trigger;
- **repository observation** — a source-backed fact about existing code;
- **research finding** — an externally or experimentally supported fact;
- **workstream** — a coherent area of ongoing work;
- **milestone** — a useful project state with observable exit conditions;
- **acceptance behavior** — a scenario that demonstrates an outcome;
- **dependency** — an ordering or availability relationship; and
- **execution slice** — a bounded, currently actionable part of a milestone.

Edges capture relationships such as:

```text
requirement -> supports -> outcome
decision -> resolves -> question
decision -> supersedes -> decision
observation -> supports/challenges -> assumption
milestone -> advances -> outcome
slice -> realizes -> milestone
acceptance behavior -> verifies -> slice
risk -> threatens -> outcome
```

Every material node records provenance:

- the conversation message, repository evidence, experiment, or research that
  introduced it;
- whether it is user-stated, observed, inferred, or agent-proposed;
- confidence and freshness where relevant;
- the project revision in which it changed; and
- its current status and supersession history.

This prevents a planning summary from silently becoming more authoritative than
the conversation and evidence from which it was derived.

## 4. Plan revisions

Each planning turn may produce a `PlanChangeSet`. A change set is applied
transactionally and creates an immutable project revision.

```text
PlanChangeSet
  - add/update/supersede nodes
  - add/remove edges
  - resolve/reopen questions
  - record or revise decisions
  - update readiness evidence
  - explain material deltas
  - link provenance
```

The orchestration agent may apply low-risk interpretive updates automatically,
such as linking a repository observation to an existing workstream. It must
surface a proposed material revision before treating it as settled when it:

- changes public behavior or success criteria;
- chooses between meaningful product or architecture alternatives;
- adds cost, destructive risk, or an external side effect;
- changes a security or privacy boundary;
- expands repository, merge, deployment, or account authority; or
- invalidates an already authorized execution slice.

The user can respond naturally: “yes,” “not yet,” “choose for me,” “use the
second option,” or a longer correction. The agent translates the answer into a
new revision and shows the resulting material delta.

## 5. Human-readable projections

Users should be able to inspect the project without reading the graph directly.
The system derives several projections from the same canonical model:

- **Project brief:** intent, target users, outcomes, scope, and non-goals.
- **Current understanding:** the orchestration agent's concise working model.
- **Roadmap:** workstreams, milestones, dependencies, and current position.
- **Decision log:** accepted, delegated, provisional, and superseded decisions.
- **Open questions:** ordered by how much they block useful progress.
- **Assumptions and risks:** evidence, confidence, validation, and mitigation.
- **Architecture view:** components, boundaries, important data, and flows.
- **Behavior catalog:** desired user journeys and operational invariants.
- **Repository map:** evidence-backed mapping from planned behavior to code.
- **Next-slice proposal:** the smallest valuable work currently ready to run.

These views are generated, versioned, and traceable. They may also be exported
to Markdown, but exported documents do not become a second source of truth.
Users modify them through conversation or an edit operation that creates a plan
revision.

### 5.1 Architecture evidence and freshness

When a repository provides architecture write-ups, the orchestration agent
loads the system-level documents and the component documents relevant to the
candidate slice before proposing implementation. Each document is recorded as
a repository observation tied to the exact commit from which it was read; its
path and content hash are provenance, and its claims carry an explicit
freshness state.

Architecture documents are not accepted blindly. The agent checks load-bearing
claims against the current crate graph, schema, interfaces, and execution paths.
If code and prose disagree, the code is the current fact, the disagreement is a
planning finding, and correcting the write-up becomes part of the owning
slice. Review opinions inform recommendations and sequencing, but become hard
constraints only when repository policy says so.

The architecture projection therefore shows both the documented design and any
observed divergence, always naming the source repository commit. A later
delivery cannot reuse that observation after its base or affected structure
changes without refreshing it.

## 6. Questions, assumptions, and delegated judgment

Not every unknown should stop progress. Each question is classified by its
effect:

- **blocking now:** different answers materially change the next slice;
- **blocking later:** relevant to a later milestone but not the current slice;
- **researchable:** the agent should inspect code, documentation, or experiments;
- **defaultable:** a reversible choice with a recorded default;
- **delegated:** the user authorized the orchestration agent to decide within a
  stated boundary; or
- **obsolete:** superseded by a project revision or result.

The user can grant standing judgment such as:

```text
Decide implementation details that are internal, reversible, and do not add a
dependency or change a public interface. Bring security, data migration,
deployment, recurring cost, and product-scope decisions back to me.
```

This judgment policy is durable project state. It reduces needless questions
without turning conversational ambiguity into unlimited authority.

When the user delegates a decision, the agent must still record:

- the alternatives it considered;
- the evidence and rationale;
- why the choice falls inside delegated authority; and
- how the decision could be revisited.

## 7. Progressive readiness

A long-term plan is rarely “complete.” Readiness is evaluated for one candidate
execution slice, not for the entire project.

The readiness assessment covers:

| Dimension | Ready when |
|---|---|
| Intent | The slice advances a named outcome. |
| Behavior | Observable acceptance behavior is clear. |
| Context | Relevant current repository behavior has been inspected. |
| Boundaries | Scope and important non-goals are understood. |
| Dependencies | Required predecessors and external inputs are available. |
| Feasibility | A plausible implementation path exists. |
| Verification | The behavior can be independently demonstrated and an applicable repository verification skill or hard gate can produce trustworthy evidence. |
| Risk | Material failure modes have a treatment. |
| Authority | Required local and external actions are pre-authorized. |
| Recovery | Revert, migration, or rollback expectations are defined. |

A dimension may be satisfied by a user decision, repository evidence, a
validated assumption, or a bounded experiment. A numerical score may help sort
work, but hard safety gates cannot be averaged away.

The readiness engine returns:

- evidence supporting each dimension;
- unresolved issues and their impact;
- the smallest additional conversation, research, or experiment needed;
- whether the slice may be proposed, authorized, or executed; and
- which parts of the wider project deliberately remain unresolved.

This creates progressive commitment: the project can move while future
milestones remain exploratory.

## 8. Execution-slice proposal

When a slice is ready, the orchestration agent presents a concise proposal in
ordinary language:

```text
Next slice: Durable project decisions

Outcome
  Planning decisions and open questions survive daemon restarts and context
  compaction.

Included
  Versioned project model, decision log, question lifecycle, provenance, and
  read API.

Not included
  Git worktrees, autonomous coding, GitHub PRs, deployment, or assurance.

Acceptance
  A planning conversation records a decision, restarts, and reconstructs the
  same current understanding and decision history.

Important assumptions
  Existing conversation storage remains the source for message text; project
  state links to it rather than duplicating it.

Authority
  Local repository changes and test execution only.
```

The user may authorize it explicitly with natural language, revise it, defer it,
or establish a policy that lets low-risk ready slices start automatically.

## 9. Internal delivery manifest

Authorization compiles the proposal and its supporting project revision into an
immutable internal delivery manifest. The system may serialize this as JSON or
another implementation format, but users are not expected to write it.

The manifest contains only what execution needs:

- project and plan revision identifiers;
- source repository and pinned base SHA;
- slice objective, non-goals, and acceptance behaviors;
- frozen decisions, assumptions, constraints, and dependencies relevant to the
  slice;
- permitted paths, tools, credentials, network, merge, and deployment authority;
- risk and recovery policy;
- execution and verification budgets; and
- required verification outcomes and repository/setup skill-selection inputs;
- trace links back to the conversation and project graph.

The compiler follows four rules:

1. It can narrow authority but never widen the project's granted authority.
2. It cannot silently resolve an undecided material question.
3. Every acceptance criterion must trace to a project outcome or requirement.
4. Every frozen claim must retain provenance to a project revision.

Once execution begins, the manifest does not mutate. New conversation continues
to update the evolving project plan, not the active delivery.

## 10. Changes during execution

The orchestration agent classifies new planning input while a slice is running:

- **future-facing:** update later milestones without disturbing active work;
- **compatible clarification:** add context without changing the frozen behavior;
- **execution-affecting:** request a controlled stop and propose a replacement
  slice rather than silently changing active acceptance; or
- **urgent safety change:** pause mutation immediately under standing safety
  policy and surface the reason.

The user should always be able to continue planning future work while the
delivery controller executes the current slice.

When a slice completes, its observed result feeds back into planning:

- repository observations are refreshed;
- implemented requirements and milestone progress are recorded;
- assumptions are confirmed or challenged;
- follow-up debt and new risks are added;
- decisions contradicted by evidence are reopened; and
- the next-slice readiness assessment is recomputed.

The delivery report therefore becomes planning evidence, not a terminal blob of
text disconnected from the roadmap.

## 11. Orchestration-agent responsibilities

The orchestration agent owns coherence, not all work. Its responsibilities are:

- maintain the canonical project model and its provenance;
- keep conversation summaries grounded in stored project state;
- decide what to inspect or research next;
- synthesize specialist findings without exposing internal coordination burden;
- distinguish user decisions from its own recommendations and inferences;
- keep long-term intent connected to near-term executable outcomes;
- propose slices at useful boundaries;
- monitor active deliveries and explain material events;
- reconcile implementation and assurance results back into the plan; and
- know when an issue requires the user rather than merely more agent effort.

It does not directly declare code verified, a PR mergeable, a deployment
healthy, or an assurance incident resolved. Those remain deterministic
controller conclusions backed by stored evidence.

## 12. Durable data model

The first implementation needs these durable concepts:

```text
projects
  id, repository_id, title, status, current_revision, judgment_policy,
  created_at, updated_at

project_revisions
  id, project_id, parent_revision, author_kind, conversation_id,
  source_message_id, summary, created_at

plan_nodes
  id, project_id, node_type, title, body, status, confidence,
  introduced_revision, superseded_revision, provenance

plan_edges
  id, project_id, from_node, relation, to_node,
  introduced_revision, superseded_revision

planning_questions
  node_id, impact, decision_owner, blocking_scope, default_action,
  due_milestone

decision_records
  node_id, selected_option, rationale, authority_basis,
  reversible, decided_by

repository_observations
  node_id, repository, revision, paths, evidence_hash, observed_at,
  freshness_policy

readiness_assessments
  id, project_id, project_revision, candidate_slice_id, dimensions,
  blockers, recommendation, created_at

slice_proposals
  id, project_id, project_revision, outcome_node, included_nodes,
  excluded_nodes, status, proposed_at, authorized_at

delivery_manifests
  id, slice_proposal_id, manifest_hash, base_sha, authority_snapshot,
  created_at
```

Message text remains in the existing conversation store. Project records link
to source messages rather than copying an alternate transcript.

## 13. API and event surface

The planning surface should support:

- create or attach a project to a repository;
- continue the canonical project conversation;
- inspect any project revision;
- view projections, provenance, decisions, questions, risks, and readiness;
- compare project revisions;
- accept, reject, revise, or delegate a proposed decision;
- propose, authorize, defer, or supersede an execution slice;
- follow delivery and assurance events within the same project timeline; and
- export a human-readable project snapshot.

Important events include:

```text
project.created
planning.turn_started
planning.research_requested
planning.observation_added
plan.revision_proposed
plan.revision_applied
question.opened
question.resolved
decision.proposed
decision.recorded
readiness.changed
slice.proposed
slice.authorized
slice.frozen
delivery.started
delivery.completed
plan.reconciled
```

## 14. Verification scenarios

The conversational planner is ready when black-box tests prove:

1. A vague user idea becomes an evolving brief without requiring a schema.
2. The agent asks one material question and records the answer as a decision.
3. A daemon restart preserves the project model, open questions, and provenance.
4. Context compaction reconstructs current understanding from project state.
5. A repository discovery contradicts an assumption and visibly revises the plan.
6. A user correction supersedes a decision without erasing history.
7. A deferred future question does not block a ready near-term slice.
8. A delegated reversible decision is made and its authority basis is recorded.
9. A security or destructive-data decision cannot be inferred from silence.
10. Two projections generated from one revision cannot disagree about scope.
11. A proposed slice traces every acceptance behavior to the project model.
12. Authorization freezes the exact project revision and authority snapshot.
13. Later conversation changes future work but cannot mutate an active manifest.
14. An execution-affecting correction pauses or supersedes rather than drifting.
15. Delivery results update milestone state and the next readiness assessment.
16. The user can plan the next slice while the current slice executes.

## 15. Initial construction order

The planning infrastructure should be constructed before autonomous coding:

1. Add project, revision, node, edge, decision, and question persistence.
2. Add deterministic projections and revision comparison.
3. Connect one canonical planning conversation to the project model.
4. Add repository observation and provenance capture.
5. Add decision ownership and delegated-judgment policy.
6. Add per-slice readiness assessment.
7. Add natural-language slice proposal and authorization.
8. Compile an authorized slice to an immutable internal manifest.
9. Hand that manifest to the delivery controller.
10. Reconcile delivery and assurance evidence back into the project model.

The first end-to-end milestone is not “parse a YAML spec.” It is:

> Start with a vague project idea, hold a useful planning conversation, inspect
> the repository, record a consequential decision, survive a restart, and
> propose one traceable execution slice that the user can authorize in ordinary
> language.
