## Responsibility

Read the environment, construct every object in the system, wire them together,
spawn the background tasks, run the channel loops, and shut down gracefully.
Also: subcommands (`skill`, `pair`, `keychain`, `dream`, `work`, `workers`,
`worker`, `update`) and the interactive chat REPL. The REPL, `work` and
`worker` authenticate with the daemon's
bearer token and supply the configured gateway's own HTTP origin on every
request, matching the gateway's mandatory Origin/CSRF boundary for sensitive
`/api` routes. `update check` and `update stage` never talk to the
daemon; `update apply` reads only `GET /api/version`, the same way.

## Agent definitions

Agent definitions are files (control-layer plan, section 12): `agent_defs`
loads the built-ins and `<data dir>/agents/<name>.md` once, through
`rustykrab_skills::agent_registry`, and hands the one registry to both
consumers. The `subagents` tool offers every definition but `worker`; the
local worker (named from the registry's pool, `snapper` on a fresh daemon) runs the `worker` definition under its own name, so an
operator's `agents/worker.md` changes the controller's worker without a
rebuild. With `RUSTYKRAB_TOOL_STUBS`, a stub marked `"visible": false` stays
out of the turn-0 seed, so it is found in the catalog rather than declared.

## `rustykrab work`

The control layer's terminal surface (plan section 14.2 of
`docs/plans/control-layer-and-worker-fleet.md`): `ready`, `list [--status
--kind --parent --all]`, `show <id> [--graph]`, `plan <id>`, `approve <id>`,
`reject <id> [reason]`, `cancel <id> [reason]`, `archive [list | show <id> |
search <text>]` and `tick`. Each is one or two calls to the daemon's
`/api/work` routes; nothing here opens the store or builds a controller, so
a command enters as a typed request the controller applies. It decodes the
gateway's public reply types (`rustykrab_gateway::work_routes`) and the
controller's `GraphView` and `TickReport`, which is why the crate depends on
`rustykrab-control`.

Rendering is a set of pure functions over those replies, tested on
fixtures, including section 14.2's tree verbatim: one line per item, kind,
status with `<- #origin` for a cascade, `done/total done` for a parent,
edges in words on a continuation line, archived items as their summary.
`list` folds an item into its listed parent's roll-up line, and `show` of
an archived id prints what compaction kept. Ids print as `#` and eight
characters, and any unambiguous prefix is accepted back.

It reaches the daemon through `daemon_client.rs`, the one `pub(crate)`
client `chat.rs` uses too: the gateway URL, the token chain (env, keychain,
store) and the gateway's own origin on every request. `worker_cmd.rs`
reuses `work_cmd`'s `Daemon` over it.

## `rustykrab update`

Slices 5 and 6 of `docs/plans/update-flow.md`: where a new version comes
from and how it is checked (`update_cmd.rs`), and the supervisor that swaps
it in (`update_cmd/apply.rs`). Neither opens the store.

- `check` reads the latest release of `RUSTYKRAB_UPDATE_REPO` (default
  `gcbh/rustykrab`) from `RUSTYKRAB_UPDATE_API_BASE` (default
  `https://api.github.com`) and says whether its `vX.Y.Z` tag is above the
  running `VERSION`, compared as numbers. A tag that is not a plain
  `vX.Y.Z` (a pre-release such as `v5.4.0-rc.1`) is never newer, and
  `check` says so (`Latest::plain`, `Latest::describe`).
  `RUSTYKRAB_GITHUB_TOKEN` is sent when set, for rate limits only, and only
  to the host and port of the API base (`asset_request_sends_token`);
  `Config`'s `Debug` prints it as `<redacted>`.
- `stage` does the same, and when the release is newer and not listed in
  `<data>/updates/bad.json` (a JSON array of `{"version": ..., "commit":
  ...}`, written by `apply`'s rollback; `--force` overrides it) downloads the asset
  `rustykrab-<target>.tar.gz`. The target triple is stamped by `build.rs`
  as `RUSTYKRAB_TARGET`. The asset's declared `size` must be present and
  at most `MAX_ASSET_BYTES` (256 MiB) before the download starts; its URL
  must be `https` unless the API base is itself `http` (the tests' local
  stand-in). The body is read in chunks and refused as soon as it passes
  the declared size or the cap, or if it ends short of the declared size.
  The asset's `digest` from the release API must be
  `sha256:<hex>` and equal the SHA-256 of the downloaded bytes; a missing
  or different digest refuses the release before anything is written. The
  hash is rustls's ring provider, already linked for TLS, so no hashing
  crate is added.
- Only then is the archive written and extracted with the system `tar`,
  into a `.staging-<uuid>` scratch directory under `<data>/updates/` that
  is removed on any refusal; one a killed stage left behind is removed by
  the next. Nothing at the top of the payload may be a symbolic link. On
  macOS the archive must hold a `RustyKrab.app` that satisfies
  `designated_requirement` under `codesign --verify --deep --strict -R`:
  anchored at Apple, Developer ID on the intermediate and the leaf, leaf
  team `3RRX845C4X` (`RUSTYKRAB_UPDATE_TEAM_ID` overrides the pin),
  identifier `com.gcbh.rustykrab`. The `codesign -dv` fields are read only
  to explain a refusal, since an ad-hoc signature can print any team.
  Only after that does the staged binary run, once, with `--version`,
  killed after 10 s (`output_within`); it must print the release's
  version, and its commit is recorded. A version names a directory only
  when it is exactly `X.Y.Z` in digits (`is_plain_version`). `staged.json`
  (version, tag, commit, source, digest, path, staged_at, `kind` `app` or
  `binary`, `signature_verified`) is written into the checked tree, which
  is then renamed to `<data>/updates/<version>/`.
- `stage --from <path>` copies a local `RustyKrab.app` or bare binary
  (`cp -Rp`) instead. It has no digest or tag; a bundle still goes through
  the signature check, and the version is whatever the staged copy's
  `--version` prints.

The signature check and the `--version` run sit behind the `Verifier`
trait. `SystemVerifier` runs `codesign` (a no-op off macOS, where the
digest is the check) and the binary; the tests script it, serve a release
and an archive built in the test from a local axum router, and on macOS run
the real `codesign` against an unsigned bundle and against an ad-hoc
signature that claims the pinned team, and refuse both.

`bad.json` entries match in two ways (`BadVersion::matches`). An entry
with a `commit` matches only that commit: a local build has no tag and
every local build reports the package version, so one bad local build must
not block every later one. An entry without one matches its version, which
is how a release is recorded. `stage` of a release checks by version
(its commit is unknown before the download); `stage --from` checks by
version and commit.

`apply [--yes] [--service launchd|script:<start-command>] [--url URL]
[--installed PATH]` swaps the newest `staged.json` (latest `staged_at`)
in. `staged.json` is in the data dir, which a worker can write, so it
re-derives everything it relies on:

1. `newest_staged` skips a record that does not parse and refuses the
   newest unless it is canonical (`check_canonical`): its directory is its
   plain `X.Y.Z` version, its path is `updates/<version>/RustyKrab.app`
   (kind `app`) or `updates/<version>/rustykrab-cli` (kind `binary`), and
   no symlink is on the way. It refuses a stage with no commit, one
   recorded as bad, and, with the launchd service, one whose `kind` is not
   `app` or whose `signature_verified` is false. It reads the running
   version from `GET /api/version` at `--url` (default
   `RUSTYKRAB_GATEWAY_URL`; `--url` must be https or http to `127.0.0.1`,
   `::1` or `localhost`, `check_url`) with the bearer token
   (`RUSTYKRAB_AUTH_TOKEN` first, as `daemon_client` resolves it) and the
   daemon's own `Origin`. If the staged commit is the running one there is
   nothing to do. Every stage must be at least the running version (the
   tag is a field a worker writes), a release (a stage with a tag) must be
   newer than the
   running version, and the running daemon must report `controller.lock`
   `held` and `consecutive_failed_ticks` 0, or nothing changes.
2. Without `--yes` or `RUSTYKRAB_UPDATE_AUTO=1` it prints the plan and
   changes nothing.
3. `DirSwap::prepare` copies the stage (`cp -Rp --`) beside the installed
   bundle or binary (`.<name>.next`) and passes the copy through
   `NextCheck`: a real directory (app) or regular file (binary), not a
   symlink; under launchd the Developer ID signature of the configured
   team; its binary's `--version` reporting the staged version and commit.
   The `Verifier` comes in through `Host`. This runs while the daemon is
   still up, so a stage that fails its checks never stops it.
4. It writes the journal at `stopping`, then stops the daemon through the
   `ServiceManager` and waits for it to
   exit. `Launchd`: `launchctl bootout gui/<uid>/com.gcbh.rustykrab`, then
   polls `launchctl print` until the job is gone. `Script`: SIGTERM to the
   one process `lsof` finds listening on the URL's port, only when it
   listens on loopback alone and runs the installed executable (`ps -o
   comm=`, or `/proc/<pid>/exe` on Linux; `the_daemon`), then waits for
   it. No listener, several, or any other process is refused. The
   process table is the `Processes` seam (`SystemProcesses`). If the stop
   fails, it drops the copy and starts the service again unless it is
   still running.
5. `DirSwap::commit` renames the installed one to `<name>.prev` (removing
   an older one) and the copy into place: both renames are in one
   directory. The journal moves to `swapped`. The default installed path
   under launchd is `~/Applications/RustyKrab.app`; `script:` needs
   `--installed`.
6. It starts the service (`launchctl bootstrap gui/<uid>
   ~/Library/LaunchAgents/com.gcbh.rustykrab.plist`, or the start command
   run detached in its own process group), moves the journal to `started`
   and verifies within 90 s that `/api/version` reports the staged commit,
   `controller.lock` `held`, a `last_tick` that advances twice while no
   ticks are failing, and `consecutive_failed_ticks` 0. On success the
   journal is removed.
7. On any failure it rolls back (`roll_back`): it records the stage in
   `bad.json` first (a release by version, a local build by commit,
   `bad_entry`); a failure to write that is logged, carried on past and
   reported with the outcome. It stops the new version if it is running
   (a failed stop is retried once; a second failure restores nothing
   under a running daemon), restores `.prev`, starts it and verifies it
   the same way against the commit it read in step 1. A rollback exits
   non-zero.

The journal, `<data>/updates/apply-state.json` (`Journal`: the `Phase`
`stopping`, `swapped` or `started`, both commits, the `bad.json` entry
and the time), is written as a temp file then renamed. Every run first
calls `recover`, even without `--yes`, since it only finishes what a
`--yes` run started: an install path that is missing with `.prev` beside
it gets `.prev` back; a journal at `swapped` or `started` is rolled back in
full and the new version recorded bad; a journal at `stopping` drops the
copy; then the service is started if it is not running and the journal
removed. A run that recovers applies nothing new (`Outcome::Recovered`).

Any rollback or recovery error goes through `fail_loudly`: it writes
`<data>/updates/apply-failed.json` (`ApplyFailed`: what failed, both
commits, the time), removes the journal, since a person takes over, and
last starts the service unless it is running. While that file exists
every `apply` puts its text in the error (so on stderr), exits non-zero
and changes nothing, until a person deletes it.

The seams are traits so the tests script the service manager, the
verifier and the process table, and serve `/api/version` from a local
axum router whose answers follow the installed file; no test runs
`launchctl` or signals a process.

## The worker fleet

`fleet.rs` is where plan section 5's registry meets the daemon. `main`
opens a `Fleet` after the tool stubs are applied and the tool list exists:
`WorkerRegistry` over the store's `workers` table with `AgentFactory` as
its factory, `RecordRouting` with its class default tiers seeded into
`routing_defaults`, and the local worker's name from the registry
(`snapper` on a fresh daemon, the row's name after). The local worker is
built under that name, from the `worker` agent definition, with
`RuntimeSkills` as its late tools; the controller is built with the
registry (`with_registry`), `RecordRouting`, a catalog that also knows the
skills written at run time, the interactive-turn busy signal, and a
`worktree_root` of `<data dir>/worktrees`; `Fleet::start` registers the
local worker and rebuilds every stored external worker and peer. The gateway
gets the same registry for `/api/workers`, and `evaluation.rs` reads it for
dreaming's routing criterion (`StoreRouting`).

`RUSTYKRAB_LOCAL_WORKER` (default on; `off`, `false`, `0` or `no` turn it
off) is for a daemon with no local model. The local worker sits on the
cheapest tier, so routing would lease any unconstrained item to it and every
such run would fail. With it off, `main` builds no `LocalWorker` and
`Fleet::start` registers none: the registry has no live local worker, so
nothing is leased to one, and a row a previous run stored for it is marked
`off: RUSTYKRAB_LOCAL_WORKER=off`. The name is still read from the registry,
since `DelegatedRuns` runs a peer's briefs under it. The controller,
external workers and peers run as before, and startup logs that the local
worker is off.

`RUSTYKRAB_HOLD_DISCOVERED` (`1`, `true`, `on` or `yes`; default off) sets
the controller's approval policy to hold every graph of a worker's
`discovered` drafts for a person (`ApprovalPolicy::hold_discovered`), and
the `internal` items the ladder files for a failure with them: the
follow-ups are filed, held as `blocked(needs_consent)` and released through
`POST /api/work/{id}/approve`. The ladder's own filings, `internal` items and `capability` builds alike, are held the same way. It is for a daemon that builds its own
repository, whose follow-ups would otherwise run at once on a base that
lacks their siblings' unmerged branches.

Peers (`peers.rs`, Phase 5) are workers of the same registry: `rustykrab
worker add peer --url <node> --pairing-code <code>` (or `--token`) posts a
peer spec, the factory redeems the code at the node for a device token named
after this machine, and the registry keeps the token in the secret store.
`spawn_refresh` asks every worker where it stands every two seconds, which
is how a peer's node advertisement (models, tools, MCP servers, machine) and
health reach its row and the controller's match step. The local worker
answers the same timer, at most every 30 seconds, by asking its provider
whether its model exists (`ModelProvider::check_model`), so with
`OLLAMA_MODEL` naming a model the server does not have it is listed
unhealthy and leased nothing. The same daemon is
also a node: `main` wires `DelegatedRuns` into the gateway
(`with_delegation`), built from the `worker` definition under the local
worker's name, over the same tools, sharing one model slot with the local
worker (plan 12.1), with `RUSTYKRAB_MACHINE_NAME` (else the host name) and
`RUSTYKRAB_DELEGATION_RESOURCES` as what it advertises.

`RuntimeSkills` is how "the daemon loads skills written at run time" (plan
section 8, rung 2b; scenario 13): on each refresh it loads the skill
directories not seen before, registers them with the skill registry, and
exposes each as a `SkillTool` unless its name is a boot tool's. The
controller refreshes it through the catalog before it decides a tool is
missing and before it verifies a build; the local worker reads it at the
start of every run.

`rustykrab worker add claude_code --name pinch --repos <paths>` posts a
`WorkerSpec` (repository and command paths made absolute first) to the
running daemon, so the worker is leasable at once; `rustykrab workers`
lists every worker with its health, cost tier, repositories and routing
record. A spec never serialises its token or pairing code, so `worker add
peer` puts them in the request body by hand, once.

## `main()` is ~1,240 lines

Lines 332–1571. In order it: parses subcommands, sets up tracing, resolves the
data dir, opens the keychain and store, resolves the master key and auth token,
starts the MCP connector task, builds the model provider, opens the memory
database, loads or mints the persistent `agent_id`, spawns the FTS index
rebuild, constructs the memory backend, spawns the idle lifecycle sweep, builds
the video channel, loads and audits the skill registry, assembles ~65 tools
across nine factory calls, loads the orchestration config, snapshots tools for
sub-agents, applies tool stubs (before the local worker takes its list),
builds `AppState` through ~15 builder calls (one, `with_build_info`, hands
the gateway the version, commit and build date `--version` prints, for
`GET /api/version`),
constructs the task queue, spawns the job executor, the delegated-task worker,
the worker registry's refresh timer and the dream worker, binds the HTTP server, starts the Telegram/Slack/Signal
loops, and waits on the shutdown signal. `shutdown_signal` resolves on
Ctrl-C or, on unix, SIGTERM (what `launchctl stop` and `kill` send), so both
run the same graceful shutdown. That shutdown drains first: on the signal
the controller is set draining (`ControlHandle::set_draining`), so its
ticks lease nothing new and still reconcile, and `drain` waits up to
`RUSTYKRAB_DRAIN_SECS` (20 by default) for `LoopStatus::runs_in_flight` to
reach zero while the server still answers `GET /api/version` with
`draining: true`. Then the server stops and every live external worker run
is ended through `rustykrab_agent::RunGroups::global().terminate_all`
(SIGTERM to each run's process group, SIGKILL after a five-second grace),
and every in-process local run through
`rustykrab_agent::LocalRuns::global().interrupt_all`; those runs report
`RunFailure::Interrupted`, and one more tick returns their items to `ready`
with no rung climbed, before the process exits rather than through the next
daemon's orphan sweep. Last, the infrastructure tasks are aborted, so no
`claude -p` or `codex exec` outlives the daemon.

Every one of those steps is individually reasonable, and the ordering
constraints between them are real and mostly commented (why the sub-agent tool
snapshot happens before skill-tools; why stubs are applied after every real
tool but before the local worker and the work tools; why the MCP
task starts before provider setup). But a 1,240-line function with that many
ordering constraints is held together by comments rather than by types, and it
is the least testable code in the workspace — 37 tests cover 5,300 lines.

The decomposition is obvious from the comment headers already in the file:
`build_storage`, `build_memory`, `build_tools`, `build_state`,
`spawn_infrastructure`, `run_channels`. Each returns a struct; ordering
constraints become argument dependencies the compiler checks.

## The adapters

`CronAdapter`, `MessageAdapter` and `ChannelHub` bridge concrete
implementations to the tool-layer backend traits. `MemoryAdapter` is gone —
`MemoryBackend` moved to `rustykrab-core`, so `rustykrab-memory` implements
it directly.

`CronAdapter` earns its place: `inherit_channel_for_create` merges the cron
tool's explicit arguments with the calling conversation's channel context,
because the model routinely omits `channel`/`chat_id` when scheduling from
inside a chat and the job then has no delivery target. That is real behaviour,
correctly located in the adapter layer.

`ChannelHub` is where the missing `Channel` abstraction bites: it dispatches by
matching on a channel-name string against a set of `Option<Arc<Concrete>>`
handles.

`DeferredWorkBackend` is the control layer's adapter. The local worker
(`rustykrab_agent::LocalWorker`, registered under the fleet's local name
unless `RUSTYKRAB_LOCAL_WORKER=off`) is built before the
controller, because `Controller::new` takes its worker list, and the work
tools that worker runs need the controller as their `WorkBackend`; the
deferred backend breaks the cycle and is bound the moment the controller
exists, failing closed until then. The tool-stub switch
(`RUSTYKRAB_TOOL_STUBS`) is applied just before the worker is built, so the
worker runs the same stub instances the daemon does, and the work tools are
registered after it (`work_host::add_work_tools`), so `replace` mode keeps
them. The worker keeps its runs as conversations through
`scheduled_work::JobTranscripts`, the `RunTranscripts` adapter over the
conversation store, which also resumes a firing's job conversation. The
controller's `ToolCatalog` is `RegistryCatalog`, filled once the registry is
final: a tool in the active-tools seed is `Loaded`, any other registered
tool `RegisteredUnloaded` (so `work_file` outside a session answers "load
it"), and an MCP server counts as configured when `RUSTYKRAB_MCP_SERVERS`
names it (connected or not) or its `mcp__<server>__*` tools are registered.
Its `ModelActivity` is `work_host::TurnActivity`: while the activity
tracker counts a turn in flight (every runtime turn holds a run guard; the
local worker's runs do not), no local lease is taken on the daemon's model
(plan 12.1). `main()` then hands the controller to the gateway as its
`ControlHandle` and spawns two infra tasks: the tick loop
(`RUSTYKRAB_CONTROL_TICK_SECS`, default 5), which before its first tick
takes the exclusive `$RUSTYKRAB_DATA_DIR/controller.lock`
(`rustykrab_control::lock::LoopLock`) and holds it for the life of the
task, so an old and a new daemon overlapping during a cutover never both
run the loop; while another process holds it the loop runs no tick, logs
once, and tries again each interval. Each pass is `run_control_tick`,
which logs a failed tick with the `class` and `consecutive` count read
back from `loop_status`, the same `last_failure_class` and
`consecutive_failed_ticks` that `GET /api/version` reports. A tick the
controller refuses with `Error::LockWaiting` is logged at info as skipped
because another process holds `controller.lock`, never as a failure, since
it records no failure class to read back. The shutdown reconcile tick,
`run_final_control_tick`, reads the loop's last `LockState` from
`loop_status` first and, when it is `Waiting`, logs the same skip without
calling `ControlHandle::tick` at all; the refusal branch stays for a loop
that has not yet tried the lock. `rustykrab
work tick` shows the daemon's 409 `controller_lock_waiting` message as its
error. The other infra task is
`work_host::deliver_work_notices`, which drains the work outbox through
`MessageAdapter` and marks a row delivered only when the send succeeds.
Each notice goes where its item came from, resolved at delivery time: a
scheduled firing's to its job's delivery target (a `done` firing's notice
is consumed, since the job's own message carries the result); otherwise the
thread `channel_bindings` binds the parent item's `origin_conversation_id`
to; and only with no binding does a Telegram notice fall back to the first
allowed chat. Where a notice goes is decided here; what it says is the
controller's.

`evaluation.rs` wires Phase 6 (plan sections 1.1, 10 and 11). `Evaluator`
runs one pass at a time: the review surface's decisions are read back and
applied through the controller, dreaming's `Evaluation` computes the
metrics, runs probation and files proposals through `ControlFiler` (the
controller's validator, as `dreaming`), and every engineering item is then
projected out. The gateway calls it for `POST /api/work/evaluate`, and
`spawn_nightly` runs it every `RUSTYKRAB_EVALUATION_INTERVAL_SECS` (a day by
default, the first pass one interval after start). It is not idle-gated like
the analysis worker: the pass reads the store and files a handful of items,
and holds the controller's loop lock only for each filing or decision.
`GithubIssues` is the review surface when `RUSTYKRAB_GITHUB_REPO` names a
repository and a token resolves through the credential registry
(`github_token`, overridable by `RUSTYKRAB_GITHUB_TOKEN`); it lists issues
under the `rustykrab` label, rewrites title, body and state, adds labels
without removing any, and reads comments with their author association.
The questions and routing readers are empty (`StaticQuestions`,
`StaticRouting`) until Phases 4 and 3 wire their tables.

Scheduled jobs fire through `job_executor_loop` and the task queue as
conversations of their own by default. With `RUSTYKRAB_CRON_WORK_ITEMS=1`
(set in the e2e daemon) `scheduled_work::start` replaces that loop: every
control tick it files each job due within a tick as a `personal` work item
with `trigger: at(time)` and the job in its refs, links it from
`scheduled_jobs.work_item_id`, and once the item is over (closed, or parked
on the user) records the job's run, advances the job and delivers a `done`
result to the job's target with any credential link the run minted. The
controller runs the firing in the job's persistent conversation (its run id
is that conversation's), and `JobTranscripts::resume` hands the worker the
conversation with the job's SKILL.md as guidance and the scheduled prompt as
the preface of its brief, so a firing keeps what a job run has always had.
The switch is off by default because the worker path answers through
`result_report`'s summary rather than a final message, which the local model
suites have not measured.

## The channel loops

`telegram_agent_loop` + `process_telegram_message` (≈380 lines) and
`slack_agent_loop` + `process_slack_message` (≈300 lines) implement the same
sequence: resolve conversation (memory map → DB map → create), load, snapshot
persisted message ids, append the user message, run the agent with a heartbeat
monitor, persist with `save_turn`, extract the last assistant text, map every
failure to a user-facing string. Telegram additionally runs a typing task.
Both now use the owned interactive completion, support mid-run injection,
and await cancellation before saving partial history on inactivity.

There are six copies in total once `gateway`'s two handlers and
`task_queue.rs`'s two are counted. One shared
`run_turn(context, conversation, text, hooks)` in `rustykrab-runtime` with
thin per-surface wrappers would collapse them — and would be the natural home
for a fact that is currently implicit: chat surfaces drain
`PendingLinks` while app surfaces must not.

That second one is not hypothetical. The drain existed only in the Telegram
copy, so scheduled jobs minted a credential link and dropped it; the fix added
it to a second copy. A third copy — the gateway — must *not* have it, because
Apollo and WebChat render the form from `GET /api/credential-requests` and a
live capture URL in a persisted transcript is what `pending_links` exists to
prevent.

Payment approvals ride the same drain: `payment_request` queues a `/p/` link,
and `CredentialNotifier::payment_authorized` resumes the conversation as
`TaskSource::PaymentAuthorized` through the credential-wake path, sharing its
per-conversation dedupe key so the two kinds of answer cannot start two runs
over one history. **Gap:** payment requests are not yet listed on any `/api/`
route, so a purchase asked for from WebChat or Apollo has no way to reach the
user; only the chat surfaces that drain links can approve one today.

## Two queues, two durability guarantees

Telegram and Slack commit received inputs to `store.inbound()` before spawning
or injecting, preserving UUIDs through `send_message_record`. Both save the
initial conversation before runner setup and partial completion before returning
an error. Successful final saves checkpoint the journaled IDs actually retained
in that history. Uncheckpointed inputs remain recoverable in the journal; first
use of that address after a restart warns the user and never replays actions.
This is durable admission, not an exactly-once execution queue. There remains a
transport-acknowledgment-to-CLI-receive gap, and duplicate upstream deliveries
given different UUIDs are not deduplicated here.

`ChannelTurnControl` serializes per-address fallback turns through final save.
Reset increments a generation at receive time, cancels only older-generation
handles, waits for the old turn, and unbinds only if still current. A completion
barrier prevents later turns overtaking reset. Obsolete replies/credential-link
sends are suppressed before starting; already-started network sends cannot be
recalled. Consecutive resets cannot cancel or unbind a newer-generation run.
Reset cancellation targets captured input IDs, not later admissions. A single
shared turn transaction and bounded lifecycle-map eviction remain separate work.

- `task_queue.rs` — bounded `mpsc` + semaphore, in memory. Carries cron fires
  and credential-wake resumptions. A restart drops anything queued.
- `gateway/tasks.rs` over `store::tasks`: durable, backed by `delegated_tasks`,
  survives restart (an interrupted task is queued again), supports
  cancellation.

Cron survives the gap because `scheduled_jobs.next_run_at` is only advanced
after execution, so a dropped task is re-picked on the next 30-second tick (and
`dedupe_key` prevents double submission in the meantime). That reasoning is
correct but implicit — it should be a comment on `TaskQueue`, because it is the
only thing making the in-memory queue safe.

Longer term these are one mechanism with a durability flag, not two.
