## Responsibility

Read the environment, construct every object in the system, wire them together,
spawn the background tasks, run the channel loops, and shut down gracefully.
Also: subcommands (`skill`, `pair`, `keychain`, `dream`, `work`) and the
interactive chat REPL. The REPL and `work` authenticate with the daemon's
bearer token and supply the configured gateway's own HTTP origin on every
request, matching the gateway's mandatory Origin/CSRF boundary for sensitive
`/api` routes.

## Agent definitions

Agent definitions are files (control-layer plan, section 12): `agent_defs`
loads the built-ins and `<data dir>/agents/<name>.md` once, through
`rustykrab_skills::agent_registry`, and hands the one registry to both
consumers. The `subagents` tool offers every definition but `worker`; the
local worker "pinch" runs the `worker` definition under its own name, so an
operator's `agents/worker.md` changes the controller's worker without a
rebuild. With `RUSTYKRAB_TOOL_STUBS`, a stub marked `"visible": false` stays
out of the turn-0 seed, so it is found in the catalog rather than declared.

## `rustykrab work`

The control layer's terminal surface (plan section 14.2 of
`docs/plans/control-layer-and-worker-fleet.md`): `ready`, `list [--status
--kind --parent --all]`, `show <id> [--graph]`, `plan <id>`, `approve <id>`,
`reject <id> [reason]`, `cancel <id> [reason]`, `archive [list | show <id> |
search <text>]` and `tick`. Each is one or two calls to the daemon's
`/api/work` routes; nothing here opens the store or builds a controller, so
a command enters as a typed request the controller applies. It decodes the
gateway's public reply types (`rustykrab_gateway::work_routes`) and the
controller's `GraphView` and `TickReport`, which is why the crate depends on
`rustykrab-control`.

Rendering is a set of pure functions over those replies, tested on
fixtures, including section 14.2's tree verbatim: one line per item, kind,
status with `<- #origin` for a cascade, `done/total done` for a parent,
edges in words on a continuation line, archived items as their summary.
`list` folds an item into its listed parent's roll-up line, and `show` of
an archived id prints what compaction kept. Ids print as `#` and eight
characters, and any unambiguous prefix is accepted back.

Its daemon client repeats `chat.rs`'s token chain (env, keychain, store) and
origin header rather than sharing them, because `chat.rs` keeps them
private; one `pub(crate)` client both use is the obvious follow-up.

## `main()` is ~1,240 lines

Lines 332–1571. In order it: parses subcommands, sets up tracing, resolves the
data dir, opens the keychain and store, resolves the master key and auth token,
starts the MCP connector task, builds the model provider, opens the memory
database, loads or mints the persistent `agent_id`, spawns the FTS index
rebuild, constructs the memory backend, spawns the idle lifecycle sweep, builds
the video channel, loads and audits the skill registry, assembles ~65 tools
across nine factory calls, loads the orchestration config, snapshots tools for
sub-agents, applies tool stubs, builds `AppState` through ~15 builder calls,
constructs the task queue, spawns the job executor, the delegated-task worker
and the dream worker, binds the HTTP server, starts the Telegram/Slack/Signal
loops, and waits on the shutdown signal.

Every one of those steps is individually reasonable, and the ordering
constraints between them are real and mostly commented (why the sub-agent tool
snapshot happens before skill-tools; why stubs are applied last; why the MCP
task starts before provider setup). But a 1,240-line function with that many
ordering constraints is held together by comments rather than by types, and it
is the least testable code in the workspace — 37 tests cover 5,300 lines.

The decomposition is obvious from the comment headers already in the file:
`build_storage`, `build_memory`, `build_tools`, `build_state`,
`spawn_infrastructure`, `run_channels`. Each returns a struct; ordering
constraints become argument dependencies the compiler checks.

## The adapters

`CronAdapter`, `MessageAdapter` and `ChannelHub` bridge concrete
implementations to the tool-layer backend traits. `MemoryAdapter` is gone —
`MemoryBackend` moved to `rustykrab-core`, so `rustykrab-memory` implements
it directly.

`CronAdapter` earns its place: `inherit_channel_for_create` merges the cron
tool's explicit arguments with the calling conversation's channel context,
because the model routinely omits `channel`/`chat_id` when scheduling from
inside a chat and the job then has no delivery target. That is real behaviour,
correctly located in the adapter layer.

`ChannelHub` is where the missing `Channel` abstraction bites: it dispatches by
matching on a channel-name string against a set of `Option<Arc<Concrete>>`
handles.

`DeferredWorkBackend` is the control layer's adapter. The local worker
(`rustykrab_agent::LocalWorker`, registered as "pinch") is built before the
controller, because `Controller::new` takes its worker list, and the work
tools that worker runs need the controller as their `WorkBackend`; the
deferred backend breaks the cycle and is bound the moment the controller
exists, failing closed until then. The worker keeps its runs as
conversations through `StoreTranscripts`, the `RunTranscripts` adapter over
the conversation store. The controller's `ToolCatalog` is `RegistryCatalog`,
filled once the registry is final (after the stub switch): a tool in the
active-tools seed is `Loaded`, any other registered tool
`RegisteredUnloaded` (so `work_file` outside a session answers "load it"),
and an MCP server counts as configured when its `mcp__<server>__*` tools are
registered. `main()` then registers the work tools for ordinary chats, hands
the controller to the gateway as its `ControlHandle`, and spawns two infra
tasks: the tick loop (`RUSTYKRAB_CONTROL_TICK_SECS`, default 5) and
`deliver_work_notices`, which drains the work outbox through `MessageAdapter`
and marks a row delivered only when the send succeeds.

Scheduled jobs still fire through `job_executor_loop` and the task queue as
conversations of their own; `scheduled_jobs.work_item_id` is not written yet.
Moving a firing onto a work item (plan section 12.1, scenario 30) needs the
job's persistent conversation, SKILL.md injection and per-job delivery
target carried into the worker run, and a gate that holds local leases
while an interactive turn runs.

## The channel loops

`telegram_agent_loop` + `process_telegram_message` (≈380 lines) and
`slack_agent_loop` + `process_slack_message` (≈300 lines) implement the same
sequence: resolve conversation (memory map → DB map → create), load, snapshot
persisted message ids, append the user message, run the agent with a heartbeat
monitor, persist with `save_turn`, extract the last assistant text, map every
failure to a user-facing string. Telegram additionally runs a typing task.
Both now use the owned interactive completion, support mid-run injection,
and await cancellation before saving partial history on inactivity.

There are six copies in total once `gateway`'s two handlers and
`task_queue.rs`'s two are counted. One shared
`run_turn(context, conversation, text, hooks)` in `rustykrab-runtime` with
thin per-surface wrappers would collapse them — and would be the natural home
for a fact that is currently implicit: chat surfaces drain
`PendingLinks` while app surfaces must not.

That second one is not hypothetical. The drain existed only in the Telegram
copy, so scheduled jobs minted a credential link and dropped it; the fix added
it to a second copy. A third copy — the gateway — must *not* have it, because
Apollo and WebChat render the form from `GET /api/credential-requests` and a
live capture URL in a persisted transcript is what `pending_links` exists to
prevent.

Payment approvals ride the same drain: `payment_request` queues a `/p/` link,
and `CredentialNotifier::payment_authorized` resumes the conversation as
`TaskSource::PaymentAuthorized` through the credential-wake path, sharing its
per-conversation dedupe key so the two kinds of answer cannot start two runs
over one history. **Gap:** payment requests are not yet listed on any `/api/`
route, so a purchase asked for from WebChat or Apollo has no way to reach the
user; only the chat surfaces that drain links can approve one today.

## Two queues, two durability guarantees

Telegram and Slack commit received inputs to `store.inbound()` before spawning
or injecting, preserving UUIDs through `send_message_record`. Both save the
initial conversation before runner setup and partial completion before returning
an error. Successful final saves checkpoint the journaled IDs actually retained
in that history. Uncheckpointed inputs remain recoverable in the journal; first
use of that address after a restart warns the user and never replays actions.
This is durable admission, not an exactly-once execution queue. There remains a
transport-acknowledgment-to-CLI-receive gap, and duplicate upstream deliveries
given different UUIDs are not deduplicated here.

`ChannelTurnControl` serializes per-address fallback turns through final save.
Reset increments a generation at receive time, cancels only older-generation
handles, waits for the old turn, and unbinds only if still current. A completion
barrier prevents later turns overtaking reset. Obsolete replies/credential-link
sends are suppressed before starting; already-started network sends cannot be
recalled. Consecutive resets cannot cancel or unbind a newer-generation run.
Reset cancellation targets captured input IDs, not later admissions. A single
shared turn transaction and bounded lifecycle-map eviction remain separate work.

- `task_queue.rs` — bounded `mpsc` + semaphore, in memory. Carries cron fires
  and credential-wake resumptions. A restart drops anything queued.
- `gateway/tasks.rs` over `store::tasks` — durable, backed by `delegated_tasks`,
  survives restart, supports cancellation.

Cron survives the gap because `scheduled_jobs.next_run_at` is only advanced
after execution, so a dropped task is re-picked on the next 30-second tick (and
`dedupe_key` prevents double submission in the meantime). That reasoning is
correct but implicit — it should be a comment on `TaskQueue`, because it is the
only thing making the in-memory queue safe.

Longer term these are one mechanism with a durability flag, not two.
