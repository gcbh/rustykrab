## Responsibility

Transport, and only transport now. Axum router, bearer auth, origin policy,
rate limiting, security headers, SSE streaming, static WebChat assets,
webhook receivers, APNs push, the credential page, the payment approval page.
The project-planning routes expose deterministic create, inspect, revise,
compare, and projection operations; they do not invoke a model or grant
repository, GitHub, merge, or deployment authority. The work routes
(`/api/work`) are the control layer's user surface: reads from the store's
`work_*` API, commands through the controller's `ControlHandle`; the worker
routes (`/api/workers`) are the worker registry's.

The application service layer it used to contain is `rustykrab-runtime`.
What remains here is `run.rs`: thin wrappers that supply the runtime's
`AgentContext` out of `AppState` and translate `RuntimeError` into a status
code — the one part of that job that genuinely is the web server's.

## `AppState` is no longer a god object

26 fields became 10, with the agent half moved into
`rustykrab_runtime::AgentContext` (18). The split followed a seam that was
already there: `orchestrate` used 16 fields, the handlers used 5, and only 3
overlapped. `AppState` keeps auth, rate limiter, origin policy,
credential-page policy, the task-queue signal, and the four channel handles
the webhook routes deliver to. The control layer added an eleventh,
`control: Option<Arc<dyn ControlHandle>>`, set with `with_control` by the
composition root; the `/api/work` routes read `agent.store` and call it.
Phase 3 added a twelfth, `workers: Option<Arc<WorkerRegistry>>`, set with
`with_workers`, which `/api/workers` reads and grows. Phase 6 added a
thirteenth, `evaluation: Option<Arc<dyn EvaluationHandle>>`
(`with_evaluation`), which `POST /api/work/evaluate` calls. The trait is the
gateway's own (its implementor, the CLI's `Evaluator`, sits above it) and
returns a boxed future rather than using `async-trait`, which the crate
takes only as a test dependency.

Its builder methods survive as one-line delegations to `AgentContext`, so
existing wiring reads unchanged.

The four `Option<Arc<ConcreteChannel>>` fields remain, and are still where
the missing `Channel` abstraction shows up structurally: a fifth channel is a
fifth field, a fifth builder, and a new arm everywhere channels are
dispatched.

## The link pages

`/c/{token}` (credential capture) and `/p/{token}` (payment approval) are
server-rendered HTML outside `/api/`, so a phone browser reaches them without
the bearer token or an `Origin` on the GET. Both are guarded by the same
`PageIdentityPolicy` (tailnet identity from `tailscale serve`) plus a one-time
token whose hash lives on the request row, and both render one refusal for
every failure so they cannot be probed.

The payment page differs where a checkout differs from enrolling a login: its
inputs carry `cc-*` autocomplete tokens so the phone can fill a saved card,
the terms (amount, merchant, exact origin) are the headline and are repeated
on the button, declining is an explicit answer that tells the agent not to
pay, and every response is `Cache-Control: no-store`. Submitting validates the
card (`CardDetails`) and calls `PaymentRequestStore::authorize`, which puts the
card in the in-memory vault and wakes the conversation; a validation failure
re-renders from the request alone, so nothing typed is echoed.

A request the user asked for *after* being told it repeats an earlier payment
(`duplicate_confirmed`) reaches this page looking exactly like a first purchase,
so the page loads the payment named by `duplicate_of` and renders a warning
block above the form: what was already paid, to whom, when, and that approving
here pays it again. A `held` request never reaches the page at all — it is
issued no link, and `find_by_link` only ever returns `pending` rows.

## Handlers

Most handlers are appropriately thin — load, call, map error to status. Two
are not: `send_message` and `send_message_stream`. Both carry the full turn
sequence — load conversation, snapshot persisted ids, run, `save_turn`,
extract reply — which is the same sequence written out in the CLI's two
channel handlers and twice more in `task_queue.rs`. Six copies in total.
That belongs in `rustykrab-runtime`, with these handlers doing SSE framing
only.

`project_routes` is also transport-shaped: it converts JSON requests into
domain commands, maps typed storage failures to HTTP status codes, and adds
conversation-link metadata to responses. Deterministic request-derived IDs
make server-generated project/node IDs stable across retries. Revision writes
accept a transport DTO that has no author, timestamp, or provenance-
classification fields and rejects unknown fields; the service derives user
authorship, request time, and user-stated provenance from the authenticated
request. Exact retries reload the original derived command before the store
performs its byte-for-byte comparison. The store and domain remain
authoritative for idempotency, concurrency, provenance, and graph validity.

`delete_conversation` no longer has to know what a conversation owns —
messages, recall archive and channel bindings all cascade. Its remaining work
is the recall cache and the todo list, which are process state the database
cannot reach. That is genuinely the handler's job.

## The work routes

`work_routes.rs` serves plan section 14 of
`docs/plans/control-layer-and-worker-fleet.md` behind the same auth, origin
and rate-limit middleware as every other `/api` route:

| Route | What it does |
|---|---|
| `GET /api/work` | live items; `status` (`blocked`, `blocked(needs_consent)` or `blocked:needs_consent`), `kind`, `parent`, `include_closed`; each parent with its roll-up and child counts |
| `GET /api/work/ready` | the ready items |
| `POST /api/work` | one `work_file` draft through `ControlHandle::file_draft` (a one-item plan, `FilingSource::WorkFile`); 201 accepted, 422 rejected with every failed check |
| `GET /api/work/events` | the SSE progress stream: every `work_item_events` row written after the stream opened (or after the row id in `Last-Event-ID`), one frame each, `event:` its kind, `id:` its row id, `data:` the `WorkEvent`; the store is polled by row id every 250 ms, so no frame repeats or is skipped |
| `GET /api/work/{id}` | the item, the edges it holds (an archived upstream resolves to its line), its dependents, its roll-up, its live lease (with the fan-in inputs of its brief), every lease it has had (`leases`: worker and time, from its `lease` events, so a closed item names the worker that finished it), its ladder and last error decoded from its `rung` events, its evidence and its events |
| `GET /api/work/{id}/graph` | the controller's `GraphView`, plus the rungs each item climbed (read from its `rung` events) |
| `GET /api/work/{id}/events`, `/evidence` | append-only history, readable after the item is archived |
| `GET /api/work/{id}/plan` | the plan filed under root `{id}`, preferring one whose approval question still holds items; its tree and held ids |
| `POST /api/work/plan` | a `WorkPlan` through `file_plan` as `FilingSource::Planner`; 200 accepted, 422 rejected with every failed check |
| `POST /api/work/import` | the delivery import: a `StackManifest` (`{ "manifest": ... }` or bare) turned into its layered `code` graph by `rustykrab_control::import::plan_of` and filed as `FilingSource::DeliveryImport`, the only path by which a `code` graph enters (a single `code` item may also be filed by `POST /api/work`); 201 accepted, 422 rejected whole (a cyclic manifest with `cycle`) |
| `POST /api/work/{id}/approve`, `/reject`, `/cancel` | the controller's commands; reject and cancel take an optional `{ "reason" }`; each returns the affected ids, and reject and cancel also what in the subtree had already finished |
| `GET /api/work/archive`, `/archive/{id}` | `work_item_archive`: `kind`, `since`, and `q` (or `search`) to search ids, titles and summaries |
| `POST /api/work/tick` | one pass of the loop, returning the `TickReport` |
| `POST /api/work/evaluate` | one evaluation pass now (`evaluate_routes.rs`): the review surface's decisions synced back, the section 1.1 metrics, section 10's criteria and the proposals they file, probation, the projection; answers with the `EvaluationReport`, 503 `evaluation_unavailable` while no handle is wired |
| `GET /api/work/metrics` | the newest pass's expectation metrics, `{ "metrics", "computed_at" }`, from `expectation_metrics`; empty before the first pass |

The crate depends on `rustykrab-control` for the handle, its reply types
and `Provenance`, the filing record `file_plan` takes, which the control
crate re-exports from the work tools' backend. It no longer depends on
`rustykrab-tools` directly (`tools` is still in its tree through `agent`).

No route sets a status. Every command's actor is the authenticated
principal (`user:master`, `user:<device>`), taken from the extension
`auth::require_auth` inserts. A filing body may carry
`origin_conversation_id`, which becomes the filing's provenance, so the
controller reports to that conversation as it does for one that called
`work_file`. Errors use the project routes' shape
(`{ "error", "message" }`): 404 for an unknown id, 410 `archived` for one
that aged out, 409 for a command the item's state refuses (the store's
refusals reach callers as `Error::Internal`), 503 `control_unavailable`
while no controller is wired. Without a controller the read routes still
answer from the store, a parent's roll-up then counting its children and
repeating its own status column.

The progress stream polls the store rather than subscribing to the
controller: the events table is the record every writer (the tick, a
filing, a user command) already appends to in the same transaction as the
change, so a poll by row id sees exactly what was committed, in order, and
needs no broadcast channel threaded through the controller. The `ladder`
and `last_error` of `GET /api/work/{id}` and the graph's rungs are decoded
with `rustykrab_control::ladder::rung_event`, the controller's own codec
for `rung` events.

## The worker routes

`worker_routes.rs` serves the registry of plan section 5:

| Route | What it does |
|---|---|
| `GET /api/workers` | every named worker (`{ "workers": [...] }`): kind, whether it is live here, health (checked on the way), last seen, cost tier, concurrency, capabilities (repositories, writable resources), its routing record keyed by work class, and the spec an external worker was added with |
| `GET /api/workers/{name}` | one of them |
| `POST /api/workers` | `worker add`: a `WorkerSpec` (`kind` `claude_code` or `codex`, `name`, `repos`, `command`, limits); 201 with the worker, 409 when the name is taken, 400 when the spec is refused (a `local` or `peer` kind, a malformed name) |
| `DELETE /api/workers/{name}` | removes an external worker; the local worker registers itself and is refused |

No route writes a routing record: the controller writes it from verified
results, and moving a class's default tier is a proposal (Phase 6). 503
`workers_unavailable` while no registry is wired.

## Security posture

The compatibility `run_agent_interactive` wrapper returns the runtime's
`AgentRunCompletion` handle (history plus execution result), rather than discarding
history in an error-valued join handle. HTTP route schemas are unchanged.
Both message routes persist initial admission before model/profile setup.
Non-streaming HTTP saves partial history before returning a provider failure.
SSE uses owned interactive completion; inactivity cancels and awaits the runner
instead of dropping its future, then saves partial history and unknown tool
outcomes. A failed final save produces an error, not a successful completion.
Concurrent same-conversation HTTP turn serialization is still a separate gap.

Well constructed, and the ordering is deliberate: security headers are the
outermost layer so they cover error responses from auth, origin and rate-limit
middleware. Bearer comparison is constant-time. Rate limiting is per-IP with
lockout, and recently corrected to stop limiting requests that carry a valid
token (`0e0632d`) — the right call, since rate limiting is an anti-brute-force
measure, not a quota. CSP is restrictive apart from `unsafe-inline`, which the
bundled WebChat asset requires.
