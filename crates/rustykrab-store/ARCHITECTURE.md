## Responsibility

Own `store.db`: conversations and messages, secrets and the credential guard,
scheduled jobs and their run history, paired devices, delegated tasks, outcome
records, channel bindings, the recall archive, immutable conversational
project-plan revisions, the control layer's work items (items, typed
edges, events, evidence, leases, plans, the outbox and the archive), its
named workers with their routing records and class default tiers, and its
Phase 6 records (review facets, proposals and the records they cite, the
computed expectation metrics, and which issue each item is projected to). It also persists questions and standing judgment.

## Shape

`Store` is a handle-factory, not a god object. It holds the connection, the
master key (in `Zeroizing`), a credential backend, an optional notifier, the
in-memory link and card holders, the payment cooldown and duplicate window, and
the database path,
and hands out narrow repository types, one per concern:

```rust
store.conversations()      -> ConversationStore
store.secrets()            -> SecretStore
store.guarded_secrets()    -> GuardedSecrets
store.credential_requests()-> CredentialRequestStore
store.payment_requests()   -> PaymentRequestStore   // card half in memory,
                                                    // pay cooldown and
                                                    // duplicate window carried in
store.devices()            -> DeviceStore
store.tasks()              -> TaskStore
store.jobs()               -> JobStore
store.outcomes()           -> OutcomeStore
store.outcomes_reader()    -> Result<OutcomeStore>  // its own read-only connection
store.dream_reports()      -> DreamReportStore
store.channel_bindings()   -> ChannelBindingStore
store.inbound()            -> InboundStore
store.recall_archive()     -> RecallArchiveStore
store.projects()           -> ProjectStore
store.workers()            -> WorkerStore           // the worker registry's rows
store.pending_links()      -> PendingLinks          // in-memory
```

Each is a `Clone` newtype over `Arc<Mutex<Connection>>`. Callers depend on the
one repository they need, not on `Store`. This is the right pattern, and every
concern follows it but one.

**The exception: work items.** `work_items/` adds `impl Store` methods prefixed
`work_` (`work_insert_graph`, `work_transition`, `work_lease_acquire`,
`work_archive_compact`, ...) instead of a `WorkStore` handle, and
`proposals.rs` follows it (`work_facets_*`, `proposal_*`,
`expectation_metrics_*`, `work_projection*`) so the two fold together. That was the
interface `rustykrab-control` was written against while both were built in
parallel, not a design argument: nothing in the methods needs `Store` beyond its
connection, so folding them into a handle is a mechanical follow-up once the
controller settles.

## Concurrency model

Everything funnels through:

```rust
pub(crate) async fn with_conn<T, F>(conn: &Arc<Mutex<Connection>>, f: F) -> Result<T, Error>
```

which does `run_blocking(move || f(&conn.lock().unwrap()))`. One connection, one
mutex, all access serialised, dispatched to the blocking pool. WAL is enabled
but its concurrent-reader benefit is unreachable.

For a single-user daemon that is a reasonable simplification — it should be
stated as one.

One caller escapes it. `outcomes_reader()` opens a second connection
`SQLITE_OPEN_READ_ONLY` and hands back an `OutcomeStore` that refuses `record()`.
This is the one place where the WAL's concurrent-reader benefit is actually
claimed, and it exists because the background analysis pass aggregates the whole
outcome table: on the shared handle it would block live traffic for as long as it
ran. The path is stored on `Store` so the second connection can find the same
file. Any other long read would be entitled to the same treatment; none has
needed it yet.

Poisoning is handled. Every lock on the connection recovers rather than
propagating the panic, which took two passes: `with_conn` first, then the
eight sites that bypass it (`SecretStore` locks directly inside its own
`run_blocking` closures; `RecallArchiveStore` locks directly because
`RecallPersistence` is synchronous). Test fixtures deliberately keep
`.unwrap()`.

## Migrations

`Store::run_migrations` runs one `execute_batch` of `CREATE TABLE IF NOT
EXISTS` + `CREATE INDEX IF NOT EXISTS`, then `questions::migrate` (the control
layer's Phase 4 tables, and `work_outbox.not_before` by the pattern below, in
its own file beside the code that reads them), then seven blocks of the
pattern, one per table that has grown columns:

```rust
let existing = PRAGMA table_info(t);
for (column, ddl) in [...] { if !existing.contains(column) { conn.execute(ddl) } }
```

then `workers::migrate` and `proposals::migrate`, the worker registry's and
the control plan's Phase 6 tables in blocks of their own (new tables only,
so nothing to guard, and kept in their modules so the control layer's
phases do not all edit one statement), `tasks::migrate`, Phase 5's columns
on `delegated_tasks` in the same guarded-ALTER pattern plus the run index,
then
`conversation::migrate_legacy_blobs`, which explodes pre-normalisation
whole-conversation blobs into `conversations` + `messages` rows, in one
transaction, keyed on `updated_at IS NULL` so a completed sweep is a no-op.

**Good:** idempotent, additive, restart-safe, and the comments explain why old
rows are left with NULL rather than back-filled with "now" or with the current
version — back-filling would assert an attribution that was never observed.
That reasoning is applied consistently across four separate columns.

Since the first pass, migrations also **adopt foreign keys** onto existing
tables via the rebuild SQLite requires — create the new shape, copy the rows
that satisfy it, drop, rename, restore indexes — guarded on
`PRAGMA foreign_key_list` so it runs once, with foreign keys off for the
duration and `foreign_key_check` before the commit. And
`migrate_legacy_chat_maps` folds the two per-channel tables into
`channel_bindings` and drops them.

**Weak:** still no schema-version table. Answering "what shape is this
database" requires reading the migration function and mentally replaying every
guard — and that function has grown. Legacy-schema tests now exist for jobs,
conversations, chat maps and the FK adoption, which is most of the surface.

## Notable subsystems

**Credential guard** (`credential_request.rs` 1,338 lines, `guarded.rs`,
`secret.rs`, `secret_versions`, `secret_audit`). The agent cannot silently
overwrite an existing credential — it files a request carrying the target's
version at filing time, and a stale approval is rejected. Superseded values are
retained encrypted so a mistaken delete is recoverable. Every operation appends
to an audit log. One-time fulfil links are stored only as hashes. This is the
most carefully built part of the crate and it shows.

**Payment approvals** (`payment_request.rs`). A purchase the agent wants to
make is filed with its terms — merchant, exact origin, amount in integer minor
units, currency — and approved by the user supplying a card on a one-time link.
The row is the approval; the card goes to `CardVault`, an in-memory map shared
by every `Store` clone, and is erased when the agent claims the press, after
`CARD_TTL`, when a newer request in the same conversation supersedes it, or on
restart. `CardDetails` is `Zeroizing` throughout with a redacting `Debug`, and a
test scans the database and WAL bytes for the number, holder and postcode across
the whole press, not just the approval. The approval and the card source are
separate on purpose, so a saved-card wallet could fill the vault slot later
without changing the record. Approving wakes the filing conversation through
`RequestNotifier::payment_authorized`.

**Pressing pay is a claim, not a read.** An audit found a silent double charge:
tool calls in one model turn run concurrently, `authorized_for` hands back a
*clone* of the card, and the old `mark_used` discarded its rows-affected count,
so two `pay` calls both pressed and nothing recorded the second. `claim_for_pay`
now moves the row `authorized → paying` in one conditional `UPDATE` that must
touch exactly one row, and hands the winner the card *taken* out of the vault.
The same statement enforces a global lock (at most one `paying` row daemon-wide)
and a throttle (nothing claimable while a row was marked `used` inside
`pay_cooldown`, default `DEFAULT_PAY_COOLDOWN` = 30 s, set by
`Store::with_pay_cooldown` from `RUSTYKRAB_PAYMENT_COOLDOWN_SECS`). A claim that
touches no rows is diagnosed on the same connection into a typed `PayRefusal`
whose message tells the model what to do next. `mark_used` requires `paying` and
errors on zero rows; `release_claim` is the only way back to `authorized` and
takes the `ClaimedCard` back with its original vault deadline, so it cannot
extend `CARD_TTL`. A claim older than `STALE_CLAIM_MS` (2 min) is swept to
`used` — never released, since the press may have charged the merchant — with
`used_at` set to the claim time; the sweep runs in `sweep_expired` and at the
head of `claim_for_pay` and `authorized_for`, so a crash mid-press cannot wedge
the lock. The whole guarantee is the rows-affected count of one statement, which
is why the SQL is written out in `docs/architecture/01-data-model.md` rather
than paraphrased.

**Paying twice for the same thing is a separate problem, and `held` is its
answer.** The claim protects one approval from being spent twice; it does
nothing about an agent that has forgotten a purchase and files a second,
perfectly legitimate-looking request for it. `file` therefore looks for an
earlier request matching `(origin, amount_minor, currency)` within
`DEFAULT_DUPLICATE_WINDOW_MS` (24 h, `Store::with_duplicate_window_ms` from
`RUSTYKRAB_PAYMENT_DUPLICATE_WINDOW_HOURS`) whose status is live or spent, and
files the new row `held` with `duplicate_of` instead of `pending` — no approval
link, and nothing superseded, so a hold cannot kill a live approval. `merchant`
and `description` are outside the key on purpose: both are model-authored, and
the origin is the one field the agent cannot restate. Within one conversation a
`pending`/`authorized` prior is the ordinary re-file and is excluded; a
`used`/`paying` one is not. `PaymentTerms::confirm_duplicate` is honoured only
when a `held` row with the same key already exists in that conversation, so the
override is the user's answer to a hold rather than a flag the model can
pre-set. `claim_for_pay` asks again in its `UPDATE`, for a twin paid between
filing and pressing, and refuses with `PayRefusal::Duplicate { earlier }`
(`retry_safe() == false`), diagnosed ahead of the in-flight and cooldown
refusals because those tell the model to wait and retry. `stamp_utc` is shared
so the chat alert, the approval page and the refusal all name the time the same
way.

**Work items** (`work_items/`, control-layer plan section 13). Ten tables:
`work_items`, `work_item_deps`, `work_item_events`, `work_item_evidence`,
`leases`, `work_lease_history`, `work_spend`, `work_plans`, `work_outbox` and
`work_item_archive`, plus a nullable `work_item_id` on `scheduled_jobs`
(written when a job fires as a work item: `JobStore::set_work_item_id`,
`work_item_id` and `job_for_work_item`) and on `delegated_tasks` (written
by a peer worker's structured submission, Phase 5; see below). The row types are `rustykrab_core::work`; the module defines
only what the store alone needs (`WorkFilter`, `TransitionSpec`,
`RepointSpec`, `WorkOp`, `WorkPlanRow`, `OutboxRow`, `ArchivedItem`,
`LeaseRecord`, `RunSpend`, `Spend` and the typed `WorkStoreError`).

Every lease that ends (a transition out of an active status, an explicit
release, compaction) is copied into `work_lease_history` with when it ended,
in the same transaction that drops the live row, so `work_lease_history`
reads what a worker was given (the lease's `inputs`) after the item closes
or is archived. `work_spend` takes one row per worker run (tokens, wall
time, iterations), written by the controller whether or not the item is
still live; `work_spend_totals` is what parents' remaining budgets start
from, and compaction writes the item's total into the archive's `cost`.
`WorkOp::ReleaseHold` (and `work_release_hold`) clears `held_by` when an
approval answers the question holding the item. `WorkOp::AddArtifactRef`
appends one ref to a live item's `artifact_refs` (a no-op when an identical
ref is already there); the controller uses it to add each later failing item
as evidence on a reused internal item. Neither changes status or writes an
event.

The work module has four production files. `mod.rs` is the async API, one
`with_conn` closure per call. `ops.rs` is every read and write as a synchronous
function of one connection, opening no transaction itself, so the API and
`work_apply` can compose several inside one. `rows.rs` holds the column
encodings and the row mappers, and with them the conservative parsing.
`monitor.rs` reads work, leases, evidence, finalized spend, counts and the
latest event cursor in one SQLite transaction. Display limits never change
aggregate counts or assignments. Its oldest pending notice is the due time
(`not_before`, else `created_at`), so an intentional digest delay is not a
delivery failure. Monitoring adds no tables or writes.

Two reads serve readers other than the controller's snapshot.
`work_events_after(cursor, limit)` and `work_events_last_id` page the event
log by its autoincrement row id, the cursor of the gateway's SSE progress
stream: unlike a timestamp, a row id never repeats or skips a row written in
the same instant. `work_evidence_of_kind` reads one evidence kind across every
item, live or archived, which is how the controller reloads the classifier
rules `internal` items landed (`classifier_rule` evidence).

What the store guarantees, whatever the controller asks: closed is final (a
transition out of a closed status, or one with a stale expected status, is
refused with a typed error); every status change writes its event in the same
transaction, and a note event may not carry a status; `work_apply` lands an
ordered batch (a filing, its supersede, a cascade, the outbox notice) whole or
not at all; an item with any column it cannot parse reads as `failed`, and an
unknown edge kind as `blocks`; and a lease exists only while its item is
active, and every one that ends is kept in the history. What it does not
decide: readiness, cascade, roll-up, filing validation and which items age
are `rustykrab-control`'s.

`WorkOp::Facets` writes an item's review facets (`work_item_facets`: a
`capability` item's mode, a `proposal`'s subject and review tier) in the same
`work_apply` as the item's insert, so an item never exists without them and a
failed filing leaves none behind.

**Evaluation and the review surface** (`proposals.rs`, control-layer plan
sections 1.1, 10, 11 and 13). Five tables, all keyed on a work item id (or a
pass id) without a foreign key, so they outlive compaction like the event
log: `work_item_facets`; `proposals` (dreaming's record of a proposal it
filed: the section 10 body as JSON, the review decision, the `code` item an
acceptance filed, and what probation found against the baseline taken at
acceptance) with `proposal_evidence`, the join of section 13 from a proposal
to the `outcome_records`, `dream_reports`, work items and events it cites;
`expectation_metrics`, one row per section 1.1 metric per evaluation pass,
the whole `MetricValue` as JSON beside the scalar columns, read back as the
newest pass (`expectation_metrics_latest`) so a regression is a comparison of
two passes; and `work_projections`, the issue each item is projected to, the
digest of the fields last written and the newest comment already read, so a
pass rewrites only what changed or drifted and applies a comment's decision
once. Unreadable rows are skipped rather than guessed at: a proposal whose
criterion or body does not parse files and executes nothing.

References are enforced only where they are ownership: `work_item_deps.item`
and `leases.item` cascade from `work_items`. `depends_on`, `parent`,
`status_origin`, `plan_id`, `held_by`, and the item ids in events, evidence,
the outbox, plans, the archive, the lease history and spend are deliberately
plain text, because history must outlive the live row it names (section 4.6).
Compaction deletes the item's row and the edges it holds and keeps its
events, evidence, lease history and spend.

**Workers** (`workers.rs`, control-layer plan sections 5, 10 and 13). Two
tables, created by `workers::migrate`: `routing_defaults` (below) and
`workers`, keyed by the registry's name: `kind`, `capabilities` JSON
(what the worker advertises), `config` JSON (the `WorkerSpec` an external
worker was added with, so the registry rebuilds it after a restart; `{}` for
the local worker), `health`, `last_seen`, `cost_tier`, and `routing_record`
JSON. `WorkerStore` upserts a row without touching its record, lists, gets,
removes (history keeps the name: nothing references `workers.name` with a
foreign key) and touches health. `advertise` records what a peer's node said
about itself with the health check that read it: its capabilities are
replaced only when the node answered, so a node that is down keeps its last
advertisement under an `unhealthy` health line. A peer's token is not in
`config`: the registry keeps it in `secrets` (`worker.<name>.token`). The record changes only through
`update_record`, a read-modify-write inside one transaction, so two results
judged at once never lose an update. The rule that changes it (what counts
as verified, when probation ends) is `rustykrab-control`'s
(`routing::apply`); the store only keeps it whole. An unreadable JSON
column reads as empty, so an unreadable record never earns a worker work.

The routing record is the contract dreaming reads (Phase 6), so its shape
is fixed here: an object keyed by work class (`code`, `capability:build`),
each value a `ClassRecord`:

```jsonc
{
  "code": {
    "verified_done": 3,          // results verified from evidence and closed done
    "claimed_not_verified": 1,   // results that claimed done and failed verification
    "failed": 0,                 // runs that ended in an error the worker reported or caused
    "escaped_defects": 0,        // defects found after acceptance; nothing writes it yet
    "repairs": 1,                // repair rungs its verified results took first
    "cost": { "runs": 4, "wall_seconds": 312, "tokens": 48000 },
    "probation": true,           // not yet earned, or its last result failed verification
    "last_verified_at": "2026-09-27T20:14:03.118Z",
    "last_failed_at": "2026-09-27T20:20:41.502Z",
    "recent_items": ["<item id>", "<item id>"]  // the latest 10 judged, oldest first
  }
}
```

Every field but the first two defaults when absent, so a record written by
an older build reads.

Two more facts a reader of the record needs (dreaming's routing criterion,
which asks per worker and class for the worker's cost tier and whether it
holds the class's default), and where they live:

- **A worker's cost tier** is the `workers.cost_tier` column: lower is
  cheaper. The registry writes it when a worker registers, from the spec's
  `cost_tier` or the kind's default (local 0, peer 1, codex 2,
  claude_code 3).
- **A class's default tier** is the `routing_defaults` table (`class` PK,
  `tier`, `set_by`, `reason`, `set_at`): the lowest cost tier that takes
  the class without an earned record. The controller seeds it at start
  with its policy's prior (`code` 0, `capability:build` 2; `set_by =
  'policy'`, and a class already recorded keeps its row) and reads it back;
  it never decides a move. An accepted routing proposal moves one: the
  controller's review decision applies the proposal's `routing_default`
  artifact through `WorkerStore::set_default_tier`, naming the proposal in
  `set_by`, and routing reads the new tier at once. A worker
  holds a class's default when its `cost_tier` is the lowest among live,
  healthy workers at or above that tier (that is who a new item of the
  class goes to first); a worker below the tier takes the class only once
  its record has earned it (three verified results, its last one
  verified).

**Delegated tasks** (`tasks.rs`, and control-layer plan sections 5 and 13
for Phase 5). The durable queue a peer's delegations wait in, drained by one
worker in the gateway. A task is free text (the `nodes` tool's `message`) or
structured (a controller's peer worker): the structured half is
`work_item_id`, `required_tools` (JSON; an unreadable list reads as the one
name `UNREADABLE_TOOLS`, a tool nothing has, so the node refuses the task
rather than run it with nothing activated), `brief` (the typed brief as the
submitter sent it; the store does not read it) and `run_id`, the submitting
controller's run. `submit` is idempotent by `run_id`: a submission naming a
run a task already has returns that task, under the connection mutex, so a
controller that restarted mid-run finds the task it already has instead of
queueing a second. A structured run settles with `finish_report` or
`fail_report`, which write the typed `ResultReport` as `result_json` and
what the run spent as `usage` beside the text columns a free-text reader
uses. `claim_next` counts `attempts`; `requeue_orphaned`, at startup,
returns every task a previous process left `running` to the queue (nothing
is failed by a restart alone) unless it was already claimed `MAX_ATTEMPTS`
(3) times, which fails it with the reason. Terminal rows are swept after 48
hours; queued and running ones never are.

**Questions and standing judgment** (`questions.rs`, control-layer plan
sections 6.6, 7 and 13). Two tables, `questions` and `judgment_policies`,
and `work_outbox.not_before`, created by one call from `run_migrations`
(`questions::migrate`). Like the work-item API it is `impl Store` methods
(`question_get`, `questions_list`, `questions_answered_among`,
`question_write`, `judgment_grant`, `judgment_list`, `judgment_revoke`,
`work_outbox_waiting`, `work_outbox_latest`), and two `WorkOp` variants let a
question and a timed notice land inside a `work_apply` batch:
`WorkOp::Question(QuestionWrite)`, so a question is written with the
transition that parks or resumes its item, and `WorkOp::Notice(NoticeDraft)`,
a notice with a send time that replaces a waiting one for the same parent
while it is still waiting. The pending query skips notices whose time has not
come. `questions` is the record Phase 6 reads for avoidable escalations: one
row per question with the router's `class`, the asker's claimed class, the
`rule` that decided, how it was settled (`answered_by`: a user, `default`,
`policy:<grant>`, `research:<item>`), and the delegated-decision record; rows
are never deleted (the data model has the columns). For the evaluation's
names: a question's **recorded default** is `default_answer` (the default the
asker gave as data, else one its words state and an option matches, "the
recorded default is 9am"; for a question the router defaulted, the default it
used); a **surfaced** question is one with `class = 'blocking_now'` and a
`delivered_via` (the channel it went out on); it was **answered with its
recorded default** when `status = 'answered'` and `answer = default_answer`
(a question the router answered itself has `status = 'defaulted'` and never
reached the user). A settle on a settled question is refused with `AlreadyExists`, so
an answer is given once; unreadable values read conservatively (class
`blocking_now`, status `open`).

The credential registry treats Notion and Obsidian as optional integrations,
so a standalone worker or monitor can start without either account. Missing
credentials remain absent and are resolved or requested when a tool uses them.
The encryption master key and gateway authentication requirements are unchanged.

**`credential_backend.rs`** is a proper inversion: `CredentialBackend` with
keychain / encrypted-file / env implementations, so live credential values never
have to live in the database.

The read path across the two stores has three rules, and all three are
load-bearing. `put_hardware` keeps the value in the backend and writes an
*empty* row to `secrets`, because the column is `NOT NULL`; that row marks
where the credential lives and is never itself a credential. `GuardedSecrets::get`
therefore reads the backend first, falls back to the database, and maps an
empty value to `NotFound`. And a backend that *fails* to answer is an error,
not an absence: `try_get_hardware` propagates it, while the infallible
`get_hardware` is reserved for callers reporting on storage rather than
reading a value to use. Collapsing those two — a locked keychain and an
unset credential — is what made `gmail` read its own placeholder row back as
`""` and tell the user their stored address was not an email address.

**`RequestNotifier`** exists so the store can tell someone a request was filed
without depending on the push/APNs layer. Correct direction.

**Project planning** (`projects.rs`, 911 lines). `ProjectStore` wraps the pure
`rustykrab-projects` domain in SQLite transactions. Creation and revision
application are idempotent by request id; a replay returns the historical
snapshot produced by that request, while reuse with different content fails.
Adapters can reload the original create or revision command so server-derived
timestamps and actor identity remain byte-for-byte stable across retries.
An optimistic current-revision update rejects stale parents, and the immutable
revision JSON is the reconstruction source. `plan_nodes` and `plan_edges` are
materialized indexes written in the same transaction, not competing sources
of truth. Composite foreign keys prevent current revisions, parents, nodes, or
edges from crossing project boundaries, and edge endpoints must exist in the
same revision. Restart, replay, conflict, direct-SQL rejection, conversation
deletion, and atomicity tests exercise the persistence contract against a real
SQLite database. Conversation/message identifiers deliberately remain
unenforced provenance references, and a lifecycle test proves they survive
source-conversation deletion without copying transcript text.

## Observations

Credential capture rejects explicitly named payment-card/PAN/CVV fields both
when filing and when fulfilling older pending forms. This is a conservative
name/label guard, not comprehensive payment-data detection. Cards have their
own path — `payment_requests` plus the in-memory `CardVault` — which holds one
card per approved purchase and retains no card data on disk beyond the last
four digits. There is still no reusable wallet.

`inbound.rs` journals channel input before runner admission. An exact UUID/data/
address replay is idempotent; conflicting reuse fails. Final conversation saves
mark only IDs actually retained. Pending records remain visible after restart,
without automatically replaying potentially applied actions. Bound records
cascade on conversation deletion; unassigned records have no TTL or recovery UI.
Reset cancels explicit admission IDs without deleting their data. This does not
deduplicate upstream deliveries assigned different UUIDs.

- The two per-channel map stores are gone, replaced by `ChannelBindingStore`
  over one table with a cascading foreign key. Signal gains persistence it
  never had. `address_of` answers the reverse question (which thread a
  conversation is bound to, parsed back through `ChannelAddress::parse`),
  which is how the control layer delivers a notice to the thread its work
  came from.
- Deletion is the database's job now: messages, recall archive and channel
  bindings cascade from `conversations`; run history cascades from
  `scheduled_jobs`. Callers no longer maintain a mental list.
- The remaining hand-written DDL in test fixtures is the deliberate kind —
  simulating legacy schemas to exercise the migration path.
- Planning persistence keeps full immutable snapshots and materialized graph
  indexes together in one transaction. The database enforces ownership
  cascades, while the domain crate enforces graph semantics.
- Three direct `env::var` reads (`RUSTYKRAB_MASTER_KEY`,
  `RUSTYKRAB_DISABLE_KEYCHAIN`, `RUSTYKRAB_APNS_ENVIRONMENT`) that would be
  better passed in by the composition root.

## Durable handoff receipts

`work_lease_acquire_recorded` writes the lease, its status/event and supplied
controller evidence in one SQLite transaction. Evidence must name the leased
item; any mismatch rolls back the whole lease. Existing callers use the original
method with no extra evidence. `project_context` receipts use existing evidence
rows, immutable project revisions, questions and archive history; no competing
project-state table is introduced. Monitoring reads the latest controller-owned
context receipt and workspace in the same transaction as the item and counts.
Unreadable JSON makes observation fail rather than showing an empty handoff.

## Project dreaming persistence

`dream_reviews.rs` owns `dream_project_reviews`: one typed JSON receipt per
cycle, indexed by creation time, with one globally nonterminal cycle enforced
by a partial unique index. CAS updates prevent stale drivers from overwriting
progress; the frozen input and creation time cannot change. Work IDs are audit
pointers without foreign keys, so receipts outlive work archival.

## Scheduled resource requirements

`jobs::ScheduledJob.execution` reads the additive nullable
`scheduled_jobs.execution_json` column as `core::work::CronExecution`. Legacy
rows remain NULL. `create_managed_job` validates and writes the requirements in
the same locked insertion that deduplicates the recurring job; a duplicate
request cannot silently replace its resource requirements. Malformed stored
requirements fail the read and due-job query rather than falling back to an
unconstrained runtime. Existing run history and work-item links are retained.
