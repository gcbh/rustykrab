Pure, deterministic domain rules for conversational project planning. This
crate owns the planning vocabulary and invariants; it deliberately owns no
persistence, model calls, network access, process integration, or environment
configuration.

## Responsibility

Turn explicit project commands into immutable, self-contained revision
snapshots. A snapshot contains project metadata plus a graph of typed nodes and
relationships. Each accepted change set creates a new revision; invalid input
rejects the whole change without mutating the prior snapshot.

The crate also derives deterministic projections for the product surfaces:
brief, roadmap, decisions, questions, risks, architecture, behavior catalog,
and current understanding. Callers store or expose these values, but do not
reimplement their ordering or filtering rules.

## Module boundaries

| Module | Owns |
|---|---|
| `model.rs` | Project metadata, typed planning nodes, edges, and lifecycle states |
| `change_set.rs` | Atomic graph and project-metadata edit commands |
| `revision.rs` | Validation, immutable revision application, and content-derived revision identity |
| `projection.rs` | Deterministic read models and revision comparisons |
| `provenance.rs` | Evidence source, classification, confidence, and freshness types |
| `ids.rs` | UUID entity identifiers and SHA-256 revision identifiers |
| `error.rs` | Domain validation failures |

## Revision and provenance invariants

- A change set names its exact parent revision and project. Stale or
  cross-project changes fail.
- Every graph mutation carries non-empty, structurally valid provenance.
  Project metadata changes require their own provenance.
- Nodes and edges are superseded or retired, not deleted from revision
  history. Superseding a node also retires relationships attached to it.
- Typed node state must match the node kind, and references and relationship
  directions are validated against current nodes.
- Revision sequence and timestamps move forward.
- Revision IDs are SHA-256 hashes of canonical JSON containing the project and
  complete revision content. `BTreeMap` storage and recursively sorted JSON
  keys make identical inputs produce identical IDs and serialization.

## Dependency direction

This crate depends only on external data/serialization libraries. At this
stack layer no runtime crate depends on it yet; the next layers add persistence
in `rustykrab-store` and HTTP exposure in `rustykrab-gateway`. Keeping the
domain free of those dependencies lets tests exercise planning rules without a
database, daemon, or model.
