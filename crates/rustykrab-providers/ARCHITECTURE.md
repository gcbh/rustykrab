## Structural pattern

The HTTP providers independently implement these internal functions:
`build_messages`, `build_tools`, `parse_response`, `map_status_error`, and SSE
delta accumulation.

**This duplication is mostly justified.** The wire formats genuinely differ:
Anthropic has content blocks and a separate top-level system prompt; OpenAI has
`tool_calls` with string-encoded arguments accumulated across deltas; Ollama has
its own message shape plus thinking-tag stripping and a pre-dispatch budget guard.
Forcing them through a shared translation layer would produce an abstraction
with more special cases than the three implementations have in common. The parts
that *are* genuinely shared — line buffering, backoff — have already been
factored out, which is the correct line to have drawn.

## Ollama is doing something the others are not

`ollama.rs` is 2.7× the size of the next provider because it manages the
server, not just the request: `detect_context_window` reads `/api/show`,
`check_model` asks `/api/show` whether the configured model exists (404 is
`ModelCheck::Missing`; any other failure is `Unknown`) without loading it,
`detect_model_shape` derives KV geometry, `log_kv_cache_estimate` reports VRAM
implications, `validate_input_budget` refuses oversized requests without deleting
messages, and
`chat_with_ctx` re-sizes the window per call (which is what makes compaction's
"summarise with a much larger window" strategy possible at all).

That is real capability, and it is the reason `ModelProvider::chat_with_ctx` and
`context_limit` exist as trait methods rather than Ollama-specific hacks. Good
trait design driven by a real second implementation.

`context_limit_for_tools` uses the exact serialized schema estimate, the same
clamped output reservation as dispatch, and framing overhead. Zero is reported
honestly rather than replaced by a fictitious positive floor. Estimates count
UTF-8 bytes, not Unicode scalar values; they remain heuristics and do not measure
image-token cost. `validate_tool_history` checks core call/result IDs before
Ollama serialization discards those IDs. Invalid histories fail explicitly;
the adapter never repairs them by deleting evidence. The runner owns compaction,
archive retention, and at most one shrink-and-retry on a typed budget refusal.

## The tool block is logged per request, per conversation

Chat templates render the tools array into the front of the prompt, so a
request whose array differs from its conversation's previous one pays a full
re-prefill (plan section 12). Ollama and the scripted provider fingerprint
the array each request carries (`rustykrab_core::tool_block`, FNV-1a over the
serialized wire types, stable across toolchains), attribute it to the
conversation of the runner the request comes from (the task-local
`SESSION_TOOL_CONTEXT`), and log one `tool block sent` line with the
conversation id, trace id, fingerprint, tool count and whether it changed.
The comparison used to be provider-wide, which could not tell a mid-run load
from runs interleaving on one model (31 of 46 logged changes on the live
daemon were the latter). Ollama still logs its original "tool set changed"
line, message text unchanged, now carrying the conversation id. The e2e
harness reads these lines back to check that a run's block stayed fixed.

Whether a model can call a tool it saw only as text is capability data:
`accepts_undeclared_tool_calls` is `true` for Ollama (its gemma4 and
qwen3.5-family parsers return any name; both default models called such a
tool 12 of 12 times) and the scripted provider, `false` (the trait default)
for Anthropic and OpenAI. The runner turns it into the conversation's late
binding; a harness profile overrides it for a model whose template path
differs, so no provider branches on a model name.

## Observations

- **Eight direct `env::var` reads** — `OLLAMA_NUM_CTX`, `OLLAMA_KEEP_ALIVE`,
  `OLLAMA_TIMEOUT_SECS`, `ANTHROPIC_CONTEXT_LENGTH` and friends — read inside
  the provider rather than passed by the caller. `OllamaProvider` already has a
  full `OllamaConfig` struct and a builder; the env reads bypass both, so a
  caller that constructs a provider explicitly can still be overridden by
  ambient process state. That is the wrong precedence order.
- **`scripted.rs` in the production crate.** Same trade as `tools/stub.rs`:
  necessary for the e2e harness, but it means the release binary can be pointed
  at a fake model with `RUSTYKRAB_PROVIDER=scripted`. A cargo feature would make
  the boundary structural.
- **`OpenAiProvider` does not override `requires_paired_tool_results`.** It
  inherits the `true` default, which is correct for OpenAI, but it is worth an
  explicit override with a comment — the next provider author will not know
  whether `true` was chosen or inherited.
- 105 tests, including wire-format tests that survive chunk splits inside
  multi-byte characters. The right things are being tested.

## Native Claude Max boundary

`ClaudeMaxRuntime` selects an explicit config directory or the CLI default
login, clears inherited API/provider credentials, and verifies `claude auth
status --json` as `claude.ai`, `firstParty`, `max`. Login identity is retained
only as a truncated SHA-256 email fingerprint in observations; OAuth tokens
are neither read nor copied. Checks are cached for 30 seconds for health and
forced before inference. The API/environment/settings fallback is excluded.

`ClaudeCliProvider` serializes the complete ordered conversation and declared
tools to stdin. Native tools, MCP and inherited settings/customizations are disabled with safe mode; CLI
structured output supplies text and declared tool calls, which the Rust
harness executes. Forced choice survives the streaming fallback. Unknown
calls, non-object arguments, absent structured output, image input, and
oversized estimated input fail explicitly. The input estimate is heuristic,
not a measured model context window. CLI schema enforcement handles tool
parameters; the harness validates execution permissions. This bridge emits
text after the CLI result rather than streaming intermediate tokens.

A quota error is a typed `ModelRateLimit`, with a five-minute unavailability
observation that a successful auth check does not erase. It reports neither
remaining subscription capacity nor a predicted reset. State is in memory
and a restart clears observations. `check_model` verifies runtime login
readiness; model alias/inference availability is established only by an
actual turn. There is no HTTP API fallback. `rustykrab-agent` depends on this
crate to reuse the same account isolation/verification for native executors.

## Native Codex subscription boundary

`CodexChatGptRuntime` clears inherited billing/provider/remote overrides and
selects `CODEX_HOME`, or the CLI default login. It starts an owned stdio
app-server, initializes it, reads `account/read` without token refresh, and
accepts only ChatGPT managed auth with an identified plan and email. Only a
SHA-256 email fingerprint survives. No credential file is read or copied.
A second read obtains quota windows through `account/rateLimits/read`;
explicit window fields are retained, excluding account UUIDs, credits and
arbitrary payloads. Checks have a 30-second cache and a bounded subprocess;
quota failure reports unknown capacity while preserving a verified login.

The server's `ordinaryUsageAllowed=false` marks the worker unavailable until
an exhausted Codex window's reset, or a five-minute retry when unknown.
Native JSONL quota errors become `ModelRateLimit` and retain their cooldown
across auth refreshes. A changed account clears the old account's observation.
No reset or credit is consumed. These are observations, not a reservation of
capacity; other clients of the same login share the same subscription limits.
