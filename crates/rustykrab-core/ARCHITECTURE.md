(`Tool`, `ModelProvider`), the error taxonomy, the value types that cross crate
boundaries, and the small pieces of shared in-process state that two unrelated
crates both need to touch.

**Idleness is a fact, not an inference.** `ActivityTracker` carries both a
timestamp per agent and a count of runs in flight, because a timestamp alone
cannot express "busy right now": activity is stamped when a turn *starts*, so a
turn outlasting the idle threshold reads as quiet while the agent is still
working. `begin_run` returns a `RunGuard`; `is_idle` is false while any guard is
alive, and dropping one bumps the generation so an overlapping background pass is
preempted rather than returned. RAII rather than a matching `end()` because the
agent path has many early returns, and one missed call would leave the process
permanently "busy" — silently disabling every background job, with no error.

**A post-condition is not a tool call, and the distinction is load-bearing.**
The cheap version of "did the skill succeed?" — did the run call a tool of that
name, and did the call return `Ok` — is a question about the agent's behaviour
rather than about the world. A run that created the event on the wrong day for
the wrong person satisfies it exactly as well as a correct one.

That would be a minor imprecision if the answer stayed local. It does not: it
becomes `SignalClass::Verifiable`, which is what `is_ground_truth()` admits,
which is what `Readiness::Ready` requires, which is what authorises the outer
loop to mutate memory. A proxy the agent fully controls would end up as the sole
evidence permitting self-modification.

So a probe observes state through a path independent of the run, and is sampled
*either side* of it — because "the calendar contains the event" is a claim about
the calendar, while "the calendar gained it during this turn" is a claim about
the turn. A check naming no registered probe yields no contract at all and the
run falls back to the implicit signal: not satisfied (invention), not unmet
(which is what a typo in a `SKILL.md` would otherwise mean, forever).

Which effects a skill *claims* comes from its `SKILL.md`; which effects a
deployment can *observe* comes from its `ProbeRegistry`. Keeping those separate
is why `probes.rs` is short and honest rather than aspirational.

## Design notes

**`Tool` is well shaped.** Four required methods and three defaulted ones, and
each default is the safe answer:

- `available()` → `true`. Tools depending on absent configuration override it to
  `false` and are then excluded from the schemas sent to the model, so the model
  never calls something guaranteed to fail.
- `sandbox_requirements()` → nothing required. Capability declaration replaces
  the hardcoded tool-name allowlist that this pattern usually degenerates into.
- `blocks_turn()` → `false`. This encodes a genuinely subtle distinction: the
  loop cannot trust a bare `EndTurn` after tool use (providers emit it for any
  text-only reply), so it re-prompts for `task_complete` — but re-prompting a
  model that stopped because it is *waiting on the user* makes it invent
  progress. `blocks_turn()` is how a tool says "stopping is correct here".

**`ModelProvider` defaults degrade safely.** A new provider implements `name`
and `chat`; `chat_stream` falls back to `chat` and emits one text event,
`chat_with_choice` drops the constraint, `chat_with_ctx` ignores the hint,
`context_limit` returns `None` and callers use their own default. Five optional
methods, five sensible degradations.

**`RetrievalLog` is the right kind of small.** Its doc comment states plainly
that it is a lossy in-process hint, not a ledger, and bounds itself
(64 ids/conversation, 512 conversations) with the reasoning for each bound. It
recovers from poisoned mutexes rather than propagating the panic, because an
attribution hint is never worth taking the process down for. That is the
correct instinct, and it is applied inconsistently elsewhere — see
`store::with_conn`.

## Observations

- **Token estimation now lives here**, in `token_estimate`, with the inverse
  (`max_bytes_for_tokens`) tested as a property against the forward function
  so tuning the constant cannot invert the relationship the summary cap
  depends on. Its role has since narrowed: compaction anchors on actual usage
  and applies the heuristic only to the delta, so the constant is no longer
  load-bearing for the threshold. The module doc says so, and says why
  raising it to "be more accurate" on JSON would make it worse on prose.
- **`MemoryBackend` now lives here**, which let `rustykrab-memory` implement
  its own contract and deleted the binary's pass-through adapter. The other
  five `*Backend` traits stay in `rustykrab-tools` on purpose: every one of
  their real implementors already sits at or above that crate, so moving them
  would be churn. A pure pass-through adapter is the tell that a trait is in
  the wrong crate — that was true of exactly one of the six.
