The control layer of `docs/plans/control-layer-and-worker-fleet.md`: a
deterministic controller, in code and never a model, that schedules a graph
of work items, verifies every worker result from evidence, climbs a
resolution ladder on every failure, and surfaces to the user only when the
ladder is spent.

## Responsibility

Own the lifecycle of work. The model proposes (files items, reports typed
results, asks typed questions); this crate transitions. Readiness, cascade,
parent roll-up, leases, the ladder and notification are computed here from
the store's rows, so a restart re-derives the same state and nothing depends
on a model remembering its plan.

The crate does not own persistence (`rustykrab-store`), the shared data
types (`rustykrab_core::work`), the model-facing tools (`rustykrab-tools`)
or any channel. It reads and writes the store and calls workers through
adapters that sit above it.

## Short Git revision ranges in failure identity

The workspace verifier prints its compared revisions as twelve hexadecimal
characters separated by `..`. `errors/fingerprint.rs` recognises that whole
word before normalising its individual runs: numeric-only and letter-only
revisions become `<id>..<id>`, as mixed hexadecimal revisions already did.
Paths, URLs and quoted strings retain their earlier placeholder precedence;
surrounding punctuation, ordinary numbers, standalone identifiers and other
range lengths keep their existing treatment. The fingerprint still hashes
the class, subclass, tool, worker kind and normalised message separately.

Two twelve-digit numbers in the same range shape are indistinguishable from
short revisions and take the identifier placeholders too. The common mixed
revision key is preserved; existing numeric/letter-only history keys are not
migrated or aliased. This correction adds no graph transition, proof producer,
grant or release of an independent hold. Its deterministic regression and
remaining causal limits are recorded in
[`short-git-range-fingerprint-2026-10-16.md`](../../docs/verification/short-git-range-fingerprint-2026-10-16.md).

## Invariants

Failure resolution is prerequisite work. Order 3 reuses executable work by
failure fingerprint and repository, or creates an `internal` item when absent.
Legacy internal titles remain a fallback; proposals still require acceptance.
It validates a `blocks` edge from the
waiting original, and attaches each failure's inspection pointer. The original
returns to `queued` but cannot become ready until its prerequisite is `done`.
Its next brief includes the prerequisite's evidence and prior failure.
A prerequisite is `done` only when it landed something the controller checked:
a commit git verified in its worktree, or a classifier rule that replayed. One
that reports without landing either is not done. Its report is kept as
evidence, it parks `blocked(needs_decision)` with its conclusion as the
question to its owner, and the items waiting on it are released to continue
their own bounded ladders. A later failure of the same fingerprint does not
wait behind a prerequisite that is waiting on its owner. A failure in the
daemon's own code (no repository on the failing item, or the daemon's own
source as its repository) is resolved in a worktree of that source at the
running build's commit, and what it lands stays on its own branch. When the failure
comes back after a prerequisite closed `done`, the next one names it
(`previous_fix`) and is given what it concluded and landed, and each failing
run since with whether that run's code contained the fix; a recurrence on code
or on a daemon build without the fix is recorded as such and is not evidence
that the fix failed. A repair
cannot wait on itself or create a dependency cycle; a rejected filing continues
the bounded ladder. New diagnoses carry `resolution_depth`; the existing graph
depth cap bounds recursive creation, while reuse still passes cycle validation.
Unknown-error work diagnoses classification; it does not
claim to have fixed a cause that is still unknown. Ordinary retries and task
verification establish whether the original failure is resolved.

`graph/priority.rs` derives `SchedulingPriority` from the current snapshot on
every selection pass. Interested open work donates its base urgency transitively
to unmet `blocks`/`waits_for` prerequisites, inherited ancestor gates and children.
Closed, expired, future-triggered and approval-held work does not donate; history
and unreleased alternatives do not donate. Inherited explicit urgency is the
primary rank, followed by distinct waiter count, age and id. Inheritance leaves
the stored priority unchanged, so boosts disappear
when their waiters no longer need the work. Selection still requires readiness,
actual tool/scope coverage, preconditions and resource availability.

- **The model proposes, code transitions.** No path in this crate lets a
  model set a status. Cascade statuses (`blocked(upstream_*)`,
  `cancelled(cascade | superseded)`) are written only by the controller and
  always name their origin item.
- **A filing is atomic.** `work_plan`, `work_file`, the ladder's capability
  items, an accepted proposal and the delivery import all go through the
  same validator and are accepted whole or rejected whole with every failed
  check named. An item's review facets land in the same transaction.
- **The issue is a view.** The review surface never decides readiness and
  nothing flows back from it but the decision vocabulary; a local-only item
  appears on it only as `local:#N`.
- **Closed is final.** A retry is a new item; the failed attempt and its
  ladder stay in the record. The one deliberate exception, the delivery
  plan's rebase cascade, belongs to the delivery controller.
- **Sequential work stays in one worker.** The graph orders work, waits on
  the world and fans out independent branches; validation flags a split made
  only for sequence.
- **Unreadable rows parse to the conservative case** (`failed`, `blocks`),
  as `rustykrab_core::work` defines, so nothing runs early.
- **Every result is a claim.** A `code` result's commit and paths are checked
  against git, a check it names against the commands its adapter saw run,
  a capability for a need with a registered probe against what the worker
  that needs it observed when it performed the operation itself (a build of
  any other tool against the host's catalog, labelled availability only), a
  read-only review's report against what a review may carry, and a fix
  item's claim to have fixed a failure against what it landed. A claim beyond the evidence is
  recorded as `verification_failed` and climbs the ladder; it is never
  `done`, and it counts against the worker's routing record.
- **Repository-scoped work runs in isolated worktrees.** The parent commit is the
  controller's, pinned at lease time; the worker gets a branch and a
  worktree under the daemon's data directory, and the user's checkout never
  moves.
- **A restart fails nothing by itself.** A run that died with the process
  returns its item to `ready`; a run that lives elsewhere (a peer's task) is
  re-checked with its worker and re-attached while the worker holds it.
- **Credentials stay where they are held** (plan section 12.1). A peer
  worker's submission carries the brief's typed fields, never a secret; its
  own token for the node is kept in the encrypted secret store and in no
  spec or view.
- **Routing records are observations.** The controller writes judged results
  and retains historical class defaults, but neither constrains eligibility.
  Dispatch uses tools, permissions, health, free capacity and cost.

- **The router classifies; the model only asks.** Only a blocking-now
  question outside delegated authority reaches the user. Authority comes from
  a grant the user made, compiled to checks a person can read back, never
  from the asker's claim, and every decision taken under it is recorded with
  its alternatives, rationale, authority and how to revisit it.
- **An answer resumes the item, not the conversation.** It reaches the next
  run's brief; nothing is written into the conversation that filed the
  work.
- **No item of a planned graph is ready before its planning item is
  reconciled**: the graph's top waits on it by a `blocks` edge, which a
  restart re-derives like any other.

## Project continuity across native runtimes

`handoff.rs` defines the provider-neutral `ProjectContext` carried by `Brief`.
`controller/project_context.rs` resolves an explicit `project` artifact on work
or its ancestors, or a unique exact repository/canonical-conversation match
created before that work. It loads the current immutable planning snapshot,
work objectives/constraints/decisions, questions/answers and controller-verified
proof. Each lease freezes that revision, run pointer and workspace atomically
through `Store::work_lease_acquire_recorded`; peer reattachment reads the frozen
receipt rather than refreshing it. A new run rehydrates the current revision.

Historical controller receipts establish bindings after work compaction;
archive status and surviving git/check evidence establish completed progress.
Models' artifact pointers cannot establish a historical binding or verified
commit. Repository work starts at a commit containing repository HEAD and all completed
project's verified commits for that repository. Independent verified branches
are merged with `git merge-tree --write-tree`; clean integrations are retained
under `refs/rustykrab/handoffs/<base>/<commit>` without moving HEAD or touching
the checkout. Hooks, configured merge drivers and renormalization are disabled.
Missing commits or actual merge conflicts park work with a typed decision question;
no worker starts on a guessed base. Other projects on the same repository do not
supply code. Repository HEAD is never advanced. Unverified partial work stays
available through old run/workspace evidence and is not promoted to a base.

The 128 KiB bound now applies to the execution view after verified workspace
selection. The complete immutable project snapshot remains in that view, along
with the current item, its ancestors, transitive inputs/ordering predecessors and
the work supplying the pinned base. Other historical tasks are not bulk-inlined.
The full context is still frozen in the controller receipt; all completed verified
commits participate in base selection before any prompt projection. Oversized
current intent still parks visibly rather than dropping constraints. Native
execution remains one item per CLI invocation. Tests use
real git and SQLite to switch a Claude-shaped worker to a Codex-shaped worker,
reopen the database, archive completed work, correct the project revision and
verify both inherited files and immutable old receipts. Workspace tests refuse
missing/conflicting history and preserve every cleanly integrated parent;
store tests prove receipt/lease rollback together.

Every 30 seconds, the sweep revalidates controller-authored `project_context`
decision holds against current project intent, repository state and the execution
view's size. Resolved technical questions become obsolete without a user answer,
and their leaf items return to queued. Separate open user questions, approval
holds, invalid history and oversized current requirements remain held. This
also recovers legacy whole-history size holds after an update; recovery runs
before ordinary readiness and worker selection.

Unfinished attempts carry controller-owned run/workspace/branch pointers and
classified failure records in project context. These let the successor inspect
partial work without accepting it as verified code. Model-written workspace
artifacts cannot supply these pointers or repository scope. The continuation
base still excludes every unfinished or falsely reported result.

## Generic tasks and availability queue (base v6.4.11)

Ordinary work is a task described by objective, completion criteria, required
tools and authorized resources. Historical labels remain readable but impose
no executor, filing, workspace or proof restriction. Backend identities only
select the executable/transport. Internal planning, proposal and capability
operations retain their workflow markers. Repository scope creates a worktree
and requires git proof regardless of the old label; classifier-rule artifacts
require replay proof regardless of it.

Selection filters actual health, outage backoff, tools/MCP, authorized writes,
free concurrency and model availability before applying cost preference. If no
resource fits, the ready queue is unchanged: no lease, failure, rung, question
or timeout. Provider unavailability after dispatch also returns to ready with
a 30-second resource backoff; a zero-token availability rejection is recorded
as a diagnostic run event without charging execution budgets. Actual token
usage remains charged. Existing worker-unavailable leaves are requeued without
waiting for capacity; synthetic surfaced questions become obsolete, and their
old availability rungs no longer count against budgets. Audit events remain.
Explicit expiries, authorization and actual execution failures retain their
existing semantics.

Repository scope permits inspection without edits. When no Git changes are
claimed, a clean worktree at its starting commit records `repository_unchanged`
evidence rather than requiring an invented commit. Unreported edits and false
commit/path claims still fail verification.

prerequisites, a readable wait reason and a content-hash revision. Selection in
`controller/tick.rs` walks this same list and applies its existing eligibility,
scope, readiness and capacity checks; it skips ineligible entries and can fill
multiple independent slots. A blocked entry keeps its position.

Every entry also includes previews of the existing objective (800 Unicode
characters) and completion criteria (400), with `description_truncated` when
either exceeds its bound. Tasks outside bounded telemetry still have a readable
goal and completion criterion. The projection leaves stored descriptions and
worker briefs intact; the detail route supplies the full task. Description
changes participate in the list revision but never change its scheduling rank.

`ControlHandle::priority_list` supplies the monitor and priority read route.
`controller/priority.rs` implements `reorder_priority`: under the controller
loop lock, an authenticated human must submit the current revision and a full
permutation. The command assigns descending base priorities above previous
urgency values and checks that inherited prerequisite urgency still produces
exactly the requested order. Stale, incomplete and orders inconsistent with
inherited urgency are refused before writing. Held and future-triggered work
keeps the existing rule that it donates no urgency. One `work_apply` writes `SetPriority`
operations and decision events attributed to the human. Existing priorities
carry the order across restart; no queue table, authorization or status is added.
Priority changes preserve `updated_at`, which also measures recovery-hold age.
Running jobs are not interrupted.

ControlHandle::queue_priorities derives ranks through the same normalized
controller snapshot as dispatch, including fired triggers and released holds.
The authenticated monitor projects ranks only for displayed items, while each
rank counts distinct interested waiters across the full graph. Those legacy
per-item ranks supply impact labels; consumers use `priority_list` for ordering.

Host-built general resources carry a resource_slot marker in the existing
worker configuration JSON. Registry::local_name excludes these slots when
recovering the default local identity, with legacy slot roles retained for
compatibility. This identifies a registration source; it does not gate work.

## Parallel isolated execution and stopped prerequisites (base 5bc3309)

The default-false `Worker::isolates_worktree` describes an execution guarantee,
not a model role. Dispatch retains the isolated repository resource on the live
run. Two opted-in runs may share their first `repo:` resource only when both
receive controller-owned worktrees; extra repositories, files, mailboxes,
calendars, unknown/orphan runs and non-isolating executors remain exclusive.
Worker capacity, account health, local-model serialization, approvals and actual
ordering edges still apply. Repository concurrency does not move the source
checkout or promote a worker's unverified changes. Existing continuation-base
integration combines verified branches and refuses conflicts.

`FilingContext::isolated_repo_writes` is enabled when the controller has a
worktree root. The validator and discovered-work ordering use the same shared
resource rule: independent first-repository writers need no synthetic sequence;
other shared writes still require ordering. Explicit dependencies stay intact.

The sweep recovers historical controller-created resolution waits when a
fingerprint-matched prerequisite stopped for its owner or exhausted its budget
without verified git/replay proof. A matching controller improve-rung receipt
and no subsequent resume/lease are required before dropping the edge. Ordinary
dependencies, consent holds and the stopped repair remain unchanged; a resume
event and resolution-outcome evidence explain recovery. Later failures also
avoid reusing a budget-exhausted resolution. Existing execution budgets remain
in force.

`WorkerSpec.writable_files` persists exact operator grants in the existing
worker configuration JSON. It adds no table or migration. Coverage remains
exact; adding a file grant does not authorize its parent directory or shell.

A completed capability can wake a parked item only when at least one prerequisite
landed after its latest hold. If execution subsequently reports the same missing
capability, the old completion is not new evidence and cannot restart it forever.
A live audit observed the same planner item repeatedly surfacing a missing
controller-dispatch tool and being awakened by an already completed capability.
The regression checks old, newly landed and subsequently stale completions.

The separate default-empty `readable_files` worker option grants exact read-only
inputs (`worker add --readable-files PATH[,PATH...]`). Reads may use those inputs;
write/edit calls still require a requested exact output grant or the run's own
repository worktree. Input grants do not advertise writable resources and remain
out of native shell arguments. The native host path preserves both grant arrays
from its stored spec.

## Bounded recovery (base 619d476)

On v6.5.6 one item ran at least 491 times and 8.7 hours against a one-hour
budget: every revival briefed it with a fresh budget and nothing noticed it
failing the same way. Two bounds and one release now hold for every leaf.

`controller/spend.rs` makes a leaf's budget cumulative.
`Controller::cumulative_budget` is the item's budget times its allotments,
less what all its runs spent (the durable `work_spend` totals, so a restart or
revival refills nothing), in iterations, tokens and wall time; repairs and
rung budgets stay per item. Allotments are one plus the item's `budget_grant`
evidence rows. `brief.rs`'s `brief_for` takes that remainder as the brief's
budget (and `reattach.rs` rebuilds a re-attached brief the same way), so each
attempt draws on one budget.

`tick.rs`'s select-and-lease step checks it before picking a worker:
`spend::exhausted` stops a lease when a dimension has under one iteration,
under a tenth of an allotment's tokens (at most 2,000) or under a tenth of
its wall time (at most 60 s) left; a zero allotment is unbounded in that
dimension. `stop_spent` then fails the item `budget/<dimension>` with
`observed_by = cumulative_budget_guard` through `climb`, which skips its own
rungs for a budget error, never counts the guard's stop toward recurrence
(so it is not promoted to an improvement item), and surfaces it as
`blocked(budget_exhausted)` with one question, after a plan B or the parent's
re-plan inside a graph. Nothing is leased, run or spent. The ladder's ask for
a spent budget says what an answer does (`ladder/summary.rs`).

A worker's report cannot mint any of this. `breaker.rs`'s `reported_artifacts`
drops every artifact whose kind only the controller writes (`CONTROLLER_KINDS`:
`run`, `run_log`, `workspace`, `project_context`, `work_discussion`,
`daemon_build`, `investigation_bundle`, `resolution_outcome`, the breaker's
three kinds, `budget_grant`, `error`, `summary`, `operation_probe`,
`repair_generation`) before a
failed or finished report's artifacts are stored, and notes the drop as a
warning event on the item. `spend.rs`'s `allotments` also counts a
`budget_grant` row only when its provenance holds: it names a question on that
item which its owner (the row's `verified_by`) answered, once per question, so
a row stored any other way buys nothing.

`questions.rs`'s `answer_locked` resumes a leaf in `blocked(verification_failed)`
on an answer from its owner (`user`, `user:<who>`) or a delegate
(`policy:<grant>`, which only the router writes after a standing-judgment grant
covered the question), and a leaf in `blocked(budget_exhausted)` on its owner's
answer only: no judgment check delegates budget, so a delegate's answer, like a
recorded default, research, the controller or a worker, neither grants nor
resumes a spent budget. The owner's no cancels either, as a declined consent
does. The answer that releases a spent budget records one `budget_grant` row
(reference the question id, `verified_by` the answering actor), at most one
per question; an answered question is refused a second answer. Every
independent hold stands: another open question on the item, or its approval
hold (`held_by`), keeps it parked, for the reasons that resumed before this
change too.

`controller/breaker.rs` is the repeated-outcome circuit breaker. Each lease
writes an `attempt_state` row right after its `run` row: `hash` a 16-hex
digest of `AttemptState` and `reference` its JSON (the item's objective,
`done_when`, constraints and decisions with answers; its inputs, statuses and
verified commits; the workspace base; the worker, its kind and a digest of its
effective access, `Worker::access_profile` plus the access fields of the spec
it was added with, environment variables by name only; the required tools,
servers and writable resources; the done items it waits on with their close
times, its repair generation; the daemon build; and which ladder rung queued
the attempt, `retry`, `repair`, `switch_worker` or `other`). Run ids, paths,
timestamps, processes and secrets are never in it. `judge_attempt`, called by
`fail` and by the sweep's stall path before the ladder, writes an
`attempt_failure` row (run, fingerprint, class, whether it counts; `hash` the
attempt state) and trips when the last `breaker_repeats` counted failures
(`ControllerConfig`, 3 by default, `RUSTYKRAB_BREAKER_REPEATS` in the daemon,
0 off) share one fingerprint and one known attempt state. Budget failures do
not count; interrupted runs and worker-availability waits are never judged.
`trip` writes a `circuit_open` row (the runs, the fingerprint, the state) and,
instead of a retry, repair or switch, queues the item behind one investigation
through `filing.rs::file_internal`, reusing an open one, with an `improve` rung
whose outcome is `waiting on resolution item <id>; circuit breaker tripped: ...`.
`investigate::resolution_item` reads the id from either form, for the
investigation history and for the sweep's recovery of stopped resolution
waits. When no investigation can be filed (the open one is itself waiting on
its owner) the item surfaces once with a question instead. The breaker uses
`Rung::Improve` rather than a new rung: it is order 3's move, it keeps one
investigation per fingerprint per item, and the dreaming evaluation's
`RungEvent` parsing is unchanged. Because the ladder's rung is in the state,
its own bounded retries and repairs are different approaches, and only the
same approach failing the same way three times running, with nothing else
changed, trips it.

`tests/bounds.rs` covers each of these against a real store; `breaker.rs` and
`spend.rs` unit-test the trip rule, the access identity and the floors.

## Functional capability-proof seam (base 619d476)

The exported capability_proof module validates operation_probe evidence without
a model or host execution. Catalog availability and functional success remain
distinct. The trusted producer binds the actual observed operation, executor,
inputs/access digest, repair/configuration generation and invocation; the
controller supplies the expected tuple. Later failed or unobserved probes cannot
be hidden behind an earlier success, and conflicting tied records fail closed.
The existing Evidence shape stores the receipt; no schema or crate dependency
is added. The module cannot authenticate arbitrary model-written evidence and
does not release any owner hold. Adapters discard model-written probe artifacts
before forwarding. The module also exports ExpectedOperation, registered availability actions,
ProbeRequest/ProbeScope and canonical action/ceiling digest helpers. Expected
bindings still come from the controller, including a persisted generation before
dispatch. Local adapter producers now exist; the contract is
[here](../../docs/verification/capability-proof-2026-10-14.md). Controller
dispatch, evidence persistence and the replacement of the catalog gate are
the next section.

The same module owns `registered_action`'s need mapping and
`RegisteredAction::tool_call`'s canonical fixed invocation data; the adapter
and the controller's `proof.rs` both use it, so the two cannot drift.
`capability_proven_in_generation` selects a controller-owned durable
generation for shared capability waiters; unreadable or oversized evidence
stays visible, and the latest/provenance/binding checks within that
generation are unchanged. The strict `capability_proven` still judges all
supplied item probes.

## Functional capability proof in the loop (base 619d476 + #695)

A capability item for a missing tool closed `done` once the host catalog named
the tool (a `SKILL.md` was enough), and its completion revived the item that
needed the tool with nothing checking that the operation now worked; on
v6.5.6 one item ran 491 times that way. `controller/proof.rs` puts the
`capability_proof` validator in the loop for every need with a registered
probe, and leaves every other need as it was, labelled availability only.

- **Which needs.** `registered_action` maps a capability item's `capability`
  ref to the producer's registered actions: `tool:cargo` and `tool:node`
  (and `install:` of either) to `BinaryAvailable`, `tool:work_resources` to
  `ToolCallable` with exactly `{}`. It is `capability_proof::registered_action`,
  the one registry the producer in `rustykrab-agent`'s `capability_probe.rs`
  also uses, so the controller and the adapter cannot drift.
- **The expected operation** is the controller's alone. For each open item
  holding a `blocks` edge on the capability item: the executor is the worker
  its latest `lease` event names; the scope is that worker's `probe_scope`
  for the item's run directory, a fresh worktree at the base its last run
  recorded when it is repository-scoped (removed, branch and all, after the
  probe), else none; the inputs digest is `probe_inputs_digest`; the
  generation is `<waiting item>:<n>`; the run is a fresh `probe-<uuid>`.
- **Generation first.** Before anything is dispatched, a `repair_generation`
  row goes on the waiting item (`verified_by = controller`, `hash` the
  generation): `{n, cause: "capability", source_item, permission_digest,
  probes}`, the digest the breaker's effective-access digest of the
  executor, `probes` the `ExpectedOperation` of each probe asked for at this
  generation. Every registered need of the waiting item whose capability is
  the completing one or already `done` is probed again at the new
  generation, so revival judges all of them at one generation.
- **Dispatch through the executor's capacity.** `reconcile_all` holds a
  capability's done claim in its queue (`probe_waits`) until each executor
  has a free slot by the same rule a lease uses (`has_free_slot`: under its
  capacity, and for a serialised local worker its model idle), or is not
  registered. The probe then holds one of the executor's slots
  (`State::probing`, which `load_by_worker` counts beside runs), and is
  bounded by `ControllerConfig::probe_deadline`, at most 30 seconds, plus one
  second's grace for the receipt. A probe that returns nothing in that time
  leaves no row.
- **Receipt.** What `Worker::probe` returned, and nothing else, is stored on
  the capability item as `operation_probe` evidence: `reference` the
  `OperationProbe`, `hash` the expected inputs digest, `verified_by`
  `executor:<worker>`, `at` the controller's clock. A report cannot store
  one, nor a `repair_generation` (`CONTROLLER_KINDS`).
- **Gate 1, done.** `judge` asks `judge_capability` after `verify_claims`. A
  registered need is `done` only on `Proof` for every waiting item (a
  capability item no open item waits on cannot name an executor and is not
  proven). Anything else fails verification with the observation in the
  detail: `claim_mismatch` for a failed probe, `incomplete` for an
  unobserved one, a worker with no probe scope, an executor that is not
  registered or a probe with no receipt. The detail names no run or
  generation, so a repeat keeps its fingerprint and the repeated-outcome
  breaker bounds the repairs. Catalog presence is never consulted for a
  registered need. A need without a registered probe keeps the old check (a
  build of a tool against the refreshed catalog) and its `done` says
  `availability only`.
- **Gate 2, revival.** The sweep releases an item `parked_on_landed_capability`
  names (#693's freshness rule, kept) only when `revival_proven` holds: for
  every registered need, the latest generation's planned probe for that
  capability item, judged by `capability_proven_in_generation` over that
  item's `operation_probe` rows: only rows bound to that generation compete
  (any row it cannot read is kept, so it fails closed), and among them the
  latest governs. Before using those receipts it now rebuilds the current
  effective binding; see the current-path section below. An item whose needs
  are availability only is released as before.
- **Routing instead of a capability item.** A RustyKrab tool (one the
  catalog knows) that a native coding agent (Claude Code, Codex) reports
  missing is not a capability to build or acquire: its runtime cannot host
  RustyKrab tools, so no probe there could ever be observed. `climb` switches
  the item to a worker whose tool ceiling has the tool, or surfaces it once,
  before the ladder's order 2 (`route_for_tool`).

`tests/proof.rs` covers each of these through the loop with a scripted worker
that answers probes.

## Read-only review reports

Dreaming's project-review jobs (`cli/src/dreaming.rs::queue`: `research`

report a summary, known limits or an error. The native adapters' read-only

## Foreground dispatchability observation (base a19223c)

controller/dispatchability.rs observes demand through load, graph::is_ready,
precondition checks, validated cumulative budgets, the complete routing history
and the existing pick matcher. History.requires retains tool-routing constraints;
load_by_worker counts probe occupancy alongside runs. It does not copy covers, capacity, account backoff, model activity
or single-writer decisions. Busy resources are projected from the same active
leaves/isolated-run state. Public Controller::foreground_dispatchability takes
a nonblocking loop snapshot; missing, failed, draining, busy or over-60-second
loop state returns None, not idle. No item is leased, run, granted, answered or
changed by this observation.

DispatchDemand counts potential individually dispatchable foreground leaves,
not simultaneous starts. Waiting counts distinguish parent, blocked reason,
owner/ancestor hold, trigger, expiry, dependencies, preconditions, cumulative
budget and matcher unavailability. The matcher category combines unavailable
coverage/capacity; it does not guess an underlying account or access failure.
Active demand conservatively includes in-memory runs and unreconciled active
leaf leases. Research + dream_review_job + read_only_review=true jobs are
excluded from foreground counts, while their real occupancy still constrains
the matcher. Tests cover metadata immutability, dependencies/coverage, spent
budget, active work/review exclusion, unknown loop state, owner holds,
interactive model activity and single-writer exclusion with spare worker slots.

`Controller`'s `ControlHandle::foreground_dispatchability` delegates to this
observer, so a caller holding a `dyn ControlHandle` gets the same observation.
Scheduling/analysis opportunity policy is not enabled by the observation alone.

## Current-path capability binding (base #706 14507d9)

`EffectiveRequirements` contains the execution-relevant brief fields: kind,
post-`activatable` required tools, MCP servers, writable resources, read-only
review marker and stable repository/base identity. `brief_for` and recovery
share the same tool merge helper; a host binary such as node is not injected
as a RustyKrab tool. `ProbeContext` alone holds the transient controller-owned
`bound_dir`. `ProbeScope` records executor, Local/Host/Native path and policy/
ceiling digests. Input identity hashes the fixed action, scope and normalized
requirements. Set order/duplicates, temporary worktree, run id, deadline and
clock do not change that identity. Ordered data is not arbitrarily sorted.

`repair_generation.binding` is a defaulted optional field on the existing
controller-authored evidence row; no schema/table, scheduler or grant is added.
Legacy missing binding is stale. A new binding explicitly records unavailable
executor/scope as well, preventing repeated generations for unchanged unknowns.
Gate2 rebuilds the binding and compares it, plus the existing registry/adapter
access digest, against the latest **generation**, before checking its receipts.
A mismatch uses the existing bounded probe dispatcher if the executor has a
slot, writes a fresh generation before dispatch and reprobes all satisfied
registered needs. Failed or Unobserved receipts with unchanged binding do not
mint another generation on every tick. Planning comparisons allocate no
worktree; actual repository probes still create/remove a fresh one at the last
recorded base. The actual producer requires that directory to exist.

`probe_through` validates a wrapper's current scope, selects the child's own
scope, rebinds the same fixed request, checks the returned child's operation/
executor/input/generation/run and re-attests that observation at the outer
binding. It contains no concrete tool/CLI/model executor; adapters still perform
the observation under their real boundary. A host proof cannot stand for a
native CLI proof. Generation refresh neither grants spend nor clears independent
owner holds. Fixed version/resource availability remains narrower than arbitrary
compilation or original-goal recovery. Terminal refusals allocate bounded diagnosis through the existing work graph;
no independent investigation ledger or promotion pipeline is added.

Terminal gate2 refusals now append one controller Warning per durable generation
on the original item's event/investigation trail, with executor, selected path
and bounded reason. Unchanged rechecks do not duplicate warnings, probes or
owner questions. A Native-selected subscription has no registered producer,
so every registered need is Unobserved there. The existing sweep Batch allocates/reuses an owned internal investigation,
consuming an existing Improve rung and recording a once-per-generation action
marker. It keeps the original parked; no RESOLUTION_WAIT marker or original-run
spend/grant is invented. Pending internal work cannot revive the original.
Only this waiter's recorded diagnosis ids, once Done and git/replay verified,
refresh repair identity and trigger one new bounded probe at unchanged policy.
Unrelated or unverified landings do not. Actual Proof is still required, so a
landed but ineffective/undeployed repair cannot authorize revival.

Exhausted diagnosis budget or rejected allocation records a typed once-per-
generation failure and an owner notice through Batch::notify/Cause::Asked. This
creates no question record: answering a NeedsTool question can currently requeue
it, so that fallback would bypass Proof. The existing owner outbox gives the
failure visibility while preserving its hold. No new scheduler or authority.

The generation binding also includes the controller's configured daemon build
label (version/commit/dirty identity), excluding build time and invocation data.
A different deployed build triggers fresh observation even after the landed
repair was already probed under an older build. An unchanged or unknown build
label is not a new binary measurement; fixed availability proof and live
original-goal effectiveness remain distinct.

The once-per-generation action also indexes the real probe refusal in existing
error evidence, verified_by=capability_revival. failure_history can therefore
resolve its fingerprint and supply the investigation bundle instead of sending
an investigator blind. It creates no attempt_failure, original-run record,
usage charge or budget grant. Controller tests verify that lookup explicitly.
