The control layer of `docs/plans/control-layer-and-worker-fleet.md`: a
deterministic controller, in code and never a model, that schedules a graph
of work items, verifies every worker result from evidence, climbs a
resolution ladder on every failure, and surfaces to the user only when the
ladder is spent.

## Responsibility

Own the lifecycle of work. The model proposes (files items, reports typed
results, asks typed questions); this crate transitions. Readiness, cascade,
parent roll-up, leases, the ladder and notification are computed here from
the store's rows, so a restart re-derives the same state and nothing depends
on a model remembering its plan.

The crate does not own persistence (`rustykrab-store`), the shared data
types (`rustykrab_core::work`), the model-facing tools (`rustykrab-tools`)
or any channel. It reads and writes the store and calls workers through
adapters that sit above it.

| `questions/` | Plan section 7 as pure functions. `router.rs` is the question router: `route` classifies one question, first match wins, from what code can check (the item's state, what the item already had answered, the standing judgment in force, the question's kind and options) and only then the class the asking model claimed, into the planning plan's six classes and a `Route`: ask (blocking now), later (recorded for the next message), research, the recorded default, a delegated decision with its record and the grant that covered it, obsolete, or a repeat (the worker ignored its answer: a failure for the ladder). A model may not file `needs_decision` for a defaultable question (one option, or a default given as data), nor claim delegated authority. `stated_default` reads a default a question's words record, for the evaluation's audit only, never for routing. `judgment.rs` is standing judgment: `compile` reads a grant sentence by sentence against a fixed grammar into `JudgmentCheck`s (plan thresholds, resources that need consent or are delegated, topics decided alone or always asked), returns what it did not understand, and fills the projects crate's `JudgmentPolicy` (statement, delegated scopes, reserved decisions); `Judgment` folds the active grants, oldest first, over the configured `ApprovalPolicy` (`baseline()`: payments and messages to third parties need consent, plans over ten items or a million tokens need approval). `mod.rs` maps the classes to the projects crate's `QuestionImpact`. |

## Invariants

- **The model proposes, code transitions.** No path in this crate lets a
  model set a status. Cascade statuses (`blocked(upstream_*)`,
  `cancelled(cascade | superseded)`) are written only by the controller and
  always name their origin item.
- **A filing is atomic.** `work_plan`, `work_file`, the ladder's capability
  items, an accepted proposal and the delivery import all go through the
  same validator and are accepted whole or rejected whole with every failed
  check named. An item's review facets land in the same transaction.
- **The issue is a view.** The review surface never decides readiness and
  nothing flows back from it but the decision vocabulary; a local-only item
  appears on it only as `local:#N`.
- **Closed is final.** A retry is a new item; the failed attempt and its
  ladder stay in the record. The one deliberate exception, the delivery
  plan's rebase cascade, belongs to the delivery controller.
- **Sequential work stays in one worker.** The graph orders work, waits on
  the world and fans out independent branches; validation flags a split made
  only for sequence.
- **Unreadable rows parse to the conservative case** (`failed`, `blocks`),
  as `rustykrab_core::work` defines, so nothing runs early.
- **Every result is a claim.** A `code` result's commit and paths are checked
  against git, a check it names against the commands its adapter saw run,
  a built tool against the host's catalog. A claim beyond the evidence is
  recorded as `verification_failed` and climbs the ladder; it is never
  `done`, and it counts against the worker's routing record.
- **Code runs in worktrees, never in a checkout.** The parent commit is the
  controller's, pinned at lease time; the worker gets a branch and a
  worktree under the daemon's data directory, and the user's checkout never
  moves.
- **A restart fails nothing by itself.** A run that died with the process
  returns its item to `ready`; a run that lives elsewhere (a peer's task) is
  re-checked with its worker and re-attached while the worker holds it.
- **Credentials stay where they are held** (plan section 12.1). A peer
  worker's submission carries the brief's typed fields, never a secret; its
  own token for the node is kept in the encrypted secret store and in no
  spec or view.
- **The controller never moves a routing default.** It writes each
  worker's record from judged results and reads it to qualify workers;
  moving a class's default tier is a proposal.

- **The router classifies; the model only asks.** Only a blocking-now
  question outside delegated authority reaches the user. Authority comes from
  a grant the user made, compiled to checks a person can read back, never
  from the asker's claim, and every decision taken under it is recorded with
  its alternatives, rationale, authority and how to revisit it.
- **An answer resumes the item, not the conversation.** It reaches the next
  run's brief; nothing is written into the conversation that filed the
  work.
- **No item of a planned graph is ready before its planning item is
  reconciled**: the graph's top waits on it by a `blocks` edge, which a
  restart re-derives like any other.

## Dependencies

`rustykrab-core` for the work vocabulary and the `Error` type;
`rustykrab-store` for rows, leases and their history, events, evidence,
spend, the outbox and the archive, the `workers` and `routing_defaults`
tables, the review facets, and for the one read of `scheduled_jobs` a
firing's run id needs, and the secret store a peer's token is kept in;
`rustykrab-tools` for the work backend the model-facing tools call
(`WorkBackend`, `Provenance`). Nothing here depends
on a model provider, a channel or the gateway, and nothing here speaks
HTTP: `peer.rs` is the delegation contract's types only. `rustykrab-agent`
depends on this crate to implement `Worker` (and `NodeWorkers`). The workspace module runs `git` as a
process; it is the only thing here that does. `tempfile` is a
dev-dependency, for tests over real repositories.
The controller also depends on `rustykrab-projects` for `JudgmentPolicy` and
`QuestionImpact`. Its `ControlHandle` includes question answering and standing
judgment; worker observations belong to `WorkerRegistry`, so the gateway has
one worker view rather than a second controller-shaped list.

`controller/questions.rs` routes, parks and resumes questions transactionally,
and carries settled answers into the next brief. A blank blocked detail uses
the result summary or an explicit missing-detail diagnostic. `credentials.rs`
connects a credential question to the secure capture flow. `planning.rs` files
and reconciles planning items and replans; their budgets are capped by the
parent's remaining iterations, tokens and wall time. `unavailable.rs` parks work
for unavailable workers or hosts without treating a busy qualifying worker as
unavailable. `commit.rs` coalesces notices and skips internal capability
housekeeping. These paths preserve the registry routing, shutdown drain,
model activity gate, cumulative spend and repository-scoped workspaces.

The planner shares the local model semaphore with interactive and delegated
work. Only its explicit tool ceiling contains `work_plan`. Its initial visible
tools come from `AgentDefinition.tools`, independently of the allowed ceiling.

Worker roles are explicit through `Worker::planning_only`. A peer advertising
`work_plan` remains an ordinary worker unless its adapter declares planning
reservation. Notification provenance is recorded for questions carried in
result reports as well as for `ask_user`, alongside the outbox notice. A user's
answer supplies the explicit evidence used to identify an avoidable escalation.

## Native runtime observations

`WorkerSpec` persists optional Claude profile selection and a default-false
Max-login requirement, plus optional `codex_home` and default-false
`require_chatgpt`, in the existing worker config JSON; no table changes
are needed. `Worker::runtime_status` defaults to no observation, and
`WorkerView.runtime` includes a live native worker's sanitized status for
monitoring. The control crate does not import the provider implementation:
account authentication remains in the adapter, and routing reads the same
`healthy` boundary as other workers. Observations are supplied as JSON and
are not a durable remaining-quota ledger.

The execution worker name lookup excludes stored `role=planner` rows, so a
standalone planner cannot become the execution worker after a restart.

## Project continuity across native runtimes

`handoff.rs` defines the provider-neutral `ProjectContext` carried by `Brief`.
`controller/project_context.rs` resolves an explicit `project` artifact on work
or its ancestors, or a unique exact repository/canonical-conversation match
created before that work. It loads the current immutable planning snapshot,
work objectives/constraints/decisions, questions/answers and controller-verified
proof. Each lease freezes that revision, run pointer and workspace atomically
through `Store::work_lease_acquire_recorded`; peer reattachment reads the frozen
receipt rather than refreshing it. A new run rehydrates the current revision.

Historical controller receipts establish bindings after work compaction;
archive status and surviving git/check evidence establish completed progress.
Models' artifact pointers cannot establish a historical binding or verified
commit. Code starts at the latest commit on the ancestry chain containing both
repository HEAD and all completed project's verified commits for that repository.
Missing commits or divergent branches park work with a typed decision question;
no worker starts on a guessed base. Other projects on the same repository do not
supply code. Repository HEAD is never advanced. Unverified partial work stays
available through old run/workspace evidence and is not promoted to a base.

The exact context is bounded to 128 KiB; exceeding it parks the work rather than
silently dropping constraints. This is a current scale limit, not a semantic
summarizer. Native execution remains one item per CLI invocation. Tests use
real git and SQLite to switch a Claude-shaped worker to a Codex-shaped worker,
reopen the database, archive completed work, correct the project revision and
verify both inherited files and immutable old receipts. Workspace tests refuse
missing/divergent history; store tests prove receipt/lease rollback together.

Unfinished attempts carry controller-owned run/workspace/branch pointers and
classified failure records in project context. These let the successor inspect
partial work without accepting it as verified code. Model-written workspace
artifacts cannot supply these pointers or repository scope. The continuation
base still excludes every unfinished or falsely reported result.
