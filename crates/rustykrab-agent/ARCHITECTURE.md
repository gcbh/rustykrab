## Responsibility

The exploratory structured-message-tail compaction policy retains recent
dialogue within a bounded three-user-turn window. Oversized tool call/result
groups can be archived as a whole while smaller nearby messages survive;
selection preserves original chronology and never splits a valid tool pair.
This addresses browser observations crowding out short context, but trades
direct supporting evidence for summary/recall access. Summary factuality and
model use of retained constraints remain separately evaluated.
Its v2 prompt treats same-task corrections as field-level updates: other
requirements remain active unless withdrawn or contradicted. Explicit task
switches do not inherit unrelated old-task constraints. This addresses a model
omission observed even when the older preferences were retained verbatim.

Run a turn: call the model, classify what came back, execute the tools it asked
for under a sandbox policy, compact history when it grows past budget, and
decide when the turn is actually over. Run a work item for the control layer
the same way, as a `local` worker (`LocalWorker`), and return its typed result;
hand it to an external coding agent, Claude Code or Codex, as the
`claude_code` and `codex` workers (`ExternalWorker`); or send it to a paired
node on the tailnet as the `peer` worker (`PeerWorker`), and, on the node,
run a peer's brief as a local worker inside the node's ceiling
(`DelegatedRuns`).

## The loop

`run_inner` implements the shared streaming/non-streaming loop, per iteration:

1. Expiry check; repair an oversized stored summary before the first call;
   set the conversation's late binding (below).
2. Refresh the active schemas and compact against their usable input budget,
   plus actual-usage prediction when available. A compaction folds the
   conversation's appended tools into the declared set.
3. Inject a soft warning at `soft_iteration_warning`.
4. Reuse the version-keyed schema list computed before compaction.
5. Call the provider (optionally forcing `ToolChoice::Any` on iteration 0).
6. Classify the response: empty / planning-only / progress-narration /
   idle-acknowledgment / complete.
7. If tool calls: coerce each string argument that is exactly the scalar its
   schema declares (`coerce_tool_args`; a debug line per coercion, an info
   line per batch that coerced any, counted on the tracer as
   `arg_coercions`; the conversation keeps the call as the model wrote it),
   validate args against the schema, enforce the sandbox policy,
   execute in parallel with per-tool timeouts, fence external output, decide
   retryability per error kind. A batch spawns one task per call, and tokio
   task-locals do not follow a spawn, so each task re-enters
   `SESSION_TOOL_CONTEXT`, the trace id and a worker run's `WORK_RUN_CONTEXT`
   (`TaskLocals`, `with_task_locals`). A single call runs inline and inherits
   them. `start` carries the trace id and the work-run binding into the task
   it spawns for the loop.
8. End the run on a run-ending tool (`RUN_ENDING_TOOLS`; a worker run's are
   `WORKER_RUN_ENDING_TOOLS`, below). `task_complete` is
   read from its arguments before it runs, as it always was. `result_report`,
   its typed successor, is read after it runs (`run_end_summary`), because a
   report the host rejects must not end the run: the rejection goes back to
   the model as an ordinary tool result. Either way the summary becomes the
   final assistant message (`finalize_run_end`).
9. On `EndTurn` after tool use: re-prompt for `task_complete` unless a tool
   reported `blocks_turn()`. If the model answers that reminder with nothing
   at all (`Error::ModelEmptyResponse`, which Ollama raises for zero generated
   tokens), the answer it gave just before the reminder is the final one and
   the run ends normally.
10. Track seven independent retry counters, suppressing retries once a
   side-effecting tool has run.

### One portable conversation shape

Plan section 12.1: a request carries one system message, first, for every
provider and model. Every runner notice (the completion reminder, the soft
warning, "Continue.", the empty, planning-only and missing-call nudges, the
reflection prompt after repeated errors, compaction's summary instruction and
continuation, and the iteration cap's summary request) goes through
`runner_notice` and is a `[System notice]` user turn
(`Message::system_notice`). Ollama's Qwen 3.5-family template folds a
non-leading system message to the top of the prompt, losing both the nudge's
position and the cached prefix, and qwen3.8 has answered one with nothing at
all; the reflection prompt was an assistant message, which left the
conversation ending on the assistant, and qwen3.8 answered that with nothing
too (scenario 10, 2026-09-28). A run starts by giving its conversation the
same shape (`portable_shape`): a notice an older build stored as a system
message is rewritten in place as a notice. Which notices exist is not
decided here (upstream #663 removes some); only their role is.

A notice is the host's, not the user's words, and the consumers that read
user turns as the user's say so: compaction counts only `is_user_turn`
messages for its recent-turn window and pins the latest real user turn,
renders a notice as a system line for the summarizer and the archive, and
the runtime's memory writer and distiller and the gateway's Apollo view skip
or relabel it.

### A fixed tools array; late tools by append

Plan section 12 (Phase 2): the front tool block is fixed for the run and late
tools arrive by append, because changing the tools array rewrites the front of
the prompt and costs a full re-prefill (35 s on qwen3.8 at 7K tokens) while an
append costs under a second, and both default local models call a tool first
seen as JSON in a tool result. Before its first request each run sets its
conversation's `LateToolBinding` in the `ActiveToolsRegistry`: `Append` when
`ModelProvider::accepts_undeclared_tool_calls` holds (Ollama, the scripted
provider), `Rerender` otherwise (Anthropic, OpenAI), unless the harness
profile's `late_tool_binding` overrides it. Under `Append`:

- the declared set is what the host activated before the first call (the
  seed, `DEFAULT_ACTIVE_TOOLS`, a definition's visible set, an item's
  `required_tools`), and the version-keyed schema cache only rebuilds at a
  compaction, which folds appended tools in because it re-prefills anyway;
- `tools_list` and `tools_load` append (see `rustykrab-tools`), and the
  executor dispatches a call to an appended tool like any other;
- `task_complete`, made callable at the first tool call so it is not on offer
  for greetings, is appended rather than declared, and the completion
  reminder carries its definition after the fixed reminder text.

The iteration-cap summary call carries the run's tool block too, so a run
that reaches the cap keeps one block to its end (Phase 2's exit: no
tool-block change after turn 0). It used to send none, which re-prefilled
the whole conversation for the request that ends the run. The block is
there for the cache, not to act on: the cap's notice says no more tools will
run, and a reply that calls one anyway keeps only its text (or says the
limit was reached), so no call is left without a result.

**Only a callable tool runs.** A tool is callable in a conversation when
it is declared (the meta tools and the conversation's active set: the seed,
`DEFAULT_ACTIVE_TOOLS`, a definition's visible set, an item's required
tools, what a search or load declared under `Rerender`) or appended to it
(`ActiveToolsRegistry::is_callable`). Before a batch runs, `refusal`
answers a call to any other registered tool inside the ceiling with a
`not_found` tool error naming it as `NOT_CALLABLE` here, pointing at
`tools_list` and, when a search this run named it a non-match, saying so;
the call never runs, and the rest of the batch runs in order. Under
`Append` dispatch used to run any registered, permitted tool by name, and
told a search found nothing, both default models called the near-miss it
named, which ran (scenario 10, 2026-09-28). The rule is the same under
`Rerender`, where callable is exactly what the tools array declares, so it
is one rule for both bindings. The ceiling check still comes first and an
unregistered name still gets the executor's "unknown tool": the gate
answers neither.

Each run also resets its registry's record of `tools_list` searches that
found nothing, with the profile's `tool_search_miss_limit` (default 2): a
need searched past it is answered as final and recorded as a tool gap (see
`rustykrab-tools`).

### Worker runs

A run is a worker run when its caller scoped `WORK_RUN_CONTEXT` around it
(`LocalWorker` does; see below). Two rules change, and nothing else:

- **Only a call in `WORKER_RUN_ENDING_TOOLS` ends it, on its success
  shape** (`worker_run_end_summary`): an accepted `result_report`, the
  planner's accepted `work_plan` (its output is one accepted graph), or an
  `ask_user` or `capability_request` that parked the item. A rejected report
  or plan, or a question answered at once, keeps the run going.
  `task_complete` is never activated and its summary never ends the run.
  Text never ends it either,
  from the first turn and even after a turn-blocking tool (a blocked worker
  reports `blocked`): every text-only `EndTurn` gets the `result_report`
  reminder, up to the same `TASK_COMPLETE_RETRY_LIMIT`, and each reminder is
  counted on the tracer (`completion_reminders`).
- **The iteration cap ends the run without a summary call.** Its notice says
  no more tools will run, so it could not produce a report; the tracer
  records the cap (`iteration_limit_reached`). Durable workers set zero
  (unbounded) and use the typed no-progress path instead.

`run_traced` is `run` with a tracer the caller owns, so a caller can read those
counters afterwards.

## The local worker

`LocalWorker` implements `rustykrab_control::worker::Worker` over the same
parts `SubagentRunner` uses (provider, tool catalog, sandbox, an
`AgentDefinition` and its harness profile), plus the `WorkBackend` the
`work_*` tools call. Each `run(brief)` is one conversation, fresh unless the
host resumes a kept one (below):

- one leading system message, the definition's prompt, and one user turn,
  `render_brief`'s typed lines: objective, `done_when`, constraints,
  decisions, artifact refs, writable resources, the `inputs` block (closed
  status, evidence and artifact refs, one line of summary, the error class,
  the ids past the cap), the last error and prior evidence of a repair run,
  the usage-only execution policy, and how the run ends;
- the definition's visible set (`AgentDefinition::visible_set`: its `tools`
  and every tool of its `mcp_servers`, within the ceiling), the brief's
  `required_tools`, every tool of its `required_mcp_servers`
  (`mcp__<server>__*`) and `work_file`, `work_status` and `result_report`
  activated in a fresh `ActiveToolsRegistry` before the first model call, so
  the tools array is fixed from turn 0. A required tool outside the
  definition's ceiling fails the run before any model call, as a typed
  capability gap;
- the `work_*` tools built per run over a recorder that forwards to the
  injected backend and keeps each report it accepts, so `run` returns
  exactly what the backend received, and nothing from the run's scratch
  state (its todo list, its transcript);

- the brief's `required_tools`, every tool of its `required_mcp_servers`
  (`mcp__<server>__*`), `work_file`, `work_status` and `result_report`, and a
  definition's own `allowed_tools` when it names them (the planner's)
  activated in a fresh `ActiveToolsRegistry` before the first model call.
  A required tool outside the definition's ceiling fails the run before any
  model call, as a typed capability gap. `ask_user` and `capability_request`
  are in every worker's ceiling, loadable, not in the front block;
  `work_plan` belongs to every agent's protocol ceiling and activates when the
  brief requires graph filing; there is no planner role gate;
- the `work_*`, question and plan tools built per run over a recorder that
  forwards to the injected backend and keeps each report it accepts, so `run`
  returns exactly what the backend received, and nothing from the run's
  scratch state (its todo list, its transcript);
- every tool wrapped in a `LedgerTool` that records each call as a step in
  the run's progress ledger (`rustykrab_control::progress::StepLedger`, plan
  section 6 step 7): a call whose tool, arguments and result the run has
  seen before is no progress, and after `stall_steps` of those in a row
  (`DEFAULT_STALL_STEPS`, `with_stall_steps`) each repeating call's result
  carries a notice and gives the worker another `stall_steps` unchanged
  steps to change its approach. A new fingerprint resets both windows. After
  two windows, `MeteredProvider` stops before another model request with
  `model/loop`, and `LedgerTool` refuses further tool starts in that state.
  The transcript, worktree branch, actual spend and stall detail survive for
  normal controller recovery. Already in-flight tools are not reversed;
- the conversation id is the brief's `run` (the id the controller recorded
  as the item's `run` evidence) when it is one, and with `with_transcripts`
  the conversation is kept through the injected `RunTranscripts`: once with
  the brief before the first model call, so a cancelled or lost run leaves
  its brief behind, and again when the run ends. A run is then a
  conversation like any other, marked `channel_source: worker`;
- with `with_run_logs(<data dir>/run-logs)` the same conversation is also
  written as the run's session log, `<run id>.jsonl`: a
  `rustykrab.invocation` marker line, then one JSON message per line, mode
  0600, at the same two points, replaced each time and pruned after 30
  days. `Worker::run_log` names it, so the controller records it as the
  item's `run_log` evidence exactly as it does an external worker's, and
  an investigation opens a local run's failure as a file (an external
  worker cannot read the conversation store);
- a fix item's brief renders its investigation kit
  (`rustykrab_control::investigate::bundle::brief_section`) ahead of the
  workspace line. A local run reads those paths through `exec`; its `read`
  tool stays bound to its worktree. A general host agent built
  `with_repository_shell` has no `exec` without a workspace, so a fix item
  it runs reads its kit only when it has a worktree (a repository-scoped
  failure, or one in the daemon's own source);
- durable work runs with `max_iterations = 0` (unbounded) and no per-task wall
  timer. `MeteredProvider` (`metered.rs`) counts prompt and completion tokens
  after every response, including streaming and compaction; it never refuses a
  request because of accumulated usage. Its pre-request progress-ledger check
  still returns `model/loop` after persistent unchanged tool evidence. Context
  compaction, physical input/output limits, cancellation and the shared model
  semaphore remain. Interactive harness defaults are separate from durable work;
- a need the host told the run no tool provides (`tools_list`'s final
  answer, recorded as a tool gap in the run's registry) is why a run that
  ends without a report failed, whatever it did next: `run` returns it as a
  typed `capability_gap/tool` (`RunFailure::Gap`) ahead of
  unreported prose or the provider's error, for the ladder's
  order 2 (plan section 8);
- what the run spent (the meter's tokens, its wall time, the tracer's
  iterations and completion reminders) is kept by run id until the
  controller asks for it once through `Worker::usage`, a stopped run
  counting up to where it stopped; at most 64 are kept, oldest dropped.

A local attempt that fails, reports blocked/error, or asks questions retains its
workspace instead of force-removing uncommitted changes. The next project brief
keeps its unfinished_attempt workspace pointer; those files remain unverified
and must be inspected before any carry-forward. Normal unblocked/error-free
reports without questions retain existing directory cleanup (branches stay).
This does not add automatic replay, proof for partial edits or a new pruner.

Local execution briefs explicitly assign planning, execution and verification
to the same worker within the objective, constraints and available tools. An
explicit `work_plan` run still files a graph and stops; read-only review and
resource boundaries still apply. This guidance does not grant new authority or
prove model reasoning quality. `tests/worker_autonomy.rs` drives actual
LocalWorker, ExecTool, controller, SQLite and Git: one fixture changes approach
after a repeat warning and resolves both parents itself; another stalls, hands
off to a deterministic alternate Worker, then the original local worker resumes
and produces a Git-verified useful result. The alternate is a fixture, not an
exercise of the Codex CLI or subscription. Test-only store/projects dependencies
support this execution regression and add no production dependency.

Ordinary local and native executor briefs explain that the summary becomes a
notification linked to the detailed execution. They ask for one or two sentences
about the outcome or the user's next action, with supporting detail in artifacts
and check records. This is model guidance; it does not guarantee a response length.

LocalWorker defaults to compact result summaries. The trusted host can opt in to
with_full_reports for a content-delivery worker: its per-run result_report tool
accepts at most 32,000 characters over the same recording backend, with matching fresh/resumed brief guidance. The ordinary
1,500-character bound and all report/ceiling/lifecycle checks remain the default.

**A resumed conversation.** `RunTranscripts::resume(id, brief)` (defaulted
to `None`) lets the host hand back a kept conversation for a run whose id
names one: the daemon does so for a scheduled job's firing, whose run id is
the job's persistent conversation (`rustykrab-cli/src/scheduled_work.rs`).
The run then continues it rather than starting fresh: its leading system
messages are replaced by the definition's prompt with the host's `guidance`
appended (the job's SKILL.md body as `<skill_instructions>`), any later
system message it kept becomes a `[System notice]` user turn (12.1), and the
run's user turn is the host's `preface` (the scheduled prompt) ahead of the
brief. The conversation keeps its own channel fields. A `resume` error fails
the run rather than overwriting a conversation it could not read.

It advertises every writable resource (`*`) unless its definition names
some: a local run writes through this daemon's own tools, and who may write a
resource at once is the controller's single-writer rule, not a capability.

Its definition is a file (plan section 12): `default_definition(name)` is the
built-in `worker` definition from `rustykrab-skills`, and
`named_definition(def, name)` puts any definition, such as a data dir's
`agents/worker.md`, under the worker's name, filling the `{name}` placeholder
in its prompt. `SubagentRunner` takes the same files for its `coder`,
`researcher` and `planner`; the coder starts with the filesystem and runtime
tools declared.

Two Phase 3 additions, both local to `local_worker.rs`:

- **Late tools.** `with_late_tools` takes a `LateTools` source, asked at the
  start of every run and by `capabilities()`: tools that exist only because
  something wrote them while the daemon ran (a capability build's
  `SKILL.md`, loaded by the CLI's `RuntimeSkills`). They join the host's
  catalog for that run, never replacing a tool of the same name or a
  `work_*` tool, so a resumed item can have the tool it waited for active
  from its first step (plan section 8, rung 2b; scenario 13).
- **Worktrees.** A `code` brief with a `Workspace` gets its worktree
  created before the run and removed after it, and the run's `exec` is an
  `ExecTool::in_dir` bound to it, so a local worker commits in the isolated
  checkout the controller verifies, never in the user's own (scenario 17).
  The brief says where, on which branch, from which parent commit. That
  `exec` is `confined` (macOS Seatbelt) with the daemon's data directory
  unreadable (`with_private_paths`) and its gateway port unreachable
  (`with_private_ports`); inside the sandbox any program runs and only
  forced removal is refused (`rustykrab-tools`' `Confinement`).

## The external workers

`ExternalWorker` implements `Worker` for `claude_code` and `codex` over one
adapter shape. It lives here, beside `LocalWorker`, rather than in
`rustykrab-control`: the control crate owns the seam and the workspace
kernel (`Workspace`, verification), and every implementation of the seam
sits in the crate that can run things, which is also where the local
worker's brief rendering lives. It needs nothing from the runner, so it
could move to a crate of its own if the adapters grow.

- **Where.** A `code` brief's workspace is created from the item's
  repository (a `policy/scope` stop if the repository is not one of the
  worker's), and the agent runs in the worktree under the daemon's data
  dir; any other brief runs in `<data dir>/workers/<name>/runs/<run>`.
- **How.** Claude Code: `claude -p <brief> --output-format stream-json
  --verbose --permission-mode <mode>
  --allowedTools <list> --disallowedTools "Bash(git push:*),Read(//<data
  dir>/service.json),..."` followed by the spec's `denied_tools` (a spec
  can deny more, never less), plus `--model` and, for a capability build,
  `--add-dir <skills dir>`. The allow list is `CLAUDE_DEFAULT_TOOLS`, Claude
  Code's own default working tools (`Bash`, `Read`, `Edit`, `Write`,
  `NotebookEdit`, `WebFetch`, `WebSearch`, `Agent`, `Skill`, the task-list
  tools, `LSP`), then whatever the spec's `allowed_tools` adds: a spec adds
  to the list and never replaces it. The deny list is publishing and the
  daemon's secret files (`SECRET_FILES`, by absolute path). Codex has no deny list flag, so the registry
  refuses a codex spec with `denied_tools` at add time (400
  `invalid_request`); one stored before that refusal is dropped here with
  a warning. A path-scoped deny such as `Read(~/.config/**)`
  stops Claude Code's file tools only: `Bash` is on the allow list, and a
  shell command can still read any file the user can, so it is a guard
  against a worker wandering, not confinement. Codex: `codex exec --json --skip-git-repo-check --sandbox
  workspace-write --cd <dir> --output-last-message <file>` (a ChatGPT
  runtime is not run `--ephemeral`, so its session is kept, and its web
  search is left on), plus the same
  two. The environment is cleared except `PATH`, `HOME`, the locale, the
  agent's own config and key variables, the spec's pass-through names, and
  `RUSTYKRAB_DATA_DIR`/`RUSTYKRAB_SKILLS_DIR`. The wall timeout is the
  smaller of the worker's and the item's.
  The final-message file has a fresh UUID per `Worker::run` call as well as the run
  label. Workers or controllers reusing a label cannot overwrite or remove
  one another's results. Normal completion removes the temporary file after
  reading it; a barrier-based concurrent-worker regression exercises this.
- **Starting it.** The agent is started through
  `rustykrab_providers::cli_process::spawn`, which waits out a busy
  executable (`ETXTBSY`) for about 0.6 s. A CLI whose updater is replacing
  it, or one held open by a fork from another thread, therefore does not
  fail the run. A busy start ran nothing, so starting again repeats
  nothing. The wall limit counts from the first try, so the waits come out
  of it, and no try starts after it.
- **Its process group.** On unix the agent starts in a process group of
  its own, recorded in a `RunGroups` (the process-wide
  `RunGroups::global()` unless the worker was given another) for as long
  as the run lives. A cancel drops the run, which kills the agent
  (`kill_on_drop`) and then the rest of its group, so nothing it started
  survives it. The wall timeout kills the agent and its group the same way,
  but stdout and stderr are read as they arrive, so the run still records
  the tokens and turns it had printed (summed as below) before ending
  `tool/timeout`. Daemon shutdown calls `RunGroups::terminate_all`:
  SIGTERM to every live group, SIGKILL to any still there after the grace.
  It marks each group before signalling it, so the run returns
  `RunFailure::Interrupted` (`interrupted/shutdown`) instead of a failed
  process, and the controller returns its item to `ready` with no rung
  and no repair counted; a report the agent handed in first still stands.
  Its usage is what the agent printed before it was ended: with no
  stream-json `result` envelope, Claude Code's tokens and turns are summed
  from its assistant messages (one turn per message id), so the item's
  spend survives the restart. With no result its worktree is kept for retention. Signals go through a direct `kill(2)` declaration rather than
  a `libc` dependency. `LocalWorker` has the in-process counterpart,
  `LocalRuns` (`LocalRuns::global()` unless given another through
  `with_runs`): a run joins it before waiting for its slot, and
  `LocalRuns::interrupt_all` at shutdown makes it stop where it is, remove
  its worktree and return `RunFailure::Interrupted`, so the final tick
  reconciles it instead of the task dying with the controller.
- **The brief** is the delivery plan's executor brief
  (`render_executor_brief`): the item's typed fields, inputs, the prior
  failure, repository, worktree, branch and parent commit, what a
  capability build must write where, and the section 5 result contract the
  final message must be.
- **No turn cap.** A run works until the agent returns its final message,
  in its own harness; the wall limit is the only stop. A cap of 30 turns a
  round, with resumes and a contract-only wrap-up, was removed: it limited
  nothing the wall limit did not and cut work short. A Claude Code result
  that still reports `error_max_turns` (a cap from the agent's own settings)
  reads as a process failure.
- **The session log.** Everything each invocation printed (the agent's own
  JSON event stream) is appended to `<data dir>/run-logs/<run id>.jsonl`
  behind a `rustykrab.invocation` marker line, with its stderr when it
  wrote any, mode 0600, kept 30 days. `Worker::run_log` names the file and
  the controller records it as the item's `run_log` evidence
  (`controller/spend.rs`), whether the run reported or not.
- **A fix item's kit.** A brief with `investigation` set (the ladder's item
  for a recurring or unknown failure) gets the kit's section in its prompt:
  where the controller wrote the failure's history, how to read it a
  portion at a time, what else it may read, the daemon's own source and
  commit when known, and what earlier fix items concluded. Claude Code is
  also given each of the kit's directories with `--add-dir` (the bundle,
  the session logs, any failed run's kept worktree, the daemon's source);
  its toolset is unchanged. Codex is given no flag for them: its sandbox
  reads the whole disk (checked with `codex sandbox` on codex-cli 0.159.3),
  and its `--add-dir` makes a directory writable, which evidence must not
  be.
- **The result.** `parse_contract` reads the contract from the final
  message (whole, fenced, or the last balanced object), makes an unknown
  error class or blocked reason classifiable, and reads a question given as
  a plain string as one with that text, no class and no options (a question
  that is neither an object nor a string still fails the parse). The
  adapter adds what it saw:
  shell commands from runtime events, as `command_run` artifacts (a
  model-written one is dropped), which the controller checks `checks_run`
  against, and the run's tokens, turns and wall time (`usage`, by run
  id) for the routing record and the controller's usage. No contract is a
  `RunFailure`: a native turn cap is a process failure, an operational timeout
  is `tool/timeout`, a failed process
  `process/<code>`, a final message that is not the contract
  `model/format`, and a run shutdown ended `interrupted/shutdown`.
- **Retention.** A run that produced a result gives its directory back
  (the branch stays); one that did not keeps it for diagnosis, and kept
  directories older than a week are pruned at the next run
  (`Retention::KeepFailed`, the delivery plan's "preserve failed worktrees
  for diagnosis, then clean them through an explicit retention policy").

`LocalWorker::planner_definition()` is the control layer's `planner`
(plan section 6.1): `work_plan`, `work_status`, `recall_search` and
`memory_search` as both its explicit visible `tools` and its `allowed_tools` ceiling, no write
access to the world, and a prompt that states the one-graph contract. It is
an embedded file definition in skills/agents/work-planner.md. The host loads
an optional <data dir>/agents/work-planner.md override through the same agent
catalog, then registers it as the local worker named planner. The ordinary
read-only planning subagent remains a separate definition.

A run that stops with text has answered: the text is its report, the result
contract it carries (`external_worker::parse_contract`, as Claude Code and
Codex runs give theirs) or else the text as the summary, filed through the
same recorder `result_report` uses. With `result_report_reminder` on
(`with_result_report_reminder`; off by default, since on qwen3.8 it never
fired in 32 measured runs, `docs/measurements/reminder-eval-qwen38-2026-10-14.md`)
the model is first reminded up to three times. A run that ends without a report returns
`RunFailure` (defined beside the `Worker` trait in `rustykrab-control`):
`model/loop` (persistent unchanged tool calls after a warning window) or
`model/empty` (no text). Legacy budget error types remain readable for history. A provider error passes through
unchanged. The controller classifies either through
`worker::run_failure_input`. `last_run()` keeps the numbers a report does not
carry: iterations, reminders, rejected reports.

The design intent throughout is *don't trust the model's stopping signal, and
don't let a retry duplicate an externally-visible action*. Both are right, and
both are handled with visible care — `should_retry_unchanged_tool_call` and
`tool_error_output` each carry their own test modules.

Fencing wraps every string over 80 characters in a result from an
external-content tool, with one exemption: the top-level `guidance` key, listed
in `UNFENCED_RESULT_KEYS`. That key is RustyKrab's own instruction to the model
— how to submit an approved payment, why a pay was refused — written from
string literals, `Money` displays and refusal-enum messages, never from page
text. Fencing it told the model to disregard its own safety rail, which a
payment eval caught happening. The exemption is deliberately top-level only:
a `guidance` field nested inside a fetched JSON body or an `evaluate` result
belongs to the page and is fenced like anything else. `reason`, `message`,
`error`, `payment` and `duplicate_of` stay fenced — each can carry page-derived
text (navigation reasons include page titles, errors echo page content).

Browser results have one additional context rule: when a newer result carries
page state, detailed state in earlier browser results is replaced by a small
provenance summary. Calls and action outcomes remain in history and the newest
refs remain intact. This applies browser-use's replaceable current-state model
without discarding the execution trail or repeatedly sending obsolete DOM
snapshots to the model.

## The peer worker

`PeerWorker` implements `Worker` for the `peer` kind over the delegated-task
API a node already served for the `nodes` tool, with the typed half of
`rustykrab_control::peer`. Like `ExternalWorker` it lives here rather than
in the control crate, which owns the contract's types and no HTTP.

- **Submit.** `POST /api/tasks` with the brief's typed fields
  (`workItemId`, `requiredTools`, `brief`, `run`), `hopBudget` 0 (a peer
  never delegates onward), and the brief rendered by `render_brief` as the
  message. The worktree is stripped: a peer never works in this machine's
  checkout. The run id makes the submission idempotent on the node. A `422`
  refusal comes back typed: a tool the node lacks is
  `capability_gap/tool` (the ladder's order 2), one its policy withholds is
  `policy/ceiling`. While the node does not answer, the submission is
  retried until the deadline.
- **Poll.** `GET /api/tasks/{id}` every `poll` (2 s). A connection failure
  marks the worker unhealthy and polling goes on, since the node may be
  restarting and puts an interrupted task back in its queue; a task the
  node no longer has is submitted again under the same run.
- **Result.** A done task's `report` (the node's `result_json`) is the
  result; so is a failed task's report whose `error` the node typed. A done
  task with only text is `model/format`; a failed or cancelled one with no
  type is `environment/process`. The operational deadline is the spec's
  `timeout_seconds` (an hour by default); retired task estimates cannot lower it.
  Past it the node's task is cancelled and the run ends `tool/timeout`, or with a
  transient network error when the node never answered.
- **Stop and restart.** `stop(run)` cancels the node's task in the
  background; dropping the run's future does not, so a controller that
  shuts down leaves its peers' tasks running and `resumable(run)` (`GET
  /api/tasks?run=`) finds them again: one the node has and has not
  cancelled is kept, and so is any run while the node does not answer,
  since a resubmission under the same run id is the task the node has.
- **Advertisement and health.** `refresh` reads `GET /api/node` at most
  every 30 s while the node answers and on every call while it does not;
  the worker is healthy only while the node answers and takes structured
  briefs, and its capabilities are what the node last advertised.
- **Credentials.** The token travels in the `Authorization` header only,
  with a loopback `Origin` as the `nodes` tool sends; nothing in the body is
  a secret.

On the node, `DelegatedRuns` builds a `LocalWorker` per structured task, its
definition's `allowed_tools` narrowed to the ceiling the gateway computed for
that task, so a delegated run is a local worker run in every respect: the
brief as its one user turn, `required_tools` activated before the first
model call (one outside the ceiling fails the run first, as a typed gap),
usage recorded without execution estimates, the transcript kept under the run id, the typed report
returned. Its `work_*` tools go to `DelegationBackend`, since the item lives
on the controller that delegated it. It advertises that ceiling's models,
tools and MCP servers with the node's machine name and the resources a
delegated run may write (none unless the node names some).

The crate depends on `reqwest` for the peer worker's client, which it already
had in its tree through `rustykrab-tools`.

## Compaction

`compact_history_preserving` summarises displaced history and archives the originals into
`RecallStore`, so the agent can recover detail via the `recall_*` tools rather
than losing it. Oversized inputs are packed into chunks and summarised
recursively (`summarize_text_recursively`), with a fast single-call path when
the input fits. Oversized individual fragments are split losslessly at UTF-8
boundaries rather than emitted as over-budget chunks. `enforce_summary_cap` re-summarises and, failing that,
truncates on a UTF-8 boundary. `repair_oversized_summary` fixes summaries
persisted by older builds *before* the first model call, so an old database
can't produce a prompt large enough to trip the provider's HTTP timeout.

`AgentConfig` selects the policy and optionally a total compacted-message
budget, not merely a summary-size limit. `HarnessProfile.compaction_strategy`
serializes the explicit policy; routing inherits it from the base profile
instead of resetting it to a preset. Old profiles use the default policy and
unknown spellings are rejected. `compact_for_evaluation` invokes the
same path without executing a tool, so the ablation tests the implementation
rather than a parallel approximation. Legacy, the default, keeps its old
retention (first and latest user input pinned) but since 2026-10-15 writes an
explicit state handoff: named sections for the objective with its exact
values, the latest instruction, constraints and preferences (superseded values
marked), candidates and their status, findings, failed attempts as
observations, what is done and open, and the next step (`STATE_SECTIONS`). On
the recursive path its summarizer gets its own system message
(`SUMMARIZER_SYSTEM`), the history fenced in `<history>` and the instructions
after it. The recursive model-summary path omits the agent's own
system messages for every policy; the cached one-call path keeps the original
conversation and tools block. The prompt was chosen by a
hill-climb on the 128K context eval
(`docs/verification/compaction-state-handoff-2026-10-15.md`). Structured
changes the handoff prompt, StructuredTail also protects a bounded recent
suffix of whole user turns, and Extractive skips model summarization.
All policies pin the first/latest user input verbatim. Mandatory anchors that
cannot fit cause an explicit refusal; this favors visible failure over an
apparently successful request with changed intent. Summary quality remains a
model-dependent empirical question, not a consequence of these invariants.

Summary calls use a separate message vector. Cancellation or provider failure
cannot leave a temporary summarization prompt in the live conversation. The
compactor also rejects a generation-limited summary before replacing history
or feeding the next recursive reduction. This integrity guard can make a turn
fail visibly when the generation reservation is too small; it does not prove
that a normally terminated summary preserved every relevant fact. The
archive/history replacement is committed only after final-budget validation.
This transient clone costs memory proportional to history size. Archive
existence alone does not mean the model will consult the needed detail.

## The loop was duplicated; it no longer is

### Interactive continuity repair (base `0b565fd`)

`start` returns `AgentRunCompletion { conversation, result }`, retaining partial
history on ordinary failures, caught execution panics and watch-channel cancellation.
Interrupted tool calls get an explicit unknown-outcome result: callers must inspect
external state before retrying. This does not make external effects reversible.
Admission is bounded and nonblocking; a closed/full inbox returns a failure to its caller.
`send_message_record` preserves a journaled input UUID and rejects non-user
messages. The loop deduplicates admitted records already present in history.
The loop drains accepted input before model iterations and dispatches completion-edge
follow-ups within the same total iteration allowance. It seals admission before exiting;
error/cap paths retain pending input but do not claim to have answered it.

Compaction pins the first user message and the latest inbound user message by ID,
placing the latter after the lossy summary. Runner-generated retry/cap prompts
and the diagnostic reflection containing observed errors are `[System notice]`
user turns (see One portable conversation shape): the marker, not the role, is
what keeps them from reading as user authority, and every consumer that treats
a user turn as the user's words checks it. Older persisted synthetic-user
messages without the marker remain ambiguous; no heuristic rewrites historical
user input (a stored non-leading *system* message is rewritten as a notice).
The adapter reports `ContextBudgetExceeded` before dispatch instead of silently
trimming. The runner may compact and retry that refusal once if history shrank;
otherwise it returns the partial trail and explicit error.

### Earlier loop unification

`run_inner` and `run_streaming_inner` were 82% identical. They are now one
`run_inner` parameterised by an event sink, with `run` passing a sink that
discards.

The merge was worth doing on evidence rather than principle: while it was in
review, the usage-anchoring and tool-block-on-compaction work landed into
**both** copies, ~60 lines each. The unification then halved exactly the
symbols that had been written twice (`max_tokens_retries` 8→4,
`compact_history(conv, tools)` 2→1) and left the shared ones alone, which is
how you check that a merge preserved the work rather than resolving over it.

Two things did not transfer mechanically. The per-iteration
`tracing::info!(iteration, total_messages)` existed only in the non-streaming
copy. And roughly ten comments in the streaming copy read "see run_inner" —
pointers to the function being deleted; taking that body verbatim would have
compiled, passed every test, and left the loop's reasoning pointing at
nothing.

One consequence, deliberate: every run now calls `chat_stream_with_choice`.
No provider changes behaviour, but a provider implementing only the
non-streaming variant would silently lose the iteration-0 tool-choice guard,
because the trait's default chain drops the constraint.

## Compaction now anchors on measurement

`predicted_prompt_tokens` uses the last response's actual
`prompt_tokens + completion_tokens` and applies the chars-per-token heuristic
only to messages appended since. This replaced a pure estimate that
undercounts JSON-heavy history by ~40%, which had let real prompts reach the
window while the estimate sat below the threshold. The usage anchor is
dropped whenever history is rewritten, because an anchor describing messages
that no longer exist is worse than no anchor.

## Provider-neutral project handoffs

Both `render_brief` and `render_executor_brief` render the controller's
execution view: the exact immutable planning snapshot and task-relevant durable
work/question records. Claude and Codex receive the same representation; neither
CLI's chat history is the source of project state. The full frozen context remains

portions. It follows run retention, cannot enter a normal repository commit,

partial directories are not treated as verified project code.

## Native frozen review execution

Research briefs marked `read_only_review=true` receive the adapter's reduced

`--approve-for-me`, which selects workspace-write), or Claude with native

reviews use scratch directories and have no writable repository resource.

drafts may run concurrently within resource policy. A report must not label an
unfinished current acceptance criterion complete. The guidance uses the existing
result contract rather than an additional execution queue or a model-written
completion flag. The native process regression inspects the actual private file
and argv for both runtimes, including an oversized previous repair receipt.

## Host command evidence for local execution

The per-run LedgerTool records exact exec commands only after the trusted host
tool returns a process exit code. The recording WorkBackend strips model-authored
command_run and operation_probe artifacts and attaches those observed commands before forwarding
result_report to the controller. Recording after Worker::run returns would be
too late: report forwarding can already close the work item. The returned
receipt preserves the exact command evidence passed to the backend.

The controller's existing command matcher can therefore verify local checks_run
claims whenever commands were observed, just as it does native command records.
A command record establishes execution, not test success; exit outcomes remain
in the tool transcript. Rejected or failed tool dispatch does not attest a
command. This adds no provider, trait, table or execution queue.

## Subscription capacity before native execution (base 5bb3ed7)

ExternalWorker supplies its configured model to ClaudeMaxRuntime, so a named-model
quota blocks only an affected executor. Registration and refresh read native
subscription usage as well as login; exhausted accounts are unhealthy before
the controller selects them. The run's forced verification repeats the guard
before invoking inference. Existing Worker health, refresh and runtime_status
seams carry measured windows, reset and read errors; no new trait, queue or
credential transport is introduced. A known reset supersedes the old blanket
five-minute retry. Startup re-reads native usage, and unknown reads retain dated

## Label-independent execution

Worker briefs contain objectives, criteria, constraints, resources and evidence,
without task category headers. A repository-scoped task receives its isolated
workspace regardless of a historical label. Native read-only review restrictions
come from the explicit review-only requirement, independent of WorkKind.
Backend identities remain necessary to invoke Claude, Codex or a peer correctly.

A definition with no explicit writable scope inherits the host's broad scope
only when its permitted tools declare actual side effects. Context-only tool
sets advertise no external write resources, preventing a read-only context
agent from winning repository/build jobs after planner reservations are removed.
This derives coverage from tool requirements, not an agent name or category.

## Exact host file outputs and repository isolation (base 5bc3309)

`file_scope.rs` wraps read/edit/write for exact operator-delegated files.
`ExternalConfig` validates absolute file paths with existing parents, rejects
symlinks/directories/traversal and keeps these grants out of native shell
arguments. Grants require a subscription resource with scoped host tools;
explicit Claude native deny policies cannot be bypassed by adding file grants.
A bare ExternalWorker registration refuses this unsupported execution path.

`LocalWorker::with_writable_files` adds exact file resources to its definition.
At run admission, every requested file must have an exact grant. Without a
worktree, the host retains only those scoped file tools and removes exec. With
a worktree, file tools permit that checkout and the exact additional files.
`ScopedFileTool` validates each call against the selected path and rejects a
symlink redirect or neighboring output. Files are not broad directory grants.
Operator-provided tool ceilings still determine which file tools exist.

`LocalWorker::isolates_worktree` opts in only for repository-shell workers,
whose shell/file tools are rebound to the supplied checkout. ExternalWorker
opts in for its controller-owned native checkout. Wrappers forward the
execution guarantee; ordinary/default and peer executors retain a conservative
repository-wide lock. The controller continues verifying returned git claims.

The separate default-empty `readable_files` worker option grants exact read-only
inputs (`worker add --readable-files PATH[,PATH...]`). Reads may use those inputs;
write/edit calls still require a requested exact output grant or the run's own
repository worktree. Input grants do not advertise writable resources and remain
out of native shell arguments. The native host path preserves both grant arrays
from its stored spec.

## Local read-only review execution

A brief marked read_only_review=true has only result_report in both the local
worker's catalog and session ceiling. The definition, late tools, active-tool
loading and delegated read grants cannot add host execution, writes, work
filing, questions or discovery to it. Automatic recall is omitted so a frozen
review is not mixed with retrieved material. Contradictory workspace, writable
resource, required-tool or required-server requests fail before inference or
worktree creation. The same resource slot, transcript and host usage
accounting still apply.

The recording backend rejects report artifacts, discovered work, questions,
commit/changed-path/check claims and blocked instructions before forwarding;
summary, known_limits and a failure report remain permitted. A report is not

## Host tools over MCP: run-scoped grants (base 4f7510e)

Rollout step 1 of `docs/plans/native-mcp-host-tools.md`. A native run whose
brief needs a RustyKrab tool will run in its own harness and reach that
tool over MCP rather than fall back to the host half. `mcp_grants.rs` is the
daemon's half of that: `McpGrants` holds every live grant, and
`McpGrants::mint(GrantSpec)` makes one, a 64-hex-character random bearer
token (`rkmcp_` prefix, `GrantToken`, which never prints) bound to one
item, the run's conversation, one actor (`worker:<name>`), the tools the
run may call, a deadline (the run's wall deadline, or the lease's when
sooner) and a call quota. A read-only review's grant carries no tools
whatever it was given. The minter holds an `McpGrant`; `finish` or dropping
it revokes the grant, so it ends however the run does. The gateway's
`POST /api/mcp` resolves tokens here; nothing mints one yet (rollout step 3
wires the native worker).

Admission is atomic under the grant's lock: live (not revoked, before its
deadline) and its run not ended, then the quota (every attempt counts,
refused ones too, across reconnects), then a new request id (the bridge's
session and the JSON-RPC id; a reused one is refused, never replayed), then
the tool (outside the grant is refused and recorded `denied`), then one
call in flight. A call runs as a local run's tool call does: under
`WORK_RUN_CONTEXT` bound to the grant's item and actor and
`SESSION_TOOL_CONTEXT` carrying the run's conversation (and no capability
or tool a call could load), so the work tools take their scope from the
grant and never from the agent's arguments, file and route under the run's
conversation, and reach the same `WorkBackend` as every other caller. It
runs until the grant's deadline or `tool_cap_secs`, whichever is first;
revocation or expiry cancels it (`CallError::Cancelled`) and the tool's cap
stops it with a tool error. Any call stopped where it was, or abandoned by
its request, is recorded `ambiguous`: its effect may have happened, and is
recorded as unknown, never as done or not done. Success is judged once, for
the record and for the agent's `isError`: an error, or a work tool's
`outcome: rejected`, is a failure.

A call that ends a worker run on the host half (`worker_run_end_summary`:
a question that parked the item) ends this run too: its result tells the
agent to stop and write its final report, no further call is admitted
(`CallError::Ended`), the record keeps the summary (`ended`), and
`McpGrant::ended` resolves, so the minter can stop the agent.

Observation is per grant, and so per item, run and generation: each grant
records only its own calls, and its record is sealed when it is revoked (a
late result is dropped, not carried into the item's next run, which may
reuse the run id). Only the grant attests: `McpGrant::finish(Some(report))`
replaces any `mcp_call` artifact the agent wrote with the grant's own calls,
so no other run's record can attest a report. `work_tools` is the first set
granted: `work_status`, `work_file`, `ask_user` and `capability_request`.
`result_report` is not one (a native run reports with its final message),
nor `work_discuss`, which takes its item from its arguments. The record's
`bridge_connected` is set when the bridge's `initialize` and `tools/list`
have both arrived: reachability, never proof of a call, and never an
artifact.
