## Responsibility

The credential-boundary slice adds native implicit form labels and omits
recognized card/CVV input values from compact and structured snapshots.
Generic credential requests still refuse card fields at the store level; cards
take their own path (below). This is not comprehensive card detection or a
reusable wallet; outside an armed payment page, evaluate/screenshots/page
reflection remain exposure paths.

Secure fill binds to the live canonical origin and a verified DOM input object
before vault access. The v2 origin key hashes scheme, host and effective port.
HTTPS is required except for explicitly enabled private-network test policy.
Cross-origin frames, model URL overrides, recognized payment fields and
password-to-plaintext targets are rejected. The object-bound setter rechecks
origin, attachment and type at application time. It does not use focus-based
typing, ref healing or an automatic post-fill snapshot. SSO iframe and framework
compatibility need separate testing; an authorized same-origin page can still
read and mirror its own input.

**Asking for a credential** (`credential_request.rs`, `known_credential.rs`,
`origin_key.rs`). The tool is deliberately service-agnostic: the model names the
request and every field key, which is what lets it ask for a login no registry
entry anticipated. Two repairs run before anything is filed, because that
freedom is also how the model files a request nothing can find again. A website
key is rebuilt against the page origin (`canonical_web_key`). A request that
names a service the application already resolves — Google, Notion, Obsidian,
Anthropic — is redirected onto that credential's registry name and field spec
(`known_credential::canonicalize`); the two never both fire, since a host is not
a named service. The name is the store's dedupe key, so an invented one does not
collapse against the tools' own ask (the live store held `gmail_credentials`
pending beside `gmail_app_password`, and earlier `gmail_app_password_retry` and
`_new_link`), and an invented field key stores the answer where no tool reads
it. Matching is on whole tokens across the name, the user-facing service and the
field keys, and declines rather than guesses when two services match.
`rustykrab_store::registry` stays the source of truth: the table carries no
labels of its own, taking them from each entry's description, and a test asserts
every name and key in it resolves.

**Asking to pay** (`payment_request.rs`). The agent's side of a purchase: it
files the checkout's origin, merchant, total and currency with
`PaymentRequestStore::file` and mints a one-time `/p/` link through
`credential_link::mint_payment_link`, which goes to `PendingLinks` and never
into the tool result. HTTPS is required except for exact loopback hosts, which
the browser then refuses outside its test policy. The tool blocks the turn; the
store's `payment_authorized` hook resumes it. `payment_request` is seeded into
every conversation's active tools alongside `credential_request`, and the
credential tool now points card requests here instead of saying cards are
unsupported.

**Payment fill and pay** (`browser/payment.rs`, with element operations in
`browser/actions.rs` and `oopif::run_on_element`). `fill_payment` enters one part
of a card the user approved for this conversation (`PaymentRequestStore::
authorized_for`, keyed by conversation and live HTTPS origin) into one field.
The check and the assignment are a single page-side call: the field's top origin
(read from `location.ancestorOrigins`, since card fields sit in cross-origin
frames where `top.location` throws) must be the approved merchant; its own frame
and every intermediate frame must be the merchant or one of the fixed
`PAYMENT_FRAME_ORIGINS`; and the field must identify as the part named. Only that
part's value is passed into the page, and only constant status strings come
back. Unlike login fill, site-isolated frames are supported, through the raw-CDP
bridge. `pay` resolves a control on the merchant's own document, reads its label
and the page's text, and presses it with a trusted click only if
`check_total` finds a total in the approved currency no larger than the
approval — no total is a refusal. It presses nothing at all unless the page is
armed: a `pay` on a page no `fill_payment` touched, or one armed for an
approval a newer request has since superseded, is refused before the claim, so
an approval is never spent on a checkout with no card in it. It then
**claims** the press through
`PaymentRequestStore::claim_for_pay` before making it: the store moves the row
`authorized → paying` in one conditional `UPDATE`, and the arm presses only if
it won that row. This is what stops a double charge when two `pay` calls run
concurrently in one model turn, which the old flow permitted — it read a
*clone* of the card and the store's `mark_used` discarded its rows-affected
count. `approved_payment` is still called first, for the conversation, origin
and terms checks, but its card is dropped immediately; nothing here fills a
field. A refusal comes back as `status: "blocked"`, `outcome: "not_applied"`,
`retry_safe` from the refusal kind, and the refusal's model-facing message
under `guidance` — the one result key the agent runner leaves outside its
external-content fence, because the payment arms write it from literals and
`Money` displays rather than from the page.
`PayRefusal::Duplicate` also adds a `duplicate_of` object and, through the
`PendingLinks` handle the tool now takes (`BrowserTool::with_pending_links`),
sends the user the same alert `payment_request` sends — the model is being told
to stop, and a stopping turn is not a dependable messenger.
Pressing spends the approval (`mark_used`) unless the click provably never
reached the page, which is the one case that calls `release_claim` and hands
the card back. Because a claimed row is no longer `authorized`, `fill_payment`
refuses from then on: `authorized_for` returns nothing for a `paying` or `used`
request. From the first fill until `pay` or navigation,
the page is armed: evaluate, screenshot, pdf, HTML content, coordinate clicks,
Enter, and clicking a submit-like control are refused. "Submit-like" covers
controls in site-isolated frames (`SubmitVerdict::SiteIsolated`), which the
page-side heuristic cannot judge from the merchant's document: `prepare_pay`
refuses those refs, so reading them as ordinary controls left a checkout whose
pay button lives in the provider's frame with no total check on either path.
Both doors are shut, and the refusal tells the model to hand the checkout back
to the user. Submit detection and total
parsing are heuristics that fail closed (a discounted page showing a higher
original total is refused). A live Chrome test covers the contract with a
site-isolated provider frame and a provider frame nested under a foreign origin.

`tools_load.active` is filtered against the session's registered, available and
capability-permitted tools, not unfiltered default seed names. The registry keeps
activation intent; the report describes tools eligible now. This repairs the
captured absent-memory-tool contradiction with the next request's schema set.
Dynamic availability/schema-cache invalidation remains a separate gap.

Implement 50 of the system's 66 `Tool` impls, plus the security utilities that
guard them (SSRF host policy, output sanitisation, origin keying, sandboxed
subprocess spawning).

## Browser reliability boundary

The browser family treats Chrome as a stateful external runtime rather than a
stateless tool call. One mutable browser process is shared per named profile,
so browser calls take a per-profile lease; tab affinity and element refs remain
conversation-scoped. A profile recovery replaces the CDP client (and a managed
Chrome child), clears every conversation's sticky target in the manager, and
invalidates every snapshot capability minted by the old profile instance.
Managed Chrome uses its own persistent profile by default, avoiding locks and
write races with the operator's open Chrome. Borrowing the current system
profile remains available through `RUSTYKRAB_BROWSER_BORROW_SYSTEM_PROFILE=1`;
it reuses sessions at the cost of concurrent-profile reliability.
Credential fills derive an exact-origin v2 key and omit the secret from their
direct result. There is no hostname-only or Instagram legacy fallback and no
automatic migration. Existing secrets are not deleted, but users must re-enroll
under the exact-origin key. This is an intentional compatibility discontinuity.

Element refs include their snapshot generation (`s4-12`, `s4-e12`). Snapshot
selectors accept convenient attributes such as `data-testid` only when they
uniquely identify the element in its document or shadow root; duplicated
framework attributes fall back to structural identity. Child-frame refs also
carry their CDP frame id and observed URL. Snapshotting evaluates each reachable
frame in its own execution context (bounded to 100 frames, five nesting levels,
two seconds per frame, and ten seconds overall), so same-origin and cross-origin
frame elements use document-local selectors. Chromiumoxide does not expose
site-isolated `iframe` targets, so a private, short-lived raw-CDP connection
discovers only OOPIF targets associated with the selected page, attaches using
flattened target sessions, and records the owning target id on each ref. Actions
on those refs route native input to that target. Site isolation therefore stays
enabled by default; disabling it is an explicit compatibility escape hatch.
Detached, over-depth, or otherwise unreachable contexts are returned as
`frames_skipped` rather than silently described as an empty page. Like
browser-use, visible state is bounded to the current viewport plus 1,000 pixels
in each direction; distant controls and controls outside an overflow-clipping
ancestor become available after scrolling and a fresh snapshot instead of
flooding the model with virtualized calendars or feeds. Password input values
are always omitted from snapshots. Secure credential fill withholds automatic
post-action state; an explicit later snapshot is a separate observation.
Shadow-root and legacy iframe selector chains resolve through a shared DOM
resolver.

Actions resolve that identity in the captured document context, execute under
one absolute budget, and return an explicit `applied`/`not_applied`/`unknown`
outcome with post-action page state. That automatic state retains visible text
and refs for interactive elements but uses the compact line representation,
preventing dense pages from adding a full verbose accessibility object after
every click. The tool contract tells the caller to act from those returned refs,
take another snapshot only after a scroll or when surrounding text is needed,
and avoid unchanged observe-only loops. Snapshot output is capped at 40,000
serialized characters—the
same boundary used by browser-use—while the internal ref store retains all
captured elements for scoped follow-up. The accompanying observation status says
whether that state was captured, failed, or exceeded its separate five-second
budget, without changing the action outcome. Action name, ref, outcome, and
stage are logged for process-boundary diagnosis; typed text is not. Secure
credential fills log only their field, outcome, and stage—never the value,
length, or fingerprint. Clicks
bound scroll, geometry, mouse move, press, and release separately, watch and
accept renderer-blocking JavaScript dialogs, and expose the current target set
so popup tabs are visible to the caller. An ambiguous timeout is never retried
automatically; the profile is recovered and the caller must inspect new state.

The chromiumoxide handler's per-request timeout is configured below the action
and runner deadlines. Protocol messages rejected by its generated CDP decoder
are counted and rate-limited by method name (payloads are not logged), with
browser product/protocol, method counts, and the last decoder error surfaced by
browser status. A narrow compatibility classifier separately counts Chrome
152's `ClientSecurityState` policy-field rename in the unconsumed
`Network.requestWillBeSentExtraInfo` event; every other decoder rejection stays
an unclassified warning. This makes Chrome/protocol drift observable without
letting one known metadata mismatch conceal genuinely unknown failures.

Navigation policy is enforced on requested URLs and again on renderer-observed
destinations. It covers reads, post-action state, redirects, OOPIFs, and new
popup targets; a blocked target is quarantined to `about:blank` or closed before
its content is returned. Deny rules win over allow rules. Domain patterns are
limited to exact hosts and explicit leading wildcards. The guard is a tool-
boundary invariant, not a continuously running network interceptor: a page may
reach a disallowed URL between calls, but the next read/action refuses to expose
it and quarantines it.

Download observation is also profile-scoped because Chrome emits its lifecycle
at the browser connection rather than a page session. `downloads.rs` subscribes
before enabling `Browser.setDownloadBehavior`, correlates click-time sequence
markers with start/progress/terminal events, and keeps a bounded record set.
Page-controlled filenames are normalized to a basename on ingress. Completed
paths are exposed only after canonical filesystem containment under the
profile's configured download directory; a click result alone is never treated
as proof of download completion. Remote CDP profiles report download
observation as unavailable because RustyKrab has no remote artifact-transfer
channel and therefore cannot truthfully verify a browser-host path locally.
Attaching download observation to an externally owned browser is opt-in because
Chrome's download behavior is browser-wide and would also affect the operator's
tabs.

## The `tools_load` / `tools_list` pattern

Rather than sending 65 tool schemas on every model call, an
`ActiveToolsRegistry` (in `core`) tracks a per-conversation active set, and the
agent expands it by calling the `tools_load` meta-tool. The runner caches
computed schemas keyed by the active-set version, rebuilding only on change.

This is a good answer to a real problem (schema bloat on small local models)
and it is implemented in the right place — the registry is in `core`, so
neither `tools` nor `agent` owns the other's state.

## Backend traits

Six traits are defined here — `MemoryBackend`, `CronBackend`, `MessageBackend`,
`ComputerBackend`, `VideoBackend`, `SessionManager` — so that tools can depend
on a contract rather than a concrete store or channel.

The intent is right and the placement is wrong. Because the trait lives in the
consumer crate, `rustykrab-memory` cannot implement `MemoryBackend` without a
dependency cycle. It says so in a comment (`memory/src/backend.rs:34`) and
implements a structurally identical but unrelated method set, which
`cli/src/main.rs:56` then wraps in a pass-through adapter. Moving these traits
to `rustykrab-core` deletes the adapters.

`GatewayBackend` + `GatewayTool` + `automation_tools()` have **zero
implementors and zero callers** — dead.

## The abstraction is not applied uniformly

Thirteen files import `rustykrab_store` directly: `credential_read`,
`credential_write`, `credential_request`, `payment_request`, `credential_link`,
`google_credentials`, `gmail`, `caldav`, `notion`, `obsidian`, `mcp_connector`,
`browser/mod`, and `lib`. Two import `rustykrab_channels`.

So the crate has two access patterns for external state — trait-mediated for
six capabilities, direct for the rest — with no stated rule for which applies.
In practice the split is historical: the trait pattern was applied to what
existed when it was introduced. The credential path is the one that most wants
the seam (it is the security-critical one, and the one that most needs to be
testable in isolation).

## Observations

- **25 direct `env::var` reads.** `BROWSER_HEADLESS`, `CHROME_CDP_URL`,
  `CHROME_EXECUTABLE`, `X_API_BEARER_TOKEN`, `CANVAS_API_URL`,
  `RUSTYKRAB_MCP_SERVERS`, `RUSTYKRAB_NODES`, `RUSTYKRAB_SSRF_ALLOW_HOSTS`,
  `RUSTYKRAB_WORKSPACE`, … This is the single biggest reason the crate cannot be
  embedded elsewhere, and it has already produced one test race
  (commit `37c5036`). A `ToolsConfig::from_env()` at the composition root, passed
  down, fixes it.
- **`stub.rs` (448 lines) is evaluation scaffolding shipped in the production
  crate**, activated by `RUSTYKRAB_TOOL_STUBS`. It is well-guarded and loudly
  logged, and the e2e harness needs it. It still means the release binary
  contains a switch that replaces the entire tool registry. A cargo feature
  (`--features eval-stubs`) would make that structural rather than conventional.
- **`browser/` is a subsystem, not a tool.** It has its own
  config, manager, session lifecycle, selector engine, snapshotting and
  anti-detection logic. It would be a legitimate crate.
- **Per-integration credential handling is repeated.** `gmail`, `caldav`,
  `notion`, `obsidian` and `google_credentials` each resolve credentials, handle
  the missing case, and shape the "ask the user" flow. `google_credentials`
  (commit `5085277`, "one Google credential, one way of asking for it") shows the
  consolidation is already happening for one provider; the pattern generalises.
