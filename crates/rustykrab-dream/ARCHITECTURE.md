## Responsibility

The **outer loop**. `AgentRunner` is the inner loop — one turn, seconds to
minutes, with a policy fixed to whatever memory and skills currently exist. This
crate observes many inner-loop executions and reports on the durable artifacts
that parameterise them.

It implements the **Analyze** stage — deterministic, read-only aggregation over
`outcome_records` / `outcome_attributions`, with no model call — and the
**Plan/Execute** stages as a library: `engine.rs` stages, promotes and reverses a
change-set; `planner.rs` and `cluster_source.rs` decide what a consolidation
would be.

Nothing in the mutating half has a production caller. `ConsolidationContext` and
`rollback` are reachable only from tests, deliberately: `Readiness::permits_mutation()`
gates every cycle, and it cannot return true until a skill declares checkable
post-conditions. Merging the code does not arm it.

## Why this is the best-factored crate in the workspace

It depends on a trait, not a database:

```rust
pub trait OutcomeSource: Send + Sync {
    async fn tallies(...) -> Result<...>;
    async fn total_records(&self) -> Result<u32>;
    async fn verdict_totals(&self, ground_truth_only: bool) -> Result<OutcomeTally>;
}
```

`verdict_totals` is separate from `tallies` because the two answer different
questions. A tally describes an *artifact* and is necessarily reached through
`outcome_attributions`. Signal quality describes the *record population*, and
asking that through the attribution join makes the answer depend on how many
artifacts happened to be in play — a property of the traffic, not of the
evidence. Deriving readiness from skill attributions alone pinned a
skill-light deployment at `insufficient_data` regardless of record count.

`store_source.rs` — the only place that knows SQLite exists — is 34 lines. The
491-line analysis is pure, and its 13 tests use in-memory fakes with no database
at all. That is exactly the right dependency direction, and it is why the crate
is small.

## Epistemic discipline

The analysis refuses to overclaim, and the test names say so:

- `empty_evidence_reports_insufficient_rather_than_healthy`
- `thin_evidence_withholds_a_success_rate`
- `proxy_only_evidence_does_not_permit_mutation`
- `ground_truth_evidence_permits_mutation`
- `ambiguity_is_reported_not_hidden`
- `signal_quality_counts_a_record_once_however_it_was_attributed`
- `readiness_does_not_depend_on_whether_skills_were_active`

`Readiness::permits_mutation()` gates future write stages on evidence quality,
distinguishing verifiable ground truth from proxy signals. Most
self-improvement systems conflate "I have a number" with "I have evidence"; this
one has a type for the difference.

## The worker

Three stated properties, in priority order: off-cycle (never on the session-end
path, where it would add latency exactly when a follow-up is likely), yields
immediately (abort-and-retry rather than pause-and-resume, because a pass is a
handful of aggregate queries and partial progress isn't worth persisting), and
cannot affect correctness (reads only). Each is justified in the source rather
than asserted.

A completed pass is handed to an optional `ReportSink` before it is logged. The
row is the record; the log line is the convenience copy. Without persistence the
Phase 1 gate — "reports show real, actionable patterns" — could only be answered
by grepping rotated daemon logs, which is not a gate anyone can evaluate.
`rustykrab dream [N] [--json]` reads them back.

The worker takes its own `SQLITE_OPEN_READ_ONLY` connection
(`Store::outcomes_reader`). The store is a single mutex-guarded connection, so
even reads serialize through it; a pass aggregating the whole outcome table on
the shared handle would block live traffic for as long as it ran, WAL
notwithstanding.

## The mutating half

`MemoryMutator` takes **whole change-sets** (`apply_all`, `revert_all`) rather
than single operations. That is not a convenience: a per-operation trait cannot
express atomicity, and the previous shape applied change by change and unwound on
error — a best-effort imitation of a transaction whose unwind discarded its own
failures, and which a crash could interrupt.

Three preconditions are load-bearing and each was, at one point, missing:

- **Both sides of a retirement are checked for staleness.** A plan retires a
  cluster against the one member it keeps. Verifying only the memories being
  retired let the *survivor* be invalidated in the window between planning and
  promoting, after which every copy was retired against a dead memory and the
  fact left the retrievable set. This is the one way the loop can destroy data.
  The check runs before `apply_validity_batch`, not inside its transaction, so
  the window is narrowed rather than closed; the eval below holds that open.
- **A reversal walks what was applied**, read from `dream_changes.applied`, not
  what was staged. The manifest records the engine's post-reconciliation list,
  not the rows the batch changed, and no caller outside the tests reads
  `applied_changes()` yet.
- **A restore names the tombstone it expects.** Belt and braces for the above: a
  caller that passes the staged set anyway cannot resurrect anything.

`tests/invariants.rs` checks six properties over randomised populations, and
records which fault each one catches. Invariant 6 runs the *real*
`MemoryClusterSource` over real similarity links; the other five use a
content-identity source, which cannot see a clustering bug — lowering
`MIN_DUPLICATE_WEIGHT` to the retrieval threshold fails invariant 6 while
leaving the rest green.

## Evals

The invariants prove properties over what their generator produces. `eval.rs`
is the protocol for properties the code is *known* not to meet yet: an eval
declares `Expected::Pass` or `Expected::XFail("what is missing")`, runs under
`DREAM_EVAL_SEEDS`, and appends one JSON line to `DREAM_EVAL_REPORT`. An
expected failure keeps the suite green; an unexpected pass turns it red so the
eval is promoted and the fix pinned — the e2e harness's convention, applied to
properties. `tests/evals.rs` holds the consolidation evals (the distinct
similarity band, chain-shaped oversized components, a second writer inside the
promote window, the manifest recording effect rather than intent, vector
retrieval after a reversal); `rustykrab-cli/tests/outcome_evals.rs` holds the
outcome-contract ones (the runtime's own write-back satisfying `MemoryWritten`,
an errored run with nothing produced scoring `Ambiguous`). Both files say, per
eval, why the failure is expected. `.github/workflows/dream-evals.yml` runs the
lot nightly at 300 seeds and summarises the report on the run page.

## Observations

- **Its central input crosses a database boundary it cannot see.** For
  `kind = 'memory'`, `outcome_attributions.target_id` names a row in
  `memory.db`. The analysis reports findings against ids it cannot resolve,
  cannot join, and cannot detect the deletion of. A tombstoned memory keeps
  accumulating verdicts. This is the strongest single argument for `ATTACH`-ing
  the two databases or merging them.
- Outcome capture is off by default (`RUSTYKRAB_OUTCOME_CAPTURE`), so in a
  default deployment this crate runs and finds nothing. Correct for an opt-in
  instrumentation feature; worth knowing when reading the code. On macOS the
  daemon reads that variable from its LaunchAgent plist, which `install.sh`
  rebuilds — so enabling it is not a one-time action.
- Readiness cannot reach `Ready` until some skill declares an `[outcome]` block
  whose checks name registered post-condition probes. That gate is deliberate,
  and it is currently shut on every known deployment.
