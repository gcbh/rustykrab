## The `Channel` trait does not describe this crate

```rust
pub trait Channel: Send + Sync {
    fn name(&self) -> &str;
    async fn receive(&self) -> Result<Message>;
    async fn send(&self, message: &Message) -> Result<()>;
}
```

One implementor: `WebChatChannel`. `TelegramChannel`, `SlackChannel`,
`SignalChannel` and `VideoChannel` are concrete types with no common interface.
The consequences are all downstream:

- `AppState` holds four separate `Option<Arc<ConcreteChannel>>` fields.
- `ChannelHub` in the CLI dispatches by matching on a channel-name string.
- Each channel has its own agent loop in `cli/src/main.rs`
  (`telegram_agent_loop`, `slack_agent_loop`, …).
- Telegram and Slack each get a bespoke `*_chat_map` table and store module;
  Signal gets neither.
- Cron delivery has to resolve `(channel, chat_id, thread_id)` by string match.

The reason the trait doesn't fit is that it is too narrow. A real channel
abstraction for this system needs: an addressing key (what identifies a
conversation on this surface), threading, typing/presence indication, an inbound
stream rather than a single `receive`, and outbound chunking limits. Those are
exactly the five things each concrete channel implements privately today.

Two honest options: widen the trait to cover them and store
`Vec<Arc<dyn Channel>>`, or delete `Channel` and stop implying pluggability
that isn't there. The current state advertises an abstraction the code doesn't
have, which is worse than either.
