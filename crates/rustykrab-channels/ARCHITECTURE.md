## Host commands and buttons on Telegram

`TelegramChannel::with_command_hook` takes a `CommandHook` the host
implements: a command the built-ins (`/start`, `/help`, `/ping`, `/reset`)
do not know is offered to the hook before the message reaches the agent, and
a command it handles never enters a conversation. The composition root's hook
is the control layer's work surface (`/work`, `/approve`, `/reject`,
`/cancel`, `/answer`, `/questions`; `rustykrab-cli/src/work_channel.rs`), so an
answer resumes the work item that asked, not the chat. `/help` lists the
hook's lines. `send_text_with_buttons` sends plain text with an inline
keyboard (a plan preview's approve and reject, a question's options), falling
back to the plain text when Telegram refuses the buttons; a press arrives as a
`callback_query` update, is checked against the chat allowlist, is mapped to
the command it stands for (`command_for_button`: `approve:<id>`,
`reject:<id>`, `answer:<question>:<option>`) and answered like the command
typed.

## The `Channel` trait does not describe this crate

```rust
pub trait Channel: Send + Sync {
    fn name(&self) -> &str;
    async fn receive(&self) -> Result<Message>;
    async fn send(&self, message: &Message) -> Result<()>;
}
```

One implementor: `WebChatChannel`. `TelegramChannel`, `SlackChannel`,
`SignalChannel` and `VideoChannel` are concrete types with no common interface.
The consequences are all downstream:

- `AppState` holds four separate `Option<Arc<ConcreteChannel>>` fields.
- `ChannelHub` in the CLI dispatches by matching on a channel-name string.
- Each channel has its own agent loop in `cli/src/main.rs`
  (`telegram_agent_loop`, `slack_agent_loop`, …).
- Telegram and Slack each get a bespoke `*_chat_map` table and store module;
  Signal gets neither.
- Cron delivery has to resolve `(channel, chat_id, thread_id)` by string match.

The reason the trait doesn't fit is that it is too narrow. A real channel
abstraction for this system needs: an addressing key (what identifies a
conversation on this surface), threading, typing/presence indication, an inbound
stream rather than a single `receive`, and outbound chunking limits. Those are
exactly the five things each concrete channel implements privately today.

Two honest options: widen the trait to cover them and store
`Vec<Arc<dyn Channel>>`, or delete `Channel` and stop implying pluggability
that isn't there. The current state advertises an abstraction the code doesn't
have, which is worse than either.

## Telegram send acknowledgement

Text and button sends validate the Bot API `ok` envelope, positive message ID
and intended chat/topic. HTTP success alone is not delivery.
`send_text_with_receipts` returns every chunk's acknowledged ID; unreadable or
misaddressed success responses fail without a blind resend. A partial multi-chunk
failure can have delivered earlier chunks; this is not an exactly-once protocol.
Ordinary text sends retain their unit-returning interface over the receipt path.

Text and inline-button sends share a serialized request gate and a monotonic
flood-control deadline. HTTP 429 waits use parameters.retry_after and the HTTP
Retry-After header (seconds or an HTTP date), taking the longer valid delay.
Missing or malformed delays use five seconds. The deadline survives exhausted
retry batches so concurrent senders and subsequent outbox passes wait too.
Successful button retries keep their keyboard. This does not add durable
multipart checkpoints; general multi-chunk text still has the partial-delivery
limitation described above.
