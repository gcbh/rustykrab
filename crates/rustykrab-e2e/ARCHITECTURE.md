## Responsibility

The context suite joins real `tools_load` output to the next actor request's
offered schemas, and rejects phantom active/loaded names. A deterministic HTTP
and Telegram case forces this transition with a missing seeded memory tool;
the fake provider supplies the call, not the real meta-tool's response. This is
an availability-contract check, not a model-quality score. The optional neutral
browser-ready stub is a separate prerequisite control, not real navigation.

`context` now also covers Telegram provider-failure persistence and a mid-run
follow-up injected while the first model request is blocked at a fixture barrier.
It joins native prompt logs, exact Ollama wire bodies, final SQLite messages and
channel replies. The adversarial compaction case is a retention regression now,
not a passing expectation of data loss. `context-model` excludes deterministic
Telegram fault fixtures. Credential/payment-boundary hardening is isolated in
the final stack layer; real Chrome regressions live beside BrowserTool and
write synthetic-only evidence to an explicitly selected artifact directory.

Boot the real daemon binary on a throwaway data directory and an ephemeral port,
drive scenarios over HTTP, and assert on **both** the responses and the
resulting store state. Emit a JSON report and a matching exit code.

One daemon and one database serve every scripted scenario, in the order
`scripted_scenarios()` lists them, so a scenario's state is visible to the ones
after it. That is usually harmless and occasionally load-bearing: the payment
scenarios now each use their own trigger, merchant and amount, because the
duplicate hold would otherwise stop the second scenario to ask to pay the same
site the same amount and the suite would be measuring its own interference.

## The xfail mechanism is the good idea here

Scenarios encoding not-yet-built behaviour are marked **xfail**: the suite stays
green while they fail, and a phase ships by flipping its scenarios to must-pass.
An unexpected pass (**xpass**) *fails* the suite, forcing the scenario to be
promoted rather than silently drifting into "passing but not required".

That is a real answer to the usual problem with aspirational tests — they either
block the build or get ignored. Encoding the exit criteria of a development
phase as executable, currently-failing scenarios means the plan and the test
suite cannot diverge.

## Design

The daemon suites' execution boundary is black-box: they drive the built binary over HTTP and
asserts on the SQLite file the binary wrote. It does not link or invoke the
daemon's turn assembly. Besides `store`, the context suite links `tools` only to
obtain production schemas/descriptions for inert replacements, and `core` for
the tool trait and argument validator. Those dependencies do not execute the
domain tools or substitute for observing the actual daemon's outgoing request.

The separate `compaction-study` mode links `agent` and `providers` to exercise
the production compactor directly, then captures the real Ollama adapter wire
request. It bypasses daemon prompt assembly, channels, database loading and
domain action execution. Its one `session_checkpoint` tool is an inert readout
of intent, direction, facts and proposed next action, not an agent success
claim. Legacy, structured prompt, whole-user-turn tail and extractive variants
share the same budget ceiling, model and actor prompt; full history is a
reference. An explicitly labelled exploratory `message-tail` arm uses smaller
atomic message groups while preserving assistant-call/result pairs. Oversized
tool exchanges may be archived whole so nearby short dialogue fits; this is
not a contiguous raw history suffix. Artifacts
bind exact source/model/configuration, original and compacted histories, wire
bytes and scores. Keyword rubric failures require auditing against visible
output and retained context; an omitted readout is not proof of lost memory.

The scripted suite owns its daemon through a restartable process handle. A
restart scenario terminates that process, verifies the health endpoint is no
longer reachable, boots a distinct PID on the same port and data directory, and
only then inspects the recovered API and SQLite state. Snapshot reconstruction,
daemon restart, and model-context compaction are separate scenario contracts;
one is never reported as proof of another.

The two production affordances it relies on — `RUSTYKRAB_PROVIDER=scripted`
(`providers/scripted.rs`) and `RUSTYKRAB_TOOL_STUBS` (`tools/stub.rs`) — are the
price of that. Both are loudly logged and clearly documented as harness
switches, but they are compiled into the release binary rather than gated behind
a cargo feature. Feature-gating them (`--features eval-harness`) would keep the
capability and remove it from production builds.

The harness writes its aggregate report and scenario-specific JSON evidence to
`E2E_ARTIFACT_DIR` (default `target/e2e-artifacts`). Planning scenarios do not
pass on HTTP shape alone: they query `store.db` for the project, revision, and
materialized node rows, then persist those counts with the service response and
fixture-repository revision. Authority tests also attempt forged metadata and
changed idempotent retries, require zero forbidden rows, and preserve their
status codes. Hosted CI uploads this directory together with the stdout report;
artifact paths reject absolute paths and traversal. The launcher resolves the
checkout's exact Git SHA and the artifact writer embeds it as `source_revision`
in every JSON object, binding those observations to the code that produced them.
Live browser and login modes reject an unrecorded revision: operators use
`scripts/e2e.sh`, which rebuilds both the daemon and evaluator, or explicitly
provide both the tested binary and revision. This prevents a freshly rebuilt
evaluator from silently driving an older daemon left in `target/`.

The live browser suite is deliberately excluded from `--mode all`. It drives
third-party websites whose markup, bot checks, inventory, and authentication
policies are outside the repository's control, and its Instagram and United
cases consume operator-supplied credentials. Each configured trial boots the
real daemon against a fresh data directory, CDP port, and browser profile. Its
verdict is not based on the assistant's claim alone: it reads the persisted
conversation and requires browser navigation, fresh snapshots, applied
ref-based clicks, route inputs, visible route/date evidence, and—in login
cases—two successful `fill_credential` operations plus the configured account
marker in a browser observation after a submit click. Merely filling the form
cannot pass. Flight cases also require a price and departure time in browser
output after route/date entry and their minimum result-click boundary. Reports
retain aggregate counts and redacted replies, never usernames, passwords, or
raw browser output. Runtime logs retain action names and outcomes, but not typed
text, so interrupted turns still expose applied-click evidence safely.

## Observations

### Context production and task continuity

`--mode context` drives the real daemon, SQLite loading, HTTP/Telegram turn
assembly, compaction, and Ollama adapter against a loopback response fixture.
`--mode context-model` forwards those same requests to an explicitly selected
loopback Ollama. Browser, search, fetch, and code execution are inert scripted
tools with their production descriptions/schemas from the evaluator checkout;
only in-process discovery and completion tools remain real. Neither mode
is included implicitly in `all`. CI runs the deterministic mode separately,
explicitly selecting the message-tail retention candidate; Legacy remains the
production default and still fails the deliberately lossy recent-context fixture.
`RUSTYKRAB_CONTEXT_COMPACTION_STRATEGY` selects an explicit typed harness policy
for daemon trials and records it in the manifest; it does not change the live
daemon's configuration or silently replace a policy in the runner.
`RUSTYKRAB_CONTEXT_BROWSER_READY=1` is a separate prerequisite-control fixture:
the first inert browser call returns neutral readiness, then subsequent calls
fail. It provides no site, date, action-applied receipt or task answer. This
helps distinguish startup blockage from inability to choose a task-specific
request. The default always-unavailable fixture and its failures are retained;
neither variant proves a real browser navigation or website success.

Each trial starts from synthetic message rows in an empty fixture conversation,
verifies the seeded rows independently, submits a real follow-up at the channel
boundary, and captures both the optional pre-provider prompt trace and the
actual post-conversion HTTP body (or an explicit pre-dispatch budget refusal). Output artifacts include the
initial and final message rows, ordered exchanges, tool schemas, model options,
terminal usage metadata, and per-call retention checks. SHA-256 fingerprints
bind the wire bytes, daemon binary, evaluator binary, and compiled fixture/grader;
live manifests also record Ollama version, model metadata/template, and digests.
Only synthetic inputs are accepted; this is not an importer of production data.

The missing-history negative control passes only when the perturbation is
detected, not because continuity passed. The former provider-trim case is now
a regression requiring explicit refusal, zero outgoing requests and intact
durable inputs. The adversarial compactor is required to retain the newest
instruction independently of its lossy summary. These distinct invariants are
reported separately rather than treating all negative controls as success.
The generation-limit fixture returns an actual adapter-level length stop and
requires intact SQLite history with no following actor request; it is not a
direct call to a mocked compactor. The fieldwise-corrections follow-up separately
tests whether unchanged constraints remain active after a date/preference update.
The live action rubric requires a task-related tool request, rejects clock
drift, and does not count generic Google navigation or a claimed completion as
success. It separately reports task alignment and validates calls against the
schemas actually offered on that request. An on-task but invalid call cannot
pass. This reuses the runner's intentionally limited schema validator, not the
tool's execution-time checks. Unknown action forms remain unverified.

The proxy buffers responses, tools and skills differ from the historical
incident, and the local model's final rendered token input is not observed.
Consequently this is boundary interoperability plus an optional bounded model
behavior evaluation, not an exact historical replay, browser-functionality
test, or production latency measurement. See
[`docs/evals/context-continuity.md`](../../docs/evals/context-continuity.md).

- Roughly 7,200 lines of harness against the larger system is a healthy ratio, and
  the presence of an ablation runner and an LLM judge means the harness is
  measuring quality, not just liveness.
- Fifteen direct environment reads, all appropriate for a test driver; evidence
  location and source revision are explicit inputs to the run.
- Supporting modules such as surface, assertion, transcript, judge,
  classification, planning scenarios, and repository fixtures each have one
  job. `main.rs` still combines process supervision, deterministic scenario
  definitions, and report assembly; it is the clear next extraction boundary
