## The xfail mechanism is the good idea here

Scenarios encoding not-yet-built behaviour are marked **xfail**: the suite stays
green while they fail, and a phase ships by flipping its scenarios to must-pass.
An unexpected pass (**xpass**) *fails* the suite, forcing the scenario to be
promoted rather than silently drifting into "passing but not required".

That is a real answer to the usual problem with aspirational tests — they either
block the build or get ignored. Encoding the exit criteria of a development
phase as executable, currently-failing scenarios means the plan and the test
suite cannot diverge.

## Design

Black-box by construction: it drives the built binary over HTTP and asserts on
the SQLite file the binary wrote. It never links the daemon's internals. That
makes it a genuine integration test rather than a large unit test, and it is why
`rustykrab-store` is its only dependency.

The scripted suite owns its daemon through a restartable process handle. A
restart scenario terminates that process, verifies the health endpoint is no
longer reachable, boots a distinct PID on the same port and data directory, and
only then inspects the recovered API and SQLite state. Snapshot reconstruction,
daemon restart, and model-context compaction are separate scenario contracts;
one is never reported as proof of another.

The two production affordances it relies on — `RUSTYKRAB_PROVIDER=scripted`
(`providers/scripted.rs`) and `RUSTYKRAB_TOOL_STUBS` (`tools/stub.rs`) — are the
price of that. Both are loudly logged and clearly documented as harness
switches, but they are compiled into the release binary rather than gated behind
a cargo feature. Feature-gating them (`--features eval-harness`) would keep the
capability and remove it from production builds.

The harness writes its aggregate report and scenario-specific JSON evidence to
`E2E_ARTIFACT_DIR` (default `target/e2e-artifacts`). Planning scenarios do not
pass on HTTP shape alone: they query `store.db` for the project, revision, and
materialized node rows, then persist those counts with the service response and
fixture-repository revision. Authority tests also attempt forged metadata and
changed idempotent retries, require zero forbidden rows, and preserve their
status codes. Hosted CI uploads this directory together with the stdout report;
artifact paths reject absolute paths and traversal. The launcher resolves the
checkout's exact Git SHA and the artifact writer embeds it as `source_revision`
in every JSON object, binding those observations to the code that produced them.
Live browser and login modes reject an unrecorded revision: operators use
`scripts/e2e.sh`, which rebuilds both the daemon and evaluator, or explicitly
provide both the tested binary and revision. This prevents a freshly rebuilt
evaluator from silently driving an older daemon left in `target/`.

The live browser suite is deliberately excluded from `--mode all`. It drives
third-party websites whose markup, bot checks, inventory, and authentication
policies are outside the repository's control, and its Instagram and United
cases consume operator-supplied credentials. Each configured trial boots the
real daemon against a fresh data directory, CDP port, and browser profile. Its
verdict is not based on the assistant's claim alone: it reads the persisted
conversation and requires browser navigation, fresh snapshots, applied
ref-based clicks, route inputs, visible route/date evidence, and—in login
cases—two successful `fill_credential` operations plus the configured account
marker in a browser observation after a submit click. Merely filling the form
cannot pass. Flight cases also require a price and departure time in browser
output after route/date entry and their minimum result-click boundary. Reports
retain aggregate counts and redacted replies, never usernames, passwords, or
raw browser output. Runtime logs retain action names and outcomes, but not typed
text, so interrupted turns still expose applied-click evidence safely.

## Observations

- Roughly 7,200 lines of harness against the larger system is a healthy ratio, and
  the presence of an ablation runner and an LLM judge means the harness is
  measuring quality, not just liveness.
- Fifteen direct environment reads, all appropriate for a test driver; evidence
  location and source revision are explicit inputs to the run.
- Supporting modules such as surface, assertion, transcript, judge,
  classification, planning scenarios, and repository fixtures each have one
  job. `main.rs` still combines process supervision, deterministic scenario
  definitions, and report assembly; it is the clear next extraction boundary
  if the harness grows.
